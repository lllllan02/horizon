**并发控制防止多个任务的总消耗压垮服务。** 单个沙箱即使有内存上限，同时启动太多仍可能超出机器容量。它限制执行环境的总量，[[tool-scheduling|工具调度]]另行判断调用之间的依赖与资源冲突。

| 面临什么情况 | 对应做法 |
| --- | --- |
| 任务资源需求接近 | 设置同时运行的名额上限，用信号量等机制原子占用 |
| 任务需求差异很大 | 按资源需求分配不同权重，为服务自身留出余量 |
| 名额暂时用完 | 有界排队；限制队列长度与等待时间，超出则拒绝或稍后重试 |
| 多台执行器共享同一容量 | 使用共享名额或预分配额度，不能每台各自放满 |

**申请名额 → 占用 → 创建并运行 → 完成清理 → 释放。** 创建失败、取消和超时也需回收；后台进程仍占资源时不能提前归还名额。

先明确名额代表一条命令、一个容器还是一台 VM，并让限制落在实际管理该资源的服务上。安全上限由容量与负载验证决定，没有通用数量。

这与启动速率限制不同：每秒只启动一个任务，任务若都长时间不结束，仍会积累。并发控制要与[[sandbox-resources|单任务配额]]、[[sandbox-processes|进程清理]]配合。

## 为什么请求已经入队，用户仍然长时间等不到结果？

大任务长期占用全部名额，小查询排在后面；用户已经取消的请求又没有及时出队。单一并发上限只能防止总量失控，不能保证公平性或有用吞吐。

可按任务资源需求和租户分配额度，限制每个请求的排队时间，取消时移除尚未启动的任务。预估资源只是准入依据，执行期间仍要用真实配额约束；排队超时与执行超时分开报告，否则容易误认为模型响应慢。

执行器失联后也不能仅因占用记录过期就立即认定资源已经释放。先核对或终止残留实例，再回收容量；否则旧任务仍消耗资源，新任务又占用了相同名额。观察排队时长、拒绝量和清理延迟，才能定位容量不足还是回收失效。
