**协作与控制模式是约定多个 Agent 怎样分工、谁持续负责，以及谁接续处理任务的组织方式。** 在[[multi-agent-orchestration|多 Agent 编排]]中，需要根据中间成果调整任务，或让成员利用彼此的发现时，这些约定让分工与后续处理衔接起来。

本篇关注「**成员怎样分工、谁决定后续处理**」；任务的先后、并行与循环由[[multi-agent-flow-patterns|流程模式]]描述。

## 常见协作与控制模式

下面从[[multi-agent-orchestration-sources|持续协调、接手处理与共同讨论]]观察成员关系；这些方式可以组合，并非互斥分类。图中的成员数量仅作示意。

![[assets/multi-agent-collaboration-patterns.png|640]]

- **主管与执行者（Supervisor / Manager）**：主管分配子任务、收取成果，再决定补查或汇总。适合需要统一约束与综合判断的任务，依赖主管的分解与核验能力。把[[langchain-multi-agent#具体怎样实现？|子 Agent 包装成工具]]调用，就是「**Agent 作为工具（Agents as Tools）**」：专家返回成果，主管继续负责。

- **控制权交接（Handoff）**：A 把后续处理权交给 B，由 B 接续任务或对话。适合需要切换专业角色的阶段，重点是「**谁接手后续处理**」；须避免来回转交却无人完成。它与工具式调用后返回主管的控制关系不同。

- **群组对话（Group Chat）**：多个成员在共享会话中轮流贡献，回应已有讨论。适合需要讨论或共同修订的任务；须选择发言者、控制上下文与结束条件，也可以由协调者主持。

## 任务怎样分解与委派

成员关系确定后，还要分别考虑任务从哪里来，以及是否继续向下分派：

- **动态任务分解（Orchestrator–Workers）**：按具体输入临时形成子任务，再分发和综合。它可由主管实现，区别于预先写好的固定分支。
- **层级任务分解（Hierarchical Task Decomposition）**：成员 A 接收上层任务后，又向 A1、A2 分派，形成[[multi-agent-orchestration-sources#Google ADK：分派、分解与反馈|逐层委派、成果返回]]的结构。A「**对上是执行者，对下是主管**」，适合仍需细分的任务，也增加信息压缩与协调成本。

动态分解可以发生在一层或多层；父／子 Agent 表示相对创建或嵌套关系，不代表能力等级。「任务委派（Task Delegation）」只是交出工作的宽泛说法，仍须看成果返回谁、后续处理由谁负责。

## 有无主管怎样影响组织结构

**是否有主管、成员能否直连、是否分层委派，需要分开判断。** 可以从三个角度观察：

- **谁持续协调**：主管根据进展分派、调整任务；没有固定主管时，也可由程序安排独立分支与末尾汇总。固定汇总点不等于动态协调的主管。
- **成员怎样联系**：集中协调主要经主管交换信息；对等协作允许成员直接交流；混合结构保留主管，也开放成员直连。
- **委派是否分层**：观察前述逐层委派关系；有主管不意味着只有一层。

[[multi-agent-study-sources#Google：协作效果取决于任务和开销|架构对照研究]]展示了主管与成员直连的不同组合，并未穷尽全部组织结构。群组对话也可由协调者选择发言者，不能直接归为「无主管」。

这些关系可以组合：主管既可依次调用专家，也可并行委派，或按输入路由到合适的专家。
