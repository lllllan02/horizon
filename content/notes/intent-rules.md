**规则式意图识别是用人工编写的匹配条件，把用户表达映射为意图标签。** 无需训练，适合固定命令和少量约定句式；按钮已有动作 ID 时可直接校验。

## 整套规则怎样运行？

用户表达 → 清理约定格式 → 检查所有适用规则 → 汇总命中 → 返回标签或未确定结果

例如收到「请帮我申请退款」，程序先检查它是否符合申请退款的句式，再返回 `refund_submit`。每条规则保存匹配条件、标签和规则编号，后者用于解释为什么命中。规则只决定任务类别，订单号、权限与退款资格仍由后续程序处理。

## 匹配条件怎样写？

可以使用字符串相等、关键词或正则表达式。简单包含「申请退款」也会误中「不要申请退款」；固定句式可以改成整句正则：

```text
^(请)?(帮我)?申请退款$
```

`^…$` 限定整句，`?` 表示前一部分可省略，因此接受「请帮我申请退款」，拒绝「不要申请退款」。**「限制越严格，漏掉的说法也越多。」** 未命中只表示规则没有覆盖，不能直接判断业务不支持。

清理首尾空白和句尾标点时应按约定处理，保留否定等会改变意思的内容。规则也可受[[dialogflow-intent-design|当前对话状态]]约束，使退款确认页的「确认」只绑定当前申请。这里的规则直接返回标签，与[[rasa-intent-classification|向分类模型提供线索的正则]]职责不同。

## 命中以后怎样决定下一步？

| 命中情况 | 后续处理 |
| --- | --- |
| 只命中一个意图 | 合并同标签命中，返回标签与规则编号，进入参数和业务校验 |
| 没有命中 | 返回 `no_match`，可交给模型继续识别 |
| 命中不同意图 | 返回 `ambiguous`，进入[[intent-clarification\|澄清与回退]] |

不要简单取排列最前的规则；若设置优先级，需要验证它不会遮住正确结果。识别到申请退款，也不能跳过订单归属、资格与执行条件。

## 怎样验证与维护？

用明确请求、否定、相似说法和多目标请求做[[intent-evaluation|回归评测]]，记录规则版本、命中编号、未匹配率及错误样本。命中率上升不一定更准确；正常请求大量回退或否定补丁持续增加时，可考虑分类模型，让规则继续负责固定命令。

[[assets/intent-rules-demo.go|完整 Go 示例]]保留规则定义、命中合并与七条输入；在仓库根目录执行 `go run content/assets/intent-rules-demo.go`，仅依赖标准库。示例只识别标签，未实现状态约束、参数提取和业务调用。

## 新增一条规则，为什么会破坏原本正常的表达？

为了覆盖「帮我退款」增加“包含退款就进入申请”的规则，会同时误伤「不要退款」「退款规则是什么」。规则优先级越多，局部补丁越容易截走后续更合适的路径。

每条规则都应有适用场景、排除条件和冲突处理。只在明确命令或固定界面上下文中直接路由；命中多个互斥动作时返回歧义，不靠代码顺序偷偷决定。对自由表达保留模型或人工回退，不强求关键词规则覆盖所有说法。

新增规则时同时检查正例、否定表达和原来由其他规则处理的近邻用例。保留命中规则及版本，发生误路由时先判断是规则过宽、优先级冲突还是上下文缺失，避免继续叠加特例。
