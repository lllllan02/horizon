**任务拆分（Task Decomposition）是把整体目标划分为可分别完成和验收的子任务的过程。**

LLM 一次处理复杂任务时，需要同时追踪多项要求和中间结果，容易遗漏或混淆。把大任务拆成小步骤，让每步聚焦一个明确目标，有助于[[xiaolin-task-decomposition-summary|降低单步复杂度、减少错误]]；每步产出也能单独检查，及时纠正问题，避免影响后续步骤。实际收益取决于任务和拆分质量，并非拆得越细越准确。

显式计划（Plan）是记录子任务依赖、顺序与进度的安排，同一个 Agent 即可执行。拆分和维护计划也有成本，因此需要判断当前任务是否值得拆。

## 什么时候拆？

**按已知做法完成同一项改动，就能兑现全部要求，而且无需另排阶段时，不必拆分。** 同一规则的批量操作也适用。

先检查是否满足「不必拆」的三个条件：

1. 做法已知：能说清「对什么对象，做什么操作」；尚需选方案或验证关键可行性，就不满足。
2. 同一项改动即可交付：做完就兑现全部要求。代码和对应测试可算一项；SSO 的认证、会话、应用接入需要分别实现，即使架构已知，也需要拆分。
3. 无需分阶段推进：普通的读取、修改、测试可直接收尾；先试点再全量、迁移切换与回退等需要另排阶段。

**三项都满足，直接做；明确不满足，先规划；缺少事实，先查证。** 不知道函数位置可以先搜索；文件多、重复操作多或等待久，本身不触发拆分。

![[assets/agent-task-decomposition-direct.png|不必拆分的三项检查及具体正反例；三项满足才直接执行，缺少事实先查证]]

可复制的[[assets/agent-planning-decision.txt|判定提示词]]要求逐项给出事实依据。已有计划覆盖的步骤沿用原计划；用户明确要求 Plan 时遵从。

这是根据[[claude-codex-planning-summary|Claude Code 与 Codex 的规划条件]]归纳的工程策略；来源未给出统一步数或时长阈值，这套判定也尚未评测准确率。

## 怎么拆？

**按需要单独确认的结果划分子任务，按前置依赖安排顺序。** 每项写清前置条件、完成结果和验收方式，再判断颗粒度：

| 结论 | 判断标准 |
| --- | --- |
| 继续拆 | 还有需要分别验收的要求，或必须先确认一个结果，才能决定、放行后续工作 |
| 停止拆 | 前置已具备、结果与验收明确，内部没有其他必须单独确认的结果 |
| 合并回去 | 只拆出了读文件、改代码、跑检查等操作；合并不会丢失独立要求的完成状态、关键决定或阶段条件 |

这些标准根据[[codex-execplans-summary|ExecPlans 对里程碑与细粒度进度的区分]]归纳；来源未提供统一颗粒度阈值。操作可以记在内部清单里，不必各占一个计划项。

图用同一任务对比三种粒度：需要分别验收的行为拆开，服务于同一结果的查询、修改和验证留在一起。

![[assets/agent-task-decomposition-granularity.png|同一 B 接入任务的太粗、合适、太细三种划分；按独立验收点拆开，将内部操作合回各自任务]]

只细化近期工作，远期保留里程碑；用[[anthropic-long-running-harness-summary|功能清单]]核对全部要求并保留整体验收。前提改变时[[agent-replanning|调整计划]]，跨会话用[[agent-task-state|任务状态]]记录完成与剩余工作。
