**意图识别的评测是用有参考答案的请求，检查系统是否理解正确并进入正确流程。** 不能只看标签命中率：把「只查资格」送进退款流程，即使其他类别表现很好，也属于需要优先处理的错误。

## 整套验证怎样进行？

准备代表性请求 → 检查分类、参数与路由 → 调整接受条件 → 比较版本 → 小流量观察与回滚

测试既包含单句，也包含补参、改口与撤回的完整对话。[[intent-production-testing|Lex、Dialogflow 与 Rasa 的测试资料]]分别提供逐轮检查、发布前回归和数据冲突检查的依据。

## 测试数据怎样准备？

每条用例保存当前消息、必要状态、期望任务和参数，以及允许或禁止的下一步。例如：

```json
{"text":"先别退，只查订单 A 能不能退","intent":"refund_eligibility","order_id":"A","forbidden":"submit_refund"}
```

这是教学格式。真实样本用于观察日常表现，否定、域外、含混与条件请求用于检查边界。含混输入可标为应澄清，不能强行分入业务类别。

训练集用于学习，验证集用于选择模型、提示和阈值，最终测试集检查选定方案。按会话、模板或时间分组，避免只换订单号的句子分散到训练与测试。标注分歧先检查类别定义；[[rasa-nlu-data-practice|数据版本]]也要随模型保留。

## 看哪些结果才能定位问题？

| 检查 | 要回答的问题 |
| --- | --- |
| 每类查准率、查全率 | 判为这类的请求有多少正确；真实属于这类的请求找回多少 |
| 接受率与接受后的错误率 | 自动处理了多少；其中又错了多少 |
| 域外误接受 | 不支持的请求是否被硬塞进业务流程 |
| 参数与会话结果 | 对象、条件及跨轮变化是否正确，任务是否实际完成 |

类别分布不均时，可以用 Macro-F1 汇总各类的查准与查全表现，使小类也有同等权重；它仍不能代替具体错误分析。分母为零的指标记为不适用。[[azure-clu-intent-design|CLU 的评估口径]]提醒，模型分类表现与应用回退后的结果可能不是同一口径。

## 阈值怎样选？

阈值是最低接受分数。固定模型后，在验证集比较不同阈值及候选分差，同时观察覆盖与错误，按业务误操作成本选择，再用独立测试集验收。提高阈值通常拒绝更多请求，不能只看剩下的少量请求是否全对。

[[assets/intent-thresholds-demo.py|阈值示例]]用 Python 3 标准库比较五条自拟记录，运行 `python content/assets/intent-thresholds-demo.py` 即可。阈值 0.50、0.80、0.95 的接受率依次为 100%、60%、20%，接受后错误率为 40%、约 33.3%、0%；最后只接受一条，不能据此宣称可上线。示例仅检查计算，不代表业务效果。

## 版本怎样上线与排错？

以下是自建服务的设计建议：固定数据、模型或提示、输出结构及阈值版本；先用同一批请求回放，再让新版本读取实际请求副本但不执行业务动作，最后按会话小流量发布。观察误路由、回退、完成率、成本与延迟；退化时回滚，但已执行动作不会随模型回滚撤销。

记录会话、识别版本、候选、回退原因、所选流程和执行结果，原文按隐私要求处理。分类对却调用错接口，检查路由；改订单后沿用旧资格，检查状态；新版本才退化，比较配置和数据。尚未验证真实流量上的质量与性能。

## 分类标签都对，为什么用户任务仍然失败？

模型正确识别“条件退款”，却把“低于 10 元”理解为“不超过 10 元”；也可能订单抽取正确，但用户改口后仍沿用旧确认。只统计意图标签，无法发现这些差异。

按业务决策检查对象、条件、否定、缺参和多轮替换，再验收实际进入的流程及副作用。对条件边界准备刚好等于阈值、值未知和报价变化的用例；对多目标请求分别检查完成与未完成部分。误进入执行路径与多问一次问题应分开统计，不能用平均准确率抹平代价。

阈值调整后同时观察误执行和不必要回退。如果高准确率来自拒绝大量正常请求，应把覆盖率与人工接管成本一起报告。
