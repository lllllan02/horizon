**用大语言模型（LLM）做意图识别，就是提供任务类别、判断示例和用户输入，让模型返回任务标签及参数。** 可以直接使用预训练模型，业务类别的含义仍需开发者定义。

## 整套方法怎样工作？

用户表达与必要上下文 → 模型生成任务对象 → 程序校验结果 → 选择业务流程

例如「查一下订单 B 能不能退，先别提交」，模型应判断为查询资格，并提取订单 B。它还没有查询订单数据，也没有执行退款。

如果已有少量[[tool-calling|工具]]，也可让模型直接提出工具调用；业务流程较多时，先单独分类便于评测与排查。[[langgraph-intent-routing|结构化分类与固定路由]]体现了这种分工，是否增加一次分类调用要比较收益、耗时和成本。

## 要告诉模型什么？

先按业务动作区分类别，而不是统一使用 `refund`：查询规则、查询资格和申请退款分别对应不同流程；再提供动作不明的 `unclear` 与超出能力的 `unsupported` 出口。

提示还要给出边界例子：「能不能退」是查询，「先别退」不能当作提交要求，情绪不代表授权。缺订单号时保留明确的任务，询问缺少的参数，不猜测对象。[[anthropic-intent-routing|Anthropic 的分类资料]]说明了类别、示例与输出约束怎样配合。

用户原话是待识别的数据；其中要求修改分类规则的内容不能替代系统定义。

## 输出怎样交给程序？

上述订单请求的期望结果可以是：

```json
{"intent":"refund_eligibility","order_id":"B","question":null}
```

`intent` 是任务标签，`order_id` 是订单号，`question` 是需要追问的问题；`null` 表示没有值。用 JSON Schema 这类结构约束声明允许的标签、字段类型及必填项，可以减少格式错误。

这三个字段及下述代码示例仅支持单任务；无法表达多目标或条件执行时应返回限制，不能丢掉「免费才退」等约束。扩展契约所需的目标、对象与条件绑定，见本篇最后一节；它不是现有示例已经具备的能力。

**「结构合法不等于语义正确。」** 模型仍可能选错任务或抄错订单号。程序先检查请求是否正常完成、结果是否可解析，再校验字段；缺参就补参，意图不明就[[intent-clarification|澄清]]，通过后才映射到业务函数。订单归属、退款资格和操作权限由业务系统校验。

## 怎样接入和验证？

[[assets/intent-llm-demo.py|完整 SDK 示例]]使用 Anthropic 官方 Python SDK，避免手写请求协议。需 Python 3.11+，安装 `anthropic pydantic`，设置 `ANTHROPIC_API_KEY` 与账号可用、支持结构化输出的 `ANTHROPIC_MODEL`，再运行 `python content/assets/intent-llm-demo.py`；会发起付费请求。Go 服务可调用封装后的识别接口，处理上述任务对象。

原示例在 Python 3.14.2、anthropic 1.13.0、Pydantic 2.14.1 下用模拟 HTTP 响应验证过结构发送与解析，以及拒绝、截断、非法标签的失败分支；未真实调用模型，不能据此确认分类质量或服务兼容性。

服务设置总时限和有限重试，失败时报告识别故障，不能当作业务不支持，也不能随识别重试重复退款。分类接口只做识别，业务执行另行控制。

按[[intent-evaluation|回归评测]]比较正确率、延迟和成本，并记录模型、提示及结构版本。类别多时可先筛选业务域，但上层分错会排除正确类别；重复请求若使用缓存，也须考虑对话状态、租户能力与版本，不能只按原句复用结果。

## JSON 正确，业务解释仍可能在哪里出错？

「费用低于 10 元才退」可能被输出成「允许支付 10 元」，字段类型全部合法，但边界条件已经改变。多个订单和多个动作也不能靠增加一个通用备注字段可靠承接，因为下游程序不知道备注必须约束哪一步。

输出契约应区分目标、对象、条件、明确禁止的动作和未解决歧义，并让条件绑定具体操作。可执行条件使用服务端能校验的表示，例如费用币种、比较关系和阈值；不能表达的条件保留原话并停止相关执行。程序验证结构和业务边界，抽取是否忠实仍需用原话对照及代表性用例评测，不能靠 Schema 自动证明。

同一模型既识别又执行时，也要在动作入口落实这些条件。否则模型前一轮正确提取「先别提交」，下一轮仍可能调用提交工具。识别结果应成为后续校验的输入，而不只是聊天里的一段文字。
