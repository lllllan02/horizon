**企业值得自建 Agent 的前提，是通用 Agent 加 MCP 无法满足关键业务要求，或专用实现能带来经验证、足以覆盖维护投入的收益。** 差异若只是企业知识、业务接口和操作方法，通常先补服务与配置。

## MCP 的边界在哪里？

按 [[mcp-architecture-summary|MCP 的职责划分]]，Server 提供工具、资料和提示模板，宿主应用（Host）组织模型与上下文。企业可以把检索、计算、审批、业务流程，甚至完整 Agent 放到 Server 背后。

**「Server 能控制自身返回什么、执行什么；接入 MCP 不会自动取得对宿主全部行为的控制权。」**

![[assets/enterprise-agent-architecture-gaps.png|通用 Agent 加 MCP 的整体架构，橙色标出目标宿主未提供或未开放的控制]]

因此，MCP 未规定某项能力，不代表 Server 实现不了。[[mcp-specification-summary#可选扩展已经覆盖哪些需求|Tasks 和 MCP Apps]]也已覆盖长任务交互与嵌入界面，实际边界要对照目标宿主的支持程度判断。若 Server 内部已经运行自己的 Agent，企业仍须承担其运行与维护成本。

## 哪些缺口值得自己掌控？

以下要求在现成宿主无法满足时，才构成自建理由：

| 业务要求 | 仅提供 MCP 服务仍缺什么 | 应掌控的范围 |
| --- | --- | --- |
| 事件触发后持续处理，等待后自动接续 | 整项任务的调度、状态与恢复 | 任务服务或业务编排 |
| 所有路径必须核对证据、授权和审批 | 跨工具约束及最终输出的检查关口 | 应用与执行控制 |
| 质量依赖特定资料组合、复核与停止条件 | 每轮上下文和决策过程的控制 | 专用运行系统 |
| 操作必须融入工单页或客户产品 | 所需的入口、交互和交付方式 | 企业应用 |
| 数据要求覆盖推理、会话与日志 | Server 返回数据后的处理边界 | 部署与数据管理 |
| 必须管理版本、完整轨迹和单任务成本 | 工具调用之外的观测与运行控制 | 运行管理及必要的定制 |

这些要求并不都需要重写 Agent。固定步骤可用[[agent-vs-workflow|工作流]]，审批和防重复可先在业务服务落实；自己的界面可以复用托管能力。只有缺口落在模型输入、循环、验证或停止策略上，才需要定制 [[agent-harness|Agent Harness（运行系统）]]。

内部知识多、系统多或流程复杂，本身都不足以证明需要自建。内网 Server 返回的数据仍可能进入外部模型，自建应用也不会自动改变这一点；同样，调用量大不保证自建更便宜。

## 怎样判断投入是否值得？

先用真实任务建立「通用 Agent 加 MCP」基线，定位失败来自数据、工具、配置还是宿主，再只接管缺口所在部分。通过 [[agent-evaluation|Agent 评测]]比较任务成功、违规动作、人工返工、耗时与总成本，并计入持续研发、运维和升级适配。

建设范围应以满足要求为限：补业务能力、建设 Agent 应用与定制运行系统，承担的责任不同。上述场景是判断依据，具体产品能力与收益仍需实测。
