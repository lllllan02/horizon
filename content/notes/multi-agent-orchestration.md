多个 Agent 共同完成任务时，需要决定任务怎样拆分、成员怎样衔接，以及信息和结果怎样传回并影响下一步。**编排（Orchestration）是组织多个 Agent 执行、信息流转与控制流程的方式。** 合适的模式让各个局部成果接回共同目标；是否值得增加成员，仍取决于[[multi-agent-benefits|分工收益与协调成本]]。

编排可采用「**模型驱动**」（根据进展决定流程）、「**程序驱动**」（预先规定流程），也可「**两者组合**」。下面的模式可以嵌套组合，并非一套互斥、穷尽的分类。

## 任务怎样按步骤和分支推进

[[multi-agent-flow-patterns|流程模式]]首先解决任务之间的依赖和分发问题：顺序流水线规定「谁依赖谁」，并行分发与汇合规定「哪些工作同时进行、结果怎样综合」，路由规定「选哪些处理路径」。三者可以组合；节点由多个 Agent 分别承担时，才属于多 Agent 编排。

## 成员怎样分工和接续处理

当下一步需要结合进展判断，或需要让成员利用彼此的发现时，[[multi-agent-orchestration-sources|协作与控制模式]]进一步约定谁持续负责、谁接手，以及谁可以参与讨论：

| 模式 | 怎样运行 | 适用条件与主要代价 |
| --- | --- | --- |
| **主管与执行者（Supervisor / Manager）** | 主管分配子任务、收取成果，再决定补查或汇总 | 需要统一约束和综合判断；依赖主管的分解与核验能力 |
| **层级任务分解（Hierarchical Task Decomposition）** | 上层委派给中层，中层继续分派，成果逐层返回 | 复杂任务需要分层拆解；层级增加也会带来信息压缩与协调成本 |
| **控制权交接（Handoff）** | A 将后续处理交给 B，B 接续这一阶段的任务或直接回答用户 | 需要切换到合适的专业角色；须防止来回转交而无人完成任务 |
| **群组对话（Group Chat）** | 多个成员在共享会话中轮流贡献，读取并回应已有讨论 | 需要多轮讨论或共同修订；须选择发言者、控制上下文和结束条件 |

路由通常负责一次分类分发，主管则结合中间成果持续决定下一步。主管可以通过「**Agent 作为工具（Agents as Tools）**」调用专家：专家返回子任务成果，主管保留整体责任；Handoff 则转移后续处理权。[[langchain-multi-agent|LangChain 的 Supervisor]]和 OpenAI 的 Manager 对应这类集中协调角色。任务委派（Task Delegation）是交出工作的宽泛说法，也可能用于描述交接，不能只凭这个词推定控制流。

**动态任务分解（Orchestrator–Workers）强调根据具体输入临时形成子任务，再分发和综合。** 它区别于预先写好固定并行分支，也比泛称「主管」更具体。[[multi-agent-orchestration-sources#Google ADK：分派、分解与反馈|层级分解]]可以继续嵌套这种分工；父／子 Agent 描述相对创建或嵌套关系，不代表模型能力等级。

## 信息与成果怎样传递

**持续协作需要信息回流：分派时传入任务与约束，执行后返回成果、状态和缺口，再据此决定下一步。** 只指定「谁负责」还不够；接收者缺少必要条件会误解任务，协调者拿不到结果与失败原因，也无法判断该汇总、补查还是改派。

### 传入任务与上下文

传入[[agent-context-input|上下文]]时，应围绕当前子任务提供目标、约束、已有结论和必要证据，并说明预期输出。完整聊天历史和中间搜索过程不会因成员同级或共享主管就自动传递；只传摘要时，也要保留影响判断的条件与不确定项。

常用传递方式包括「**调用参数与返回值**」「**成员间消息**」和「**共享状态或记录**」。子任务调用通过参数和返回值交换信息；成员直连需要可用的消息通道；共享状态则要约定谁读取和更新哪些字段。共享工作区也不表示各成员已读到同一份最新信息。成员是独立 Agent 服务时，可用 [[a2a|A2A]] 规范消息、任务状态与成果交互。

### 返回成果与执行状态

每个分支应返回「**结论、依据、适用条件与未完成部分**」，让接收方核对结果是否回答了原问题。分支还应区分已完成、失败或需要补充信息；后台执行时，启动成功不能代替结果完成，须继续跟进状态并回收成果。

分支失败时，返回原因和已有成果，由负责人决定重试、改派或保留缺口；依赖该结果的步骤不能假定成功。并行成果冲突时，先核对版本、条件与出处，再定向补查，不能仅按多数意见决定事实。

审查意见也是交付物，应说明「**问题位置、判断依据与影响**」，让[[multi-agent-study-sources#Cognition：单一写入者与独立判断|负责人判断是否采纳]]。意见中应区分已核实的问题和仍需验证的疑点，避免接收者把建议直接当成已证实的结论。这些成果与反馈构成后续评价、修订和重新分工的输入。

## 反馈怎样决定继续与结束

**评估与改进（Evaluator–Optimizer）是根据评价反馈反复修订结果的循环。** 生成者先产出，评价者按明确标准检查；未通过则将具体问题返回生成者，修订后再评。满足标准时结束，达到预算或次数上限仍未通过时保留缺口。[[anthropic-effective-agents-summary#什么时候适合评估后再改进？|评价标准可操作、反馈确实能指导改进]]，才有引入循环的价值；只评审一次属于顺序流程。

需要人补充信息、确认判断或批准操作时，还可加入「**人工介入（Human-in-the-loop）**」：流程在指定节点暂停，取得输入后继续。这是可嵌入上述模式的交互环节，不要求额外设置一个 Agent。

## 有无主管怎样影响组织结构

**观察组织结构时，要区分谁持续协调、成员能否直连，以及委派是否存在多层。** 集中协调主要经主管交换信息，可以是一层主管，也可以逐层委派；对等协作允许成员直接交换发现；混合结构保留主管，同时开放成员之间的交流。没有持续主管时，也可以让分支独立完成，只在末尾汇总；有最终汇总点，不等于有动态分工的主管。[[multi-agent-study-sources#Google：协作效果取决于任务和开销|架构对照研究]]比较了主管与成员直连的不同组合，并未穷尽全部编排方式。

群组对话也可以由协调者统一选择发言者，因此不能直接归为「无主管」。多层主管、并行分支和交接同样可以共存：例如主管动态拆分调查，研究者并行推进，作者汇总后交给评价者，未通过再修订。这是模式组合的示意。
