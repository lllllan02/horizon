多个 Agent 共同完成任务时，需要决定任务怎样拆分、成员怎样衔接，以及信息和结果怎样传回并影响下一步。**编排（Orchestration）是组织多个 Agent 执行、信息流转与控制流程的方式。** 合适的模式让各个局部成果接回共同目标；是否值得增加成员，仍取决于[[multi-agent-benefits|分工收益与协调成本]]。

编排可采用「**模型驱动**」（根据进展决定流程）、「**程序驱动**」（预先规定流程），也可「**两者组合**」。下面的模式可以嵌套组合，并非一套互斥、穷尽的分类。

**同一套编排可以从任务推进、成员关系与信息流转三个维度理解；相似的箭头可以表达不同含义。**

| 观察维度 | 关心的问题 |
| --- | --- |
| 流程模式 | 任务怎样按依赖、分支与汇合推进？ |
| 协作与控制模式 | 成员怎样分工，谁持续负责，谁接手后续处理？ |
| 信息与成果传递 | 交换哪些内容、怎样送达，接收方实际读到什么？ |

例如，`A → B` 在顺序流水线中表示 B 使用 A 的成果执行下一步，在交接中表示 B 接手后续处理。主管也可以先调用 A，再把 A 的成果交给 B，形成顺序流程，同时保留整体控制权。**执行顺序相似，不代表控制权关系相同；同一实现需要从这些维度分别描述。**

## 任务怎样按步骤和分支推进

[[multi-agent-flow-patterns|流程模式]]首先解决任务之间的依赖和分发问题：顺序流水线规定「谁依赖谁」，并行分发与汇合规定「哪些工作同时进行、结果怎样综合」，路由规定「选哪些处理路径」。三者可以组合；节点由多个 Agent 分别承担时，才属于多 Agent 编排。

## 成员怎样分工和接续处理

[[multi-agent-collaboration-patterns|协作与控制模式]]约定谁持续负责、谁接手，以及谁参与讨论：主管分配任务并收取成果，也可通过多层嵌套形成层级分解；交接让另一成员接续处理，群组对话让成员共同讨论。把子 Agent 当工具调用属于主管模式，成果返回后仍由主管继续决策。

## 信息与成果怎样传递

[[multi-agent-communication|信息与成果传递]]比较调用与返回、消息传递、共享状态，并分别展开消息收发与共享记录更新。交付的数据还须进入接收成员的模型输入；数据送达、任务完成和成果验收需要分别判断。

## 反馈怎样决定继续与结束

**评估与改进（Evaluator–Optimizer）是根据评价反馈反复修订结果的循环。** 生成者先产出，评价者按明确标准检查；未通过则将具体问题返回生成者，修订后再评。满足标准时结束，达到预算或次数上限仍未通过时保留缺口。[[anthropic-effective-agents-summary#什么时候适合评估后再改进？|评价标准可操作、反馈确实能指导改进]]，才有引入循环的价值；只评审一次属于顺序流程。

需要人补充信息、确认判断或批准操作时，还可加入「**人工介入（Human-in-the-loop）**」：流程在指定节点暂停，取得输入后继续。这是可嵌入上述模式的交互环节，不要求额外设置一个 Agent。

## 有无主管怎样影响组织结构

**观察组织结构时，要区分谁持续协调、成员能否直连，以及委派是否存在多层。** 集中协调主要经主管交换信息，可以是一层主管，也可以逐层委派；对等协作允许成员直接交换发现；混合结构保留主管，同时开放成员之间的交流。没有持续主管时，也可以让分支独立完成，只在末尾汇总；有最终汇总点，不等于有动态分工的主管。[[multi-agent-study-sources#Google：协作效果取决于任务和开销|架构对照研究]]比较了主管与成员直连的不同组合，并未穷尽全部编排方式。

群组对话也可以由协调者统一选择发言者，因此不能直接归为「无主管」。多层主管、并行分支和交接同样可以共存：例如主管动态拆分调查，研究者并行推进，作者汇总后交给评价者，未通过再修订。这是模式组合的示意。
