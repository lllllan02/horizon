## 什么是意图识别？

**Agent 意图识别（Intent Recognition）是结合用户表达与上下文，判断用户要做什么，并提取对象、参数和约束的过程。**

例如「订单 A 能退吗」表示查询退款资格，对象是订单 A；「免费才退」还包含费用条件。多个对象或目标需要分别保留，避免漏掉任务或用错条件。

## 什么时候需要单独做意图识别？

意图识别帮助系统根据用户要求选择处理方式，判断的对象随系统结构变化：

![[assets/agent-intent-levels.png|同一订单查询在单 Agent、多 Agent 与混合系统中的判断位置]]

- 单个 Agent、少量工具：模型在[[tool-calling|工具调用]]中判断该用哪个工具、传什么参数，已经完成了最基本的意图识别，通常无需额外分类。
- 多个 Agent：入口根据任务选择由哪个 Agent 处理，例如把订单问题交给订单 Agent，把技术问题交给技术支持 Agent。
- Agent 与接口、服务并存：入口判断请求应交给 Agent、进入固定业务流程，还是直接调用服务；多个目标也可能涉及多条处理链路。

单独设置识别环节，是为了提前分流：能直接查接口的请求可以直接处理，需要推理或多步操作的请求再交给 Agent，减少无效调用和错误分派。若现有 Agent 已能可靠选择工具，通常无需重复分类；按钮或上游已指定动作时，可以直接校验并执行。是否单独设置，取决于提前分流的收益，不能只看 Agent 或工具数量。

## 怎么做？

先按后续处理的差异定义任务类别，再选择识别方式：

| 方式 | 做法 | 适用场景与代价 |
| --- | --- | --- |
| [[intent-rules\|规则]] | 人工编写关键词、句式或正则匹配条件 | 固定命令、少量句式；自由表达容易漏判或误判 |
| [[intent-text-classifier\|本地模型（文本分类器）]] | 用「用户表达＋正确类别」样本训练，预测新请求的类别 | 类别稳定、已有样本；需维护数据与模型 |
| [[intent-llm\|大模型]] | 提供类别说明、示例和上下文，让模型输出任务、参数与约束 | 样本少或表达复杂；需控制延迟、成本与误判 |

识别后，程序校验结果并进入对应流程；涉及前文对象时维护[[intent-dialogue-state|多轮状态]]，目标不明或缺参时[[intent-clarification|澄清与回退]]。识别到操作意图后，仍须校验权限、业务条件和执行约束；用[[intent-evaluation|评测]]检查是否理解正确并进入正确流程。

## 需要把三种方式串成漏斗吗？

「规则 → 本地分类模型 → 大模型」是按成本逐级升级的可选方案：规则处理明确命令，未命中或有歧义时交给分类器；分类器分数不足或候选接近时，再交给大模型。大模型仍可能需要追问，不能保证所有请求都能判断。

![[assets/agent-intent-funnel.png|三级漏斗的升级条件、直接分流出口与前层误判边界]]

这种组合适合流量大、类别稳定、简单请求可直接处理或分流的入口。前两层能让足够多请求绕过大模型，才可能抵消规则、数据与模型的维护成本。「规则承接大部分流量」必须由真实请求验证，不能作为默认前提。

对最终仍要调用同一个大模型的 Agent 服务，前置分类往往增加步骤。只有它能减少后续上下文、调用次数或错误分派时，才有增加的理由；少量工具可由模型直接选择。设计应[[anthropic-effective-agents-summary#什么时候值得增加复杂度？|从简单方案开始，用评测确认增加复杂度的收益]]，无需默认凑齐三层。

后层只会收到升级的请求，前层误判并放行后，大模型没有纠正机会；分类器也可能高分错判。因此要比较整条链路的任务成功率、总成本和延迟，不能只看拦截了多少流量。
