**选型是在隔离边界、环境可复现性和维护成本之间取舍。** 先明确需要防止哪些访问、是否要防内核漏洞逃逸，再比较依赖、兼容性和交付方式。

## 方案与用法

| 方案 | 主要收益 | 需要承担的代价或边界 |
| --- | --- | --- |
| [[srt-sandbox-practice\|SRT]] | **沿用本机工具**，给原命令加文件与网络限制，减少环境准备 | **依赖本机环境、共享宿主内核**；资源额度另行配置，跨系统规则需核对。 |
| [[bubblewrap-sandbox-practice\|bubblewrap]] | **自行组装 Linux 隔离**，精细组织可见目录、进程与网络视图 | **隔离规则与运行环境需自行维护**：包括依赖挂载、网络策略、限额与回收；仍共享内核。 |
| [[docker-sandbox-practice\|普通 Docker 容器]] | **镜像打包、环境复现**，容器便于重复创建、配置额度与销毁 | 要维护镜像、容器运行环境和权限策略；**仍共享宿主内核**，不能仅靠容器名称推断隔离充分。 |
| [[gvisor-sandbox-practice\|gVisor／runsc]] | **容器接入「替身内核」**，保留容器工作流，减少对宿主内核的直接暴露 | 需要运行时支持；**兼容性与性能有取舍**，部分系统功能不兼容，系统调用与文件 I/O 密集任务需验证性能。 |
| [[firecracker-sandbox-practice\|Firecracker]] | **自建轻量虚拟机**，每个 microVM 有独立客户内核，与宿主内核分开 | 需要 Linux／KVM；**运维工作更多**，需自行管理客户内核、磁盘镜像、网络、任务通信和回收。 |
| [[docker-sandboxes-practice\|Docker Sandboxes]] | **现成的 Agent 沙箱产品**，整合 microVM、Agent 启动与网络／凭据代理 | **受产品支持范围约束**，包括平台、Agent 与配置接口；需确认能否接入自己的工作流。 |
| [[e2b-sandbox-practice\|E2B]] | **远程虚拟环境**，通过 SDK 管理托管的 microVM，减少底层基础设施运维 | **代码与数据进入远程平台**；还需承担**传输延迟、费用与平台依赖**，受平台额度约束，仍需管理任务策略。 |

## 具体场景怎么选

以下是满足所列条件时的选择起点，仍需配置权限并验证任务。

| 场景 | 建议与原因 | 何时重新评估 |
| --- | --- | --- |
| Agent 在自己的项目中调用本机 Python、Git，主要防止误改其他目录和随意联网 | **SRT**：包装原命令，沿用现有工具，不必先制作镜像。 | 开始自动执行来源不明的代码，需要额外的内核隔离时，评估 gVisor 或虚拟机。 |
| 服务反复执行自己维护的固定脚本，每次需要相同依赖、独立临时目录 | **普通 Docker**：镜像固定依赖，容器便于创建与回收。 | 允许用户提交代码或 Agent 自由生成并执行代码时，重新评估隔离边界。 |
| 已有 Docker 执行环境，要运行用户提交的代码，并保护共享执行机器 | **Docker + gVisor**：保留镜像与容器管理，增加应用内核隔离；先验证兼容性和性能。 | 所需功能不兼容，或明确要求独立客户内核时，评估虚拟机方案。 |
| 要给 Agent 提供远程代码执行，但不准备维护执行机器，代码与数据允许交给平台 | **E2B**：通过 SDK 创建环境、上传代码、执行并回收。 | 数据必须留在自有环境，或平台费用、延迟、额度不能接受时，考虑自建。 |
| 要自建大量独立内核的任务环境，已有 Linux／KVM 运维能力 | **Firecracker**：用 microVM 承载任务，自己控制镜像与基础设施。 | 不具备镜像、网络和实例调度能力时，先考虑成熟的虚拟机平台或托管服务。 |
| 想直接启动产品支持的编码 Agent，并使用配套的网络与凭据管理 | **Docker Sandboxes**：使用集成产品，减少自行拼装。 | 自写 Agent 或执行服务所需接口不受支持时，选择可自行接入的运行时或 SDK。 |

**Docker + gVisor 仍然要创建容器、配置挂载与网络。** gVisor 替换的是容器运行时，不替代环境管理；是否添加它，取决于额外隔离收益是否值得兼容性与性能代价。

## 怎样从比较得到选择

- **先看隔离边界。** 系统访问限制回答「允许做什么」；gVisor、microVM 进一步减少程序直接攻击宿主内核的机会。风险涉及恶意代码逃逸时，这一层应优先评估；额外隔离也不能补救主动暴露的秘密文件或权限。
- **再看环境与兼容性。** 必须复用本机工具时，命令包装方式更直接；需要固定依赖、重复创建时，镜像更便于交付。增加应用内核或虚拟机后，还要验证实际程序、设备和负载是否适配。
- **最后看接入与维护。** 自行组装换来控制权，也要负责策略、额度和清理；产品封装减少搭建，但要求接口与工作流匹配；远程托管进一步减少运维，前提是能接受数据位置、延迟与持续费用。

这些维度可以组合：Docker 可选择 gVisor 运行时，容器也可运行在虚拟机中。[[worktree-sandbox-usage|Git Worktree]]只分开工作副本，不能代替执行隔离。各方案仍需核对[[sandbox-filesystem|文件]]、[[sandbox-network|网络]]和[[sandbox-resources|资源边界]]。

上述为机制与产品形态的取舍分析，不是性能实测。各方案卡片提供用法与来源，组合案例见[[sandbox-projects|项目方案对照]]。[SRT](https://github.com/anthropics/sandbox-runtime#usage)、[gVisor 生产建议](https://gvisor.dev/docs/user_guide/production/)、[Firecracker 架构](https://github.com/firecracker-microvm/firecracker)。

## 后续学习

Linux 机制暂不展开，后续按这些问题补充：

- Namespace 与挂载：为什么同机进程能看到不同目录、网络和进程列表？只读与不可见有什么区别？
- cgroup 与 systemd：怎样给整组进程限制 CPU、内存和数量，并统一回收？
- 权限与 seccomp：文件可见后谁决定能否读写？怎样限制程序可发起的系统调用？
- 网络命名空间、防火墙与代理：怎样组合，才能既按域名放行又防止绕过？
- KVM 与客户内核：microVM 与共享内核的容器，边界到底差在哪里？

## 更强的隔离方案，一定更适合当前服务吗？

同一任务在不同后端可能遇到内核能力、网络、文件挂载或依赖兼容问题。只按隔离机制排名，容易选出安全边界看起来强、却需要长期绕开限制才能工作的方案。

先列可信边界：运行谁提供的代码、能接触哪些数据、是否跨租户、是否需要宿主能力。再用代表性任务验证启动、执行、取消、产物导出和清理，比较兼容性、延迟、运维与故障恢复成本。不能把一个正常命令跑通外推为全部工具链兼容。

方案可按任务等级组合，但切换条件应明确。要求隔离的任务在后端不可用时进入等待或失败，不应自动退化为直接在宿主执行；否则高强度方案的名义选择并没有形成稳定边界。
