**穿透、击穿、雪崩的共同结果是大量请求绕过缓存打到后端，但触发原因不同，要分别处理：不存在的数据、单个热点、大面积失效。**

| 问题 | 触发条件 | 主要措施 |
| --- | --- | --- |
| 穿透 | 反复查询不存在的数据 | 参数与权限校验、短时空值缓存、[[bloom-filter\|布隆过滤器]] |
| 击穿 | 热点 key 到期或未加载 | [[victoriametrics-singleflight-summary\|请求合并]]、受控重建、允许时用旧值 |
| 雪崩 | 大量 key 同时失效，或缓存整体不可用 | TTL 抖动、分批预热、后端限流与降级 |

几个容易踩的边界：

- 布隆过滤器可能误判「存在」，所以「可能存在」仍要查后端；它不会把已加入集合的元素判为不存在，但新数据没及时加入会错误拦截——不能只引用算法性质、忽略维护过程。
- 热点重建可以让同一 key 只有一个请求回源、其余等待有限时间或读旧值；但锁等待必须有上限、重建失败要退避，否则锁超时后会出现新一轮同时回源。
- 逻辑过期能保留旧值、由受控任务异步刷新，但把等待变成了陈旧数据风险：要定义最长可接受陈旧时间、刷新失败怎么办、首次没有旧值时怎么回源。
- 缓存整体故障时不能把全部流量转给数据库，应据后端容量 [[rate-limiting|限流]] 并 [[circuit-breaker-fallback|降级]]，优先保关键业务；降级数据的有效期和误差要明确，不能拿旧库存成交。
- **恢复阶段同样要控制预热速度**：一次性加载所有 key 会让数据库、网络和 Redis 同时承压，在刚恢复时制造第二轮故障。

诊断时看 key 是否实际存在、是否集中在一个热点、缓存服务是否整体异常；故障持续多久不是分类依据。
