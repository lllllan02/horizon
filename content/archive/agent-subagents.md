**子 Agent 是由调用方委派子任务、运行自身模型与工具循环，并向调用方交付结果的 Agent。** 主 Agent 通常保留整体目标与汇总责任；「子」描述的是委派关系，不要求不同模型、独立机器或新进程。

当排查日志会产生大量中间输出时，主 Agent 可以把「定位异常的时间与证据」交给子 Agent。日志和试探留在子上下文，主 Agent 收回结论、证据位置与不确定项。这样减少主上下文负担，也可能损失摘要未保留的细节。

## 创建子 Agent 实际创建了什么？

应区分**「能力定义」**与**「执行实例」**。定义说明名称、适用任务、提示词、模型、工具与权限；执行实例包含这一次的任务输入、消息历史、运行状态与结果。预先注册专家后可以多次启动，不必每次生成一套新角色。

典型链路是：主模型提出委派 → Harness 校验目标和权限 → 组装子上下文并启动实例 → 子 Agent 运行工具循环 → 返回或保存产物 → 主 Agent 核对并继续。

模型可以判断何时委派、怎样拆分；[[agent-harness|Harness]]负责实际启动、调度、状态记录和资源限制。**「在提示词里说创建一个助手，不会自行产生执行实例。」**

[[langchain-multi-agent|LangChain 的工具包装方式]]让一个工具函数调用子 Agent 的运行入口，再将结果交回主 Agent。[[claude-code-agent-collaboration|Claude Code 的配置方式]]则由应用读取专门的 Agent 定义，并在需要时委派。两者封装不同，配置与运行的区分相同。

## 任务说明与上下文怎么传？

委派输入必须让子 Agent 无需猜测主对话意图。以下是假设的只读排障任务说明，不是某个 SDK 的字段格式：

| 输入部分 | 示例 |
| --- | --- |
| 目标与范围 | 检查指定时间段的数据库慢查询，仅判断它能否解释请求超时 |
| 已知信息 | 请求 ID、时间范围、日志位置与已确认的超时现象 |
| 权限与边界 | 只读日志；不修改配置，不启动压测；发现缺失信息就报告 |
| 输出要求 | 结论、对应日志位置、反例与未确定项 |
| 停止条件 | 检查完指定范围或触及预算后返回，不无限扩大调查 |

上下文可以从干净任务开始，也可以继承主历史或选取摘要。干净上下文节省输入、减少无关干扰，但容易缺少隐含条件；复制历史方便接续，也会复制噪声和先入判断。无论采用哪种方式，都应保留目标、约束、证据位置与影响结论的前置状态。

结果适合返回「结论＋证据引用＋完成状态＋限制」。详细日志或报告可存为产物，再交回可访问的引用；主 Agent 需要时读取原件。返回摘要只是压缩，不能等同于已经核实。

## 怎样运行、等待与收回结果？

同步委派时，调用方等待子任务返回；后台委派时，调用方拿到运行标识，可以推进不依赖该结果的工作，再查询、等待或接收完成事件。并行通常需要多个独立任务，后台机制本身不会消除数据依赖。

应用至少要能区分运行中、成功、失败与取消，并把结果关联到原任务。以下是运行层设计建议：保留已完成分支，只重试可安全重试的失败部分；主任务结束或取消时检查仍在运行的后代；对迟到结果按任务版本判断是否仍适用。

子 Agent 还可继续委派，形成层级树，但需要限制深度、并发、总预算和任务范围。不同产品的嵌套能力与默认限制会变化，不能把单一工具的限制当作概念定义。

## 隔离的到底是哪一层？

**「上下文隔离不等于文件、权限和副作用隔离。」** 两个 Agent 即使看不到彼此对话，也可能同时编辑同一个文件或操作同一个数据库。

因此，排障子任务可以共享只读资料；编辑任务应划定写入范围，或用独立工作区后由指定责任人整合。独立工作区仍不能隔离共同使用的远程服务。需要限制真实访问能力时，使用[[agent-guardrails|权限检查]]与[[agent-sandbox|执行环境隔离]]，不能只依赖角色提示。

是否共享[[agent-memory|记忆]]、子运行是否保留历史，也都是显式实现选择。「已经告诉主 Agent」不能推出子 Agent 已经知道，「子 Agent 同意」也不能推出用户已经批准。

## 什么时候换成其他方式？

需要把整段后续对话转给专家时，使用交接；只需装载专业知识与操作方法时，可用 [[agent-loading|Skill 按需加载]]；依赖固定步骤时，由工作流顺序调用更容易控制。

子 Agent 最适合有明确输入与交付物、内部过程可以独立推进的任务。工作短小、需要频繁追问或与主任务共享大量隐含信息时，启动与上下文交接的成本可能超过收益。

## 子任务交付了答案，主 Agent 怎样判断能不能用？

主 Agent 要求比较三个方案，子 Agent 只查了一个来源却给出确定结论；或者调查期间用户已经改变限制，子 Agent 仍按旧要求交付。主 Agent 不能只把自然语言答案拼起来。

委派时交代目标、范围、输入版本、可用权限和交付证据，返回时核对覆盖范围、依据与未解决问题。晚到结果先判断对当前要求是否适用；部分失败时保留有效部分，并说明缺口，不把缺席分支当作赞同。涉及修改时，最好让交付物可独立审阅，再统一验收。

子任务预算也属于主任务总预算。无限等待慢分支会拖垮整体响应，提前结束则需要取消和结果回收规则。分工是否值得，应看节省的关键路径时间是否超过上下文复制、协调与重复工作的成本。
