## 场景一：热点商品缓存失效

假设每秒 2 万次商品详情读，数据库只能额外承受 2 千次，展示允许 5 秒陈旧。

回答思路：识别是单 key 未命中还是 Redis 整体故障；前者用请求合并和受控刷新，后者按数据库预算限流，允许的读降级到旧值。成交库存继续走权威校验。不能把「加锁重建」当成所有场景下的完整方案。

追问：首次访问没有旧值怎么办？十台应用的本地 singleflight 能否全局只回源一次？刷新连续失败超过 5 秒后如何响应？验证时应观察最大回源并发、陈旧时长和数据库负载，而不只看缓存命中率。

## 场景二：成功扣减后客户端超时

假设 Redis 返回途中断网，调用方重试同一笔购买请求。

回答思路：将结果视为未知，用稳定请求 ID 查询或重复提交；去重检查、扣减和结果记录要在同一原子边界内。订单提交与 Redis 预占分别设计失败恢复，记录保留期覆盖重试窗口。

追问：去重 key 被淘汰后重试怎么办？切主丢了扣减或去重记录怎么办？验证要注入「执行后、回复前」断连，并核对业务账目；仅测试同时发十个请求不足以证明安全。

## 场景三：扩容后热点仍慢

假设三主 Cluster 扩成六主，某个排行榜占总请求的大部分。

回答思路：先检查槽与 key 流量分布，一个 ZSet 不会因节点增加自动拆开。读多可缓存查询结果或限范围，写多则评估按业务维度拆榜及聚合代价，同时观察迁移中的路由与尾延迟。

追问：怎样提供拆榜后的全局 Top N 和某用户精确排名？hash tag 是否反而把更多 key 聚集在同一槽？没有数据分布和一致性要求时，不应给出固定拆分数量。

## 场景四：任务执行后进程退出

假设优惠券已写入数据库，任务工作进程在确认完成前退出。

回答思路：允许任务再次领取，以业务唯一键在数据库中避免重复发券，并恢复结果。[[redis-go-projects|Asynq 项目]]可用于解释领取、租约、重试与完成状态的分工，但框架的去重选项不能替代外部业务幂等。

追问：毒任务不断失败怎样隔离？积压增长是消费者不足还是处理变慢？删除历史消息或清理任务状态会影响哪些恢复路径？验证要记录业务结果、重试次数和最老待处理时间。

这些验证是建议的观察方法，尚未执行实验；回答时应区分推演、源码阅读与自己的实测结果。
