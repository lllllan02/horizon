**故障切换要把服务职责交给可接替的节点，同时约束旧节点继续工作的能力。** 心跳超时只能说明当前观察者联系不到目标，**不能证明目标已经停止**。

- 流程通常是：通过多个观察或协议规则判断是否需要切换 → 选数据进度满足要求的候选者 → 建立新的任期或所有权 → 更新流量入口 → 检查客户端恢复。Redis 和 [[raft|Raft]] 的选取与提交规则不同，不能把所有自动切换当成同一种保证。
- **脑裂**：网络分区时，新旧两侧都自以为有权写入就可能脑裂。多数派能约束参与共识的成员，但旧客户端仍可能往数据库、文件或外部 API 写。需要 [[distributed-locks|fencing token 或资源侧校验]]让接收端拒绝过期持有者——只删注册信息不能让旧进程立刻消失。
- 切换前后的在途请求还可能处于「已执行但响应丢失」的状态，客户端重试要靠幂等键、状态查询或业务去重，不能把超时当未执行。数据复制延迟还可能让新主缺少已确认的写入，要在 [[high-availability|RPO 与恢复策略]] 里说清。

旧主恢复后要先验证身份、追赶数据，再决定是否切回，不能因为原机器上线就重新放开写入。一次演练要检查**数据、请求、流量**三个方面，而不只看主节点名字是否变了。
