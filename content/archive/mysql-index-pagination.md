**分页是按指定顺序，每次返回结果集一部分记录的查询方式。** 优化时要分清：哪些记录只为跳过而读取，哪些数据确实需要返回。

**偏移分页（Offset Pagination）是先跳过指定数量的结果，再返回一页数据的分页方式。** MySQL 用 `LIMIT 数量 OFFSET 偏移量` 表达。

## 开销在哪里

假设 MySQL 8.4、InnoDB 的 orders 有索引 `(user_id, created_at, id)`，id 唯一，created_at 非空。查询用户 7 的订单，按 created_at、id 排序，执行 `LIMIT 20 OFFSET 100000`：

- 大 OFFSET：即使索引提供顺序，通常仍要越过前十万条合格记录。B+ 树按键定位，没有为查询结果提供「第十万条」的直接地址；若还要读取索引外字段，被丢弃记录也可能产生回表成本。
- 额外排序：索引不能提供所需顺序时，还要读取候选并排序，返回二十条不代表只处理二十条。
- 大 LIMIT：一次确实要返回很多记录，读取、传输与应用处理的开销都随结果量增加。

## 对应的解决办法

先让索引尽量匹配过滤条件与[[mysql-index-ordering|排序顺序]]，再按需要减少的工作选择方案：

| 场景 | 解决办法 | 减少什么，仍有什么限制 |
| --- | --- | --- |
| 保留页码，完整行读取很贵 | [[mysql-deep-pagination#保留页码：延迟关联\|覆盖索引分页，再延迟关联]] | 只为当前页补齐字段，减少无用取行；仍需扫描 OFFSET |
| 连续翻下一页 | 游标分页：从上一页排序键之后读取 | 避免从头跳过历史结果；不能直接跳到任意页码 |
| 必须快速跳到任意深页 | [[mysql-deep-pagination#快速任意跳页：预计算位置\|预计算结果位置]] | 用序号范围定位；需提前构建，并维护结果版本 |
| 列表不需要展示那么多 | 限制页深、单页数量，或缩小筛选范围 | 减少请求的数据范围；会限制用户的浏览方式 |
| 确实需要大量数据，如导出 | [[mysql-batch-reading\|按键分批、流式读取]]，必要时后台执行 | 控制单批工作量与客户端内存；总读取、传输量仍在 |

这些方法可以组合：例如按键分批导出时，每批再流式写入文件；覆盖索引也可以用于游标分页。索引和分页写法的收益应通过实际访问量验证。

## 把位置换成键值边界

**游标分页（Cursor Pagination）是记录上一页的排序边界，再从边界后读取下一页的分页方式。** 这里的游标是应用保存的键值，不是数据库游标对象。

沿用前面的订单索引，假设上一页最后一条是 `created_at='2026-10-01 12:00:00', id=500`：

```sql
SELECT id, created_at FROM orders
WHERE user_id = 7
  AND (created_at > '2026-10-01 12:00:00'
       OR (created_at = '2026-10-01 12:00:00' AND id > 500))
ORDER BY created_at, id
LIMIT 20;
```

现在条件给出键值边界，可以从上一页之后定位。相同时间还需比较 id，否则会漏掉同一时间尚未返回的记录。用 EXPLAIN 核对是否形成预期范围，不能断言改写后一定只扫描二十条。

该示例依据[[mysql-manual-queries#分页与连接的工作量|范围定位与 LIMIT 规则]]推导，未实测。稳定排序不等于跨页快照：并发修改排序键仍可能造成重复或遗漏，跨批次一致性需另外约定。
