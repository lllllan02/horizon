**数据库选型先看数据怎么写入、查询和更新，再看一致性、容量与延迟要求。** 只按「结构化 / 非结构化」分类，判断不了事务、全文检索和大范围聚合的差别。

| 主要需求 | 适合评估的模型 | 代表与边界 |
| --- | --- | --- |
| 多实体约束、事务、关联查询 | [[relational-database\|关系模型]] | MySQL 等；需要索引与事务设计 |
| 按 key 低延迟访问 | 键值模型 | Redis；关注内存、持久化与热点 |
| 以完整对象读写嵌套结构 | 文档模型 | [[mongodb\|MongoDB]]；结构灵活仍需建模 |
| 文本相关性、多条件检索 | 倒排索引 | [[elasticsearch\|Elasticsearch]]；关注分析器与可见延迟 |
| 大量明细上的过滤与聚合 | 列式分析 | [[clickhouse\|ClickHouse]]；排序与扫描范围关键 |
| 带标签的指标时间序列 | 时序模型 | [[prometheus\|Prometheus]]；控制标签基数 |
| 向量近邻召回 | 向量索引 | RAG 检索；评估召回率、过滤与更新成本 |
| 多跳关系遍历 | 图模型 | 关系路径与访问模式决定收益 |
| 大对象与长期归档 | 对象存储 | 文件和归档，查询另靠元数据或计算层 |

例如订单交易用关系库维护状态与约束，搜索副本提供检索，分析库计算销量；这些副本可以由 [[cdc|CDC]] 派生，但要接受并管理传播延迟，不能让每个系统都变成同一业务事实的权威。

**先用已有系统验证查询与容量，再决定要不要引入新组件。** 新增一种存储，也会新增备份、恢复、监控、权限和跨系统一致性问题——功能匹配之外，这些成本同样影响选择。
