**评估记忆要观察一系列交互之后，后续任务是否更正确、更省成本，并且能及时接受纠正。** 数据库里有记录和检索命中，都不能单独证明效果。

## 最小回归怎样构造？

沿用同一个假设用户与项目，按顺序执行：

| 历史或状态变化 | 后续检查 | 常见故障 |
| --- | --- | --- |
| 会话 A 明确 demo 项目偏好 Go | 新会话写示例 | 未保存、未触发读取或漏注入 |
| 会话 B 明确改成 Python | 再开会话，不带旧聊天 | 仍使用旧事实、索引未更新 |
| 另一个项目没有设置 | 查询那个项目 | 把局部偏好推广为全局 |
| 信息已过期或用户已删除 | 查询并运行后台整合后再查询 | 缓存残留、从旧摘要重新生成 |
| 当前请求明确“这次用 Rust” | 生成本次示例 | 历史默认覆盖当前要求 |
| 问及从未提供的事实 | 给出答案或请求补充 | 模型臆造“记得”某事 |

前三类同时测写入与使用；不能只预填一组正确记忆，再声称验证了自动提取。

## 怎样定位问题在哪一段？

在 [[agent-trace|Trace]] 中关联来源消息、候选、写入结果、记忆 ID／版本、召回候选、最终注入项与回答。然后分层判断：

- 应记而未形成候选：提取范围或触发策略问题。
- 候选正确却未入库：校验、写入或后台任务问题。
- 已入库却未召回：查询、过滤或索引问题。
- 已召回却未注入：去重、预算或当前版本核对问题。
- 已注入却答错：表达不完整、冲突未澄清或模型使用问题。

日志记录以必要证据为限，避免为了调试另存一份不受删除控制的敏感记忆。

## 怎样比较方案？

[[locomo-memory|LoCoMo]]侧重长期对话中的事实、事件及时间联系；[[longmemeval-memory|LongMemEval 与 V2]]分别补充更新、拒答和环境经验。它们能扩充题型，自己的业务仍要测工具执行、删除、权限和故障恢复。

复测先固定数据文件、题型、评分脚本和阅读模型。同名基准可能采用不同子集或版本；F1、模型裁判和任务成功率也不是同一指标，不能把不同论文的最高分拼成产品排名。

固定初始记忆快照、历史输入、模型、任务及输入预算，至少比较无跨会话记忆、简单文件或档案基线、候选方案；历史能容纳时再加入完整历史输入，检查复杂记忆是否确有收益。额外加入「直接提供正确证据」帮助判断读取瓶颈。各组使用隔离存储，避免前一次测试写入影响下一次。

对[[agent-memory#写入|经验与技能复用]]，再区分同题重试和新任务迁移；对[[agent-memory-consolidation|记忆整合]]，检查省下的输入是否伴随条件遗漏。标准答案不能被写回供下一题使用，否则测到的可能是评测信息泄漏。

同时记录任务成功率、纠正后旧事实误用、信息不足时的拒答，以及写入／查询延迟、输入 Token 和模型调用成本。Token 变少但成功率下降不算单独成立的收益；后台成本也必须计入。本文给出评测设计，尚未进行产品间同条件跑分。

## 回答里出现了正确偏好，能证明记忆有效吗？

当前问题可能已经透露偏好，模型也可能凭常见模式猜对。需要构造必须依赖前序会话才能回答的任务，并加入无记忆对照，才能区分真实复用与猜测。

按时间组织事件：先提供事实，再更正、设置临时例外或删除，最后在新会话提问。检查应召回的内容，也检查不该再出现的内容；不同用户和项目使用相似表述，检验隔离。后台写入尚未完成时的结果，应与完成后的结果分开观察。

失败后沿提取、保存、检索、注入和使用逐段定位。模型没有使用正确记忆，不一定需要换向量库；提取已经写错，增加召回量也不会修复。记忆质量、延迟和维护成本要共同比较。
