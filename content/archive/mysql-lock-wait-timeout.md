**锁等待超时是请求等待其他事务释放锁，超过允许时限后报错的情况。** 它避免请求无限等待，但不会自动解决持锁方迟迟不结束的问题。以下以 MySQL 8.4 InnoDB 行锁为主，依据[[mysql-deadlock-reading#锁等待超时的时限与定位|官方参数与阻塞示例]]。

## 多久超时

行锁等待由 `innodb_lock_wait_timeout` 控制，默认 50 秒，实际以业务连接的会话值为准：

```sql
SELECT @@SESSION.innodb_lock_wait_timeout,
       @@GLOBAL.innodb_lock_wait_timeout;
```

它限制等行锁的时间，不是整个 SQL 或事务的总耗时。全局值修改后，已有连接的会话值不随之改变。元数据锁等其他等待要另查，例如 `lock_wait_timeout` 控制元数据锁等待。

## 先找到持锁方

先确认锁类型。对于 InnoDB 行锁，排查要回答「谁挡住了请求，它为什么这么久不释放锁」，可先查：

```sql
SELECT waiting_pid, waiting_query, blocking_pid, blocking_query
FROM sys.innodb_lock_waits;
```

如果阻塞者也在等别人，继续向前找；`blocking_query` 为空也可能仍有未提交事务。结合事务开始时间与应用日志追查持锁来源，尽量在等待发生时采集，超时后关系可能已消失。

如果等的是元数据锁，则改查 `sys.schema_table_lock_waits`，定位相应对象和阻塞连接。

## 为什么会一直等不到

例如 A 更新订单后一直没有提交，B 又更新同一订单，就要等 A。即使 A 的 UPDATE 早已执行完，A 的事务没结束，锁仍可能保留。B 等到时限会报错，A 不会因此自动回滚。

因此要查的是持锁生命周期：有没有漏提交、漏回滚，事务里有没有外部调用或耗时计算，批任务是不是太大，热点数据是不是被反复争抢。缺少合适索引还可能扩大扫描与加锁范围。

## 怎样修复

- 事务迟迟不结束：补齐提交／回滚路径，将不需要事务保护的工作移出去；批处理在业务允许部分提交时分批。
- 扫描和锁范围过大：检查执行计划与索引，缩小不必要的加锁范围。
- 热点竞争：按业务键限制并发、错开重叠批任务，评估排队的吞吐与延迟。
- 应急解除阻塞：保留现场后，按业务情况让持锁方结束事务；需要终止连接时，`KILL QUERY` 不等于结束事务，回滚清理也可能需要时间。

调大时限只允许多等一会儿，不会释放锁；调小可以更快失败，但仍需处理失败。超时[[mysql-deadlock-reading#官方规则：失败后还剩下什么|默认只回滚当前语句]]，如果决定整笔重试，应先回滚原事务，再按[[retry-decision|受控重试]]处理。修复后在相近负载下比较等待时间、超时比例与业务结果；上述查询未在实际实例执行。
