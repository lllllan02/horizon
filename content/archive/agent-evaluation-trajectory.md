**结果评测判断任务是否完成，轨迹评测检查关键行为与执行约束；两者结合才能区分「做成了」和「按要求做成了」。** 轨迹是可观察事件，不要求取得模型隐藏的思维过程。

## 为什么只看最终状态还不够？

订单 A 的退款账本正确，仍可能发生过先写入后确认、短暂误改 B 或重复提交后撤销。最终状态检查可能漏掉这些过程违规。相反，两条合法路径使用不同查询顺序，也不应仅因偏离参考解而失败。

[[bfcl-evaluation|BFCL V3]]以状态检查验收写操作，并用必要调用补充只读任务。自建系统可分三层核对：

| 层次 | 核对对象 | 能发现什么 |
| --- | --- | --- |
| 最终结果 | 文件、账本、服务状态、答案事实 | 未完成、错对象、产物错误 |
| 关键约束 | 写入前确认、调用参数来源、禁止动作 | 越权、无依据参数、错误先后关系 |
| 诊断信息 | 查询、模型轮次、重试、上下文变化 | 冗余、循环、信息丢失的候选原因 |

效率异常可以提示排查，但「调用多」不必然错误；为了恢复暂时故障，多一次查询可能是合理动作。

## 什么时候匹配工具路径？

[[agentevals-trajectory|AgentEvals]]提供严格、无序和部分匹配。协议要求完全固定时才严格比较；独立读取可忽略顺序；只需关键调用时用包含关系。安全约束往往需要更具体的事件判断，例如同一订单与操作版本的确认必须先于写入。

不能只查工具名集合。`refund(A)` 与 `refund(B)` 是不同效果，确认 A 也不能授权 B；模型提出调用、程序接受调用、工具实际完成又是三个状态。证据应来自真实执行边界，沿用[[agent-trace#关联并行、重试与恢复|Trace 的结构]]记录关联标识。

## 怎样从现象走到原因？

回答引用了 B 时，先沿输入、调用参数、工具返回、上下文变换、最终答复找首个偏离，再提出可检验假设。用固定输入的局部实验替换可疑环节，最后回到端到端任务验证。

例如，把错误摘要换成经人工核对的摘要后恢复正确，只支持「摘要可能是瓶颈」；它不直接证明某种新摘要策略在线上一定更好。诊断用的理想输入是上界对照，需要与实际可部署方案分开报告。

## 长任务与多 Agent 怎么测？

长任务应设置少量可验收的中间状态，并检查跨中断恢复、状态保留和最终一致性；不能把「完成计划中的步骤数」直接当作任务质量。记忆和压缩分别复用[[agent-memory#效果检查|记忆评测]]与[[context-compaction#效果判断|上下文压缩评测]]。

多 Agent 的团队结果仍按同一用户目标验收，再记录任务交接是否丢约束、共享状态是否冲突、是否重复执行副作用。比较单 Agent 与多 Agent 时计入所有成员的模型费用、并发资源和总墙钟时间。每个成员局部正确不保证整合后的结果正确；这些是从状态与交接边界推导出的评测设计，尚未在本专题运行多 Agent 实验。

## 轨迹里发现多余调用，是否就能认定它导致失败？

一次失败运行中多查了三次资料，可能是检索噪声导致，也可能是前面已经缺少关键证据，模型在尝试补救。时间上先出现或看起来异常，不足以证明因果。

先定位第一个偏离任务要求的可观测点，再用受控对照检验解释：给正确证据后是否恢复，固定工具输出后是否仍失败，禁用某项机制是否改变结果。每次尽量只改变一个关键因素，保留其他条件；无法复现时应将结论写成假设。

轨迹标准也不宜锁死唯一解法。只约束必要顺序和禁止行为，例如查询报价后才能按条件提交；允许其他合理路径。否则改进后的 Agent 可能因用了更短路线而被误判失败。
