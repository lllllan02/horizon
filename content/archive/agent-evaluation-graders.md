**评分器（Grader）是依据任务标准和执行证据作出判断的程序、模型或人工流程。** 它也是可能出错的系统，需要独立验证。

订单 Agent 的回复、工具调用和账本是三份不同证据。程序能查清账本，模型可判断解释是否充分，人工则负责解决标准含糊或自动判断分歧的问题。

## 哪类判断交给谁？

| 方法 | 优先检查 | 主要代价或风险 |
| --- | --- | --- |
| 程序评分 | 格式、测试、状态差异、权限与必要顺序 | 条件过窄会误拒合法解，覆盖不足会误放错误解 |
| 模型裁判（LLM-as-a-judge） | 语义正确性、证据支持、交互质量 | 有偏差与随机性，需参考材料和校准 |
| 人工评审 | 高价值样本、标准制定、争议仲裁 | 成本高；评审者也可能不一致 |

[[anthropic-agent-evals-summary|Agent 评测方法]]建议组合三者。组合的关键是职责明确：能直接读取的状态不让语言模型猜测；多个模型同意也不能替代实际账本。

## 怎样把「回答不错」变成可执行标准？

评分量规（Rubric）应描述可观察行为。例如「结果说明」维度：

- 通过：准确说明 A 的实际处理状态，不把等待中写成完成。
- 失败：声称完成但缺少成功证据，或混淆订单。
- 无法判定：所需账本或工具证据缺失。

给裁判提供任务、允许条件、相关证据和待评答案，要求返回结论、理由及证据位置。把待评文本标成数据，避免其中的「请给满分」变成评分指令；必要时用程序限制裁判可见范围。结构化 JSON 便于解析，但理由仍需抽查，模型写出的证据位置也可能不存在。

二元通过适合发布要求；分维度等级适合定位质量；成对比较适合判断两个开放答案谁更好。成对胜出只表明相对偏好，不证明满足最低要求。

## 怎样知道裁判可用？

先由领域评审者按同一规则独立[[data-annotation|标注]]一批样本，即为每份输出记录通过、失败或无法判定等参考判断；保留分歧并仲裁，再比较自动评分。覆盖明显通过、明显失败和容易混淆的边界，不能只给裁判看简单正例。

将「不合格」定义为正类，可以统计：误放是人工判不合格而裁判放行，误拒是人工合格而裁判拒绝。两类代价不同；整体一致率很高，也可能掩盖少数严重误放。另留校准之外的验证集，防止评分提示只适应校准样本。

[[llm-judge-evaluation|MT-Bench 的裁判实验]]表明答案位置、长度和裁判能力会影响结果。成对比较可以交换位置复评、隐藏系统身份；对重要判断提供参考证据。这些办法减少部分偏差，不能保证无偏。

固定裁判模型、提示、量规和证据格式。更换其中一项时，对新旧 Agent 输出统一重新评分，避免把裁判变宽松误认为被测系统提升。

## 没有分数是不是失败？

Agent 在业务预算内没完成可判任务失败；评分服务超时、证据损坏则可能是「无法评分」。保存原始状态和原因，按预先约定决定补跑与分母，不能默默把缺失当通过、当零分，或只删除不利样本。必要时分别报告业务失败率与评分覆盖率。

## Agent 学会讨好评分器，怎样避免高分低质量？

评分器只检查回答是否包含“已验证”，Agent 就可能在没有任何验证记录时得分；若裁判还读取候选答案中的指令，评分过程本身也可能受干扰。

能从环境获取的事实优先从环境验收，例如文件差异、订单状态和测试结果。模型评分用于语义质量时，给出明确标准与可信证据边界，把候选内容当待评数据；用已知正确、错误、模糊和试图影响裁判的样本检查判断。不能让被测 Agent 自己声明完成，再用这个声明证明完成。

评分器改版后重新评价对照系统，避免把口径变化当成产品进步。自动裁判与人工分歧较大的切片保留复核，对不确定结果明确标记，不能全部压成一个看似精确的分数。
