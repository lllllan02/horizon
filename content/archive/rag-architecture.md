**采用 RAG 的主要理由，是需要在回答时使用可更新、可定位的外部证据。** 是否需要自建索引，则取决于资料规模、查询方式与已有系统。小规模任务可直接提供全文，精确业务事实可直接查询数据库。

## 哪些方案可以替代，哪些可以组合？

| 方法 | 改变什么 | 适合解决的问题 | 主要代价与限制 |
| --- | --- | --- | --- |
| 提供全文或长上下文 | 每次给模型更多原始资料 | 文档已选定，内容量与预算可接受 | 输入开销高，放得下仍可能漏用证据 |
| RAG | 查询时选取外部证据 | 资料多、变化快、需要来源 | 检索可能漏掉关键条件，需维护索引 |
| 微调 | 改变模型参数中的行为模式 | 稳定格式、领域任务与行为适配 | 需训练和验证，不能代替实时事实查询 |
| SQL／业务 API | 按结构化条件读取或计算 | 库存、精确计数、交易状态 | 需要字段语义、权限与确定的查询约束 |

微调模型仍可使用 RAG，RAG 也可把 SQL 结果作为证据。只要问题要求“所有记录的总数”，就应考虑确定性聚合，不能把相似度 top-k 当作完整数据库扫描。以上是按处理对象归纳的工程选择，不是产品排行榜。

## 原始论文与应用管线有何不同？

[[rag-paper|RAG 原始论文]]联合训练检索与生成模型，并对检索文档的概率进行组合。常见应用则直接把外部证据放进模型请求；这属于检索增强的应用架构，不要求沿用论文训练方式。

[[langchain-rag-architectures|LangChain 的架构划分]]帮助区分控制权：固定管线由程序安排步骤，Agentic 由模型决定检索动作，混合流程在预设边界内允许改写或补查。关键词加向量的混合检索是另一维度，可以出现在以上任一架构中。

## 怎样选择起点？

已有文档搜索或业务 API 时，先复用查询能力，验证是否能得到可引用的证据。若主要失败是措辞不同，再比较语义检索；若缺的是跨多份资料的关联，再考虑更复杂编排。模型不会自动修复资料错误，增加模块应对应已观察到的失败原因。
