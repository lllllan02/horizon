**用 EXPLAIN 优化 SQL，要先还原取数与处理过程，再找出大量扫描、过晚过滤、重复访问或庞大中间结果，最后用实际执行验证改动。** 判断依据是完成业务所需结果付出了多少工作，以及时间主要花在哪里；某个字段的取值只能提供线索。

以下以 MySQL 8.4、InnoDB 的 SELECT 查询为范围。阅读顺序是「执行结构 → 访问范围与过滤 → 重复次数 → 排序等后续处理 → 实际行数与时间」，字段速查放在后面。

## 先保留查询条件，再取得计划

保留原 SQL、实际参数、表结构与索引，并明确业务需要多少行、哪些列和什么顺序。同一条 SQL 在普通参数和热点参数下可能处理完全不同的数据量；缺少这些条件，无法判断扫描量是否合理。

下面是命令模板，将 `SELECT ...` 换为原查询：

```sql
EXPLAIN FORMAT=TRADITIONAL SELECT ...;
EXPLAIN FORMAT=TREE SELECT ...;
EXPLAIN ANALYZE FORMAT=TREE SELECT ...;
```

前两条展示计划与估算：表格便于查字段，TREE 便于看连接算法及扫描、过滤、排序之间的数据流。第三条**「会实际执行查询」**，在可承受该查询开销的环境下使用，补充实际行数、循环和耗时。各格式与执行边界依据[[mysql-manual-queries#怎样知道优化器实际选了什么|官方计划说明]]。

## 沿数据流找多做的工作

先用 `id`、`select_type`、`table` 区分查询块、业务表和中间结果，再结合 TREE 确认谁给谁提供数据。表格的一行通常对应一次表访问，同一查询块可以有多行；`id` 不能直接当作执行顺序，也不能把 TREE 的缩进理解为每个节点只执行一次。

较合理的表现是：访问范围贴近业务所需数据，不必要的候选尽早被排除，后续连接与排序的输入得到控制，实际延迟与资源消耗满足目标。下面按排查顺序，把异常现象与可能的改动对应起来；是否值得改还要结合实际耗时。

| 检查点 | 联合看什么 | 值得排查的现象 | 优化方向 |
| --- | --- | --- | --- |
| 访问范围 | `type`、`key`、`key_len`、条件与索引定义；分区表还看 `partitions` | 只需少量结果，却全扫描或读取很宽的索引范围 | 检查[[mysql-index-predicates\|条件能否用于定位]]、联合索引列序，以及预期分区是否被裁剪；有候选索引却没选中时再核对成本与统计 |
| 过滤位置 | `rows`、`filtered`；实际扫描节点与过滤节点的行数 | 读出大量候选后才丢弃大部分 | 让选择性条件尽量缩小访问范围；检查能否提前过滤。[[mysql-index-condition-pushdown\|ICP]] 主要减少不必要的取行，不保证索引扫描量减少 |
| 完整行读取 | 查询所需列、索引覆盖情况、`Extra` 与实际取行路径 | 候选多且频繁补取完整行，而业务只需少数列 | 缩小列集、评估[[mysql-covering-index\|覆盖访问]]；不能从 `rows` 直接得出回表次数 |
| 重复访问 | 连接或子查询的算法、内层每轮行数与 `loops` | 每轮查得不多，但被外层大量行反复触发 | 减少外层输入，按实际路径设计 [[mysql-index-joins\|JOIN 索引]]；只需判断存在时避免生成不必要的重复组合 |
| 排序、聚合与中间结果 | `Extra`，TREE 中排序、聚合、物化节点的输入规模和耗时 | 最终结果很少，前面却处理大量记录或反复构建中间结果 | 尽早缩小输入与列集；比较[[mysql-index-ordering\|索引顺序与额外排序]]，检查[[mysql-intermediate-results\|中间结果]]是否能减少或复用 |

`rows × filtered / 100` 是当前表访问预计向后续操作提供的行数。扫描量大且保留比例低，可能意味着定位范围过宽；但 `filtered` 本身没有统一的好坏阈值。保留 100% 既可能是精准定位，也可能是业务要求读取整表；保留比例很低时，如果候选本来就少，过滤也可能很便宜。嵌套循环中的内层访问还需考虑执行次数，不能把一行的 `rows` 当作整条 SQL 的总检查量，也不能用这两个估算直接表示磁盘 I/O 或回表次数。

**「走索引、省排序、少循环」都要放回总工作量中比较。** 小表或需要读取大部分记录时，全表扫描可能合理；`type=index` 和 `Using index` 也可能扫描整个索引。`Using filesort`、`Using temporary` 表示有额外处理，不表示一定落盘。先筛出少量记录再排序，有时比沿排序索引扫描大量记录更划算。

## 用实际行数、循环与时间确定优先级

普通 EXPLAIN 只能指出计划中可能昂贵的地方。取得 ANALYZE 后，按同一节点对比估算与实际，再检查实际工作量和耗时：

- 估算与实际差距很大：检查参数分布、索引统计及列直方图。更新统计是否改变了计划和耗时，需要另外验证；估算错误不等于必然缺少索引。
- 估算接近，但实际处理很多：说明当前路径确实工作量大，按上表减少扫描、取行或重复处理。
- 实际处理量不大，耗时仍高或波动明显：结合[[mysql-slow-query|慢查询排查]]检查锁、I/O、资源竞争和请求中的其他等待，执行计划不能解释全部延迟。

`actual time=a..b rows=r loops=n` 中，a、b 分别是获得首行和完成该节点的时间，单位为毫秒；多轮执行时，时间和 rows 显示每轮平均值，loops 是执行次数。`r × n` 可辅助理解该节点累计输出量，但扫描节点输出、过滤后输出与最终返回量是不同对象，也不能跨节点相加当作总扫描量。

**「节点时间包含子节点」**，不能把父子时间相加。先沿耗时较大的分支向下检查，结合 loops 判断是单轮慢还是重复太多；子节点承担的大部分时间，不应再次归因于父节点自己的过滤或连接计算。

## 一个从现象走向优化假设的例子

[[mysql-manual-queries#EXPLAIN ANALYZE 的行数与时间|官方 ANALYZE 示例]]统计两名员工在指定月份的收款总额，先扫描 staff，再按员工索引查 payment，最后过滤日期。原文使用 MySQL 8.0.18、Sakila 数据库，以下保留其测量值说明读法，不代表本地或 8.4 的性能：

| 节点 | 预计每轮输出 | 实际每轮输出 | loops | 平均每轮完成时间 |
| --- | --- | --- | --- | --- |
| staff 表扫描 | 2 | 2 | 1 | 0.051 ms |
| payment 索引查找 | 8043 | 8024 | 2 | 19.988 ms |
| 日期过滤，包含下方索引查找 | 894 | 2844 | 2 | 22.767 ms |

staff 虽然全表扫描，但只有两行。payment 已经使用索引，仍需每轮读取约八千条；日期过滤的时间大部分来自下方取数。查找量估算接近实际，偏差主要出现在日期过滤比例，不能笼统说整个计划估算不准。

由此可以提出两类待验证假设：一是改善日期分布估算，二是评估能否将日期与员工条件共同用于定位，减少取出后再丢弃的候选。后者需核对日期条件写法和索引列序；直方图本身不提供新的取数路径。比较改动时，应检查 payment 访问量、两轮累计工作与整体耗时，而非优先消除 staff 的 `ALL` 或只看 `key` 是否非空。原文没有给出这些改动后的测量结果，不能据此断言哪种方案更快。

## 改完怎样确认有效

先说明要减少哪一步的工作，再按[[mysql-query-optimization#用对比验证收益|查询优化的验证方法]]对照：

1. 核对结果、重复行、NULL 和排序语义，确保改写仍满足业务需求。
2. 在相同数据、代表性参数及可比负载下，保留前后计划，检查目标节点的实际行数、loops 与耗时是否按假设变化，同时检查是否增加了其他扫描、排序或物化。
3. 比较完整请求延迟和资源消耗，区分冷热缓存与并发影响；新增索引还要评估写入和空间代价。ANALYZE 带有测量开销，其时间不直接等于应用请求耗时。

有效的结论应能说清「哪一步原来做了多少工作，改后减少了什么，实际收益与代价是什么」。字段取值变得更符合预期，只是验证的一部分。

## 字段含义

| 字段 | 含义 | 取值说明 |
| --- | --- | --- |
| `id` | SELECT 查询块的编号 | 整数标识查询块，同一查询块的多张表可使用相同编号；UNION 结果行可为 NULL。编号不能直接当作执行先后顺序 |
| `select_type` | 查询块在整个语句中的类型 | SIMPLE、PRIMARY、SUBQUERY 等；完整取值见[[mysql-explain-select-type\|查询块类型]] |
| `table` | 本行访问的表或中间结果 | 表名、别名，以及下文列出的中间结果标识 |
| `partitions` | 计划匹配记录的分区 | 分区名称列表；非分区表为 NULL |
| `type` | 当前表的访问方式 | const、ref、range、index、ALL 等；完整取值见[[mysql-explain-type\|访问类型]] |
| `possible_keys` | 可用于查找当前表记录的候选索引 | 索引名称列表；NULL 表示没有相关候选。候选不保证适用于最终连接顺序 |
| `key` | 计划实际选用的索引 | 索引名；NULL 表示未选用索引；index_merge 时可列出多个索引 |
| `key_len` | 选用索引键的长度 | 字节数；key 为 NULL 时也为 NULL；index_merge 时可列出各索引对应的键长度 |
| `ref` | 与索引键进行比较的对象 | 常量、列或表达式结果；具体标识见下文 |
| `rows` | 预计需要检查的行数 | 行数估算；InnoDB 下不保证准确，不等于最终返回行数 |
| `filtered` | 候选经本表条件过滤后预计保留的百分比 | 最大为 100，表示预计全部保留；数值越小，预计过滤掉的比例越大 |
| `Extra` | 其他执行信息 | 可同时出现多个标记；逐项含义见[[mysql-explain-extra\|附加信息]] |

字段定义依据[[mysql-manual-queries#EXPLAIN 的字段与常见标记|官方输出说明]]。`possible_keys` 描述查找候选，`key` 描述实际选择；仅用于覆盖扫描的索引可能出现在 key 中，却不在 possible_keys 中。

## table 的中间结果标识

| 标识 | 含义 |
| --- | --- |
| `<derivedN>` | 访问 id 为 N 的查询块产生的派生表结果 |
| `<subqueryN>` | 访问 id 为 N 的查询块产生的物化子查询结果 |
| `<unionM,N>` | 访问 id 为 M、N 等查询块的 UNION 合并结果 |

N、M 是查询块编号的占位符，这些标识不是业务表名。

## ref 的取值

| 值 | 含义 |
| --- | --- |
| `const` | 用常量与索引键比较 |
| 列名或限定列名 | 用相应列的值与索引键比较，限定名可包含库名、表名或别名 |
| `func` | 比较值来自函数或其他表达式的结果；具体表达式可通过 EXPLAIN 后的 SHOW WARNINGS 查看 |
| `NULL` | 本行没有显示此类索引键比较对象；范围访问也可出现 NULL，不表示未使用索引 |

`type=ref` 中的 ref 是访问类型，`ref` 列说明用于比较的对象，二者含义不同。

## key_len 的边界

`key_len` 结合列类型、字符集、是否可空和索引定义，可辅助判断使用了哪些联合键部分。可空列会增加 NULL 标记的一个字节；它不是索引列数，也不表示未参与定位的列不能用于过滤、覆盖访问或排序。长度更大不自动意味着更好，应核对希望用于定位的键部分是否实际参与。
