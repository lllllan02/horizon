**Temporal 是用代码编排业务流程、支持故障后恢复进度的持久执行平台。** 它把流程状态保存、任务调度和重试等基础工作集中处理，让跨服务、需要等待的业务不必全部依赖手写状态机。

例如「生成发布内容 → 等待人工批准 → 调用发布接口」：普通程序中途退出后，需要自己判断执行到了哪一步、人的决定是否收到、发布是否已经成功。Temporal 通过保存执行历史支持继续推进；这项能力称为持久执行（Durable Execution），基本分工见[[temporal-platform|官方平台导读]]。

## 一个流程怎样运行？

**Workflow（工作流）是描述步骤、分支和等待的流程代码。** 在上述例子中，它决定何时等待审批、拒绝后结束还是批准后发布。

**Activity（活动）是执行外部操作的函数。** 生成内容时的模型调用、实际发布时的网络请求放在 Activity 中；结果交回 Workflow 决定后续步骤。

**Worker 是运行这些业务代码的工作进程。** Temporal Service 保存事件历史并调度任务，Worker 通过任务队列（Task Queue）领取任务、执行代码并回报结果。

基本接入过程是：用 SDK 编写 Workflow 和 Activity → 在 Worker 注册并监听队列 → 客户端启动流程 → Worker 持续领取任务。服务端可以自建，也可以使用 Temporal Cloud；业务执行仍需要 Worker。

人的决定可通过 Signal（异步信号）传入等待中的 Workflow，由 Workflow 判断是否批准，再决定是否调用发布 Activity。

## 进程重启后，为什么能继续？

Temporal 保存事件历史（Event History），其中包括 Activity 的完成结果、定时器和外部信号。Worker 故障后，可通过重新执行 Workflow 代码并读取历史结果重建状态，再继续未完成的步骤；[[temporal-durable-execution|恢复机制导读]]解释了这一过程。

这带来两个必须遵守的边界：

- Workflow 要有「确定性」：相同历史应得到相同控制决定。时间、等待等使用 SDK 原语，网络、文件和模型调用放入 Activity。
- Activity 需要考虑「重复执行」：如果发布已成功，但完成结果尚未可靠记录，重试仍可能再次调用发布接口。业务应使用稳定操作 ID 等方式实现[[idempotency|幂等]]，不能把恢复能力理解为外部副作用必然只发生一次。

[[temporal-retry-policy-summary|重试与超时策略]]用于约束失败后的再次尝试；业务拒绝、权限不足等结果仍需由应用决定如何结束或处理。

## 什么时候值得引入？

按上述机制判断，Temporal 更适合「多个步骤必须持续推进，而且可能跨越故障或长时间等待」的场景，例如订单履约、人工审批、跨服务任务和多步骤 Agent 执行。它负责流程执行的可靠性，Agent 的判断和业务规则仍由应用提供。

如果只是一次短请求或单个可重试后台任务，可以先评估现有服务与任务队列是否已够用。引入 Temporal 还需维护 Worker、配置超时和重试，并遵守 Workflow 的确定性约束；自建时还增加服务端与存储的运维工作。这是基于机制的初步取舍，尚未做项目选型或性能实测。
