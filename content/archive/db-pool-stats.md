**Go 的 DBStats 是 `database/sql` 提供的连接池统计，包含当前连接数量和累计等待数据。**

数据库调用变慢时，它帮助判断请求是否因连接不足而排队。统计属于应用中的某一个 `*sql.DB` 连接池，不是整个 MySQL 服务端的连接总数，也不是单条 SQL 的耗时；字段语义依据[[go-sql-connections#状态和累计计数分别说明什么|Go 官方连接池导读]]。

## 能拿到哪些数值

下面是同一连接池相隔 10 秒的两次假设采样，用于解释字段，不是比赛现场实测，也不是推荐配置。

| 字段 | 含义 | 第一次采样 | 10 秒后 |
| --- | --- | --- | --- |
| `MaxOpenConnections` | 配置的最大打开连接数；0 表示不设上限 | 20 | 20 |
| `OpenConnections` | 池中打开的连接总数 | 20 | 20 |
| `InUse` | 当前使用中的连接数 | 20 | 20 |
| `Idle` | 当前空闲连接数 | 0 | 0 |
| `WaitCount` | 累计进入等待连接的次数 | 1,000 | 1,400 |
| `WaitDuration` | 已累计记录的连接等待时间 | 20s | 100s |
| `MaxIdleClosed` | 因空闲连接数量限制而关闭的累计连接数 | 12 | 12 |
| `MaxIdleTimeClosed` | 因空闲时间超限而关闭的累计连接数 | 0 | 0 |
| `MaxLifetimeClosed` | 因连接寿命超限而关闭的累计连接数 | 3 | 3 |

前四项读当前值，后五项看区间增量。`InUse` 包括事务或结果读取期间占用的连接，不等于正在执行 SQL 的数量；后三项关闭计数也不等于 SQL 失败次数。

## 怎样从数值判断排队

两次采样时，`InUse = MaxOpenConnections = 20`、`Idle = 0`，说明当时连接都在使用。仅有 `OpenConnections = 20` 不足以判断打满，因为其中可能有空闲连接。

这 10 秒内，等待次数增加 `1,400 - 1,000 = 400`，累计等待时间增加 `100s - 20s = 80s`，说明采样区间内发生了明显的连接等待。多人同时等待时，各自的时间会累加，所以 10 秒内累计增加 80 秒并不矛盾。

`80s / 400 = 200ms` 可作为该窗口的平均等待线索。等待次数在进入排队时增加，等待时间在取得连接或取消等待后记入；跨窗口的等待会影响这个比值，因此它不是精确配对的一组请求的平均值，也不是所有请求的平均耗时或 P99。累计值随对应连接池实例重新创建而重置，不能跨重启直接相减。

**「DBStats 没有直接提供当前排队请求数。」** `WaitCount = 1,400` 不能解释为此刻有 1,400 个请求在等。两次采样也不能证明整个区间始终满载；结合连续采样与[[trace-and-span|链路追踪]]中获取连接的耗时，才能进一步判断等待对请求延迟的影响。连接为什么长期被占用，还需另查 SQL、事务和资源归还路径。

## 怎样采集

原生 `database/sql` 直接调用 `sqlDB.Stats()`。使用 [[go-sql-connections#GORM 的状态入口与采样边界|GORM 的底层数据库接口]]时，先从普通数据库句柄取得 `*sql.DB`；下面是放在返回 `error` 的函数中的采样片段，需导入 `log`，`gormDB` 为已有的 GORM 数据库句柄：

```go
sqlDB, err := gormDB.DB()
if err != nil {
    return err
}
stats := sqlDB.Stats()
log.Printf("db_pool=%+v", stats)
```

可以在压测期间每秒调用一次并记录采样时间、应用实例和连接池标识；这是示例采样间隔，短于间隔的洪峰仍可能漏掉。`WaitDuration` 的类型是 `time.Duration`，上例会显示为 `80s` 等可读形式；导出数值时可用 `.Seconds()` 统一为秒。采样复用已有连接池，不为每次采样重新创建连接池。

本文未连接真实数据库运行采样代码，表中数值均为假设示例。
