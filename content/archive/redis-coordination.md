**Redis 能原子地修改自身状态，业务正确性还取决于租约、重试和外部资源是否接受这次操作。** 锁、限流和库存预扣都需要先界定这个保证范围。

## 锁保护到哪一步

以 7.2 命令为例，`SET lock:order:42 <token> NX PX 30000` 将不存在检查、写入和过期设置合为一次操作。token 为本次持锁生成唯一随机值；释放时用短 Lua 原子比较 token 后删除，避免旧持有者删掉新锁。

但 A 暂停超过租约后，B 可能已持锁，A 恢复仍会写外部数据库。比较 token 只能防止误删，不能阻止这次过期写入。严格保护资源需要资源端实际检查[[distributed-locks|隔离令牌]]，或用事务、唯一约束、版本条件实现业务不变量。续期还要处理续期失败及旧执行者停止；故障切换丢失锁记录也会影响互斥。

[[redis-coordination-docs#锁的租约与所有者|锁文档导读]]区分单实例租约与 Redlock 的多独立节点假设。Redlock 不能用「有多个副本」概括，也不能省略时钟、耗时与外部资源约束。

## 限流怎样避免并发超发

固定窗口可用维度与窗口组成 key，计数与首次设置过期放在一次原子操作中，防止进程在 `INCR` 后、`EXPIRE` 前退出而遗留永久计数。窗口边界附近仍可能出现双倍突发，所以选择算法需从业务允许的突发量出发。

滑动窗口可用 ZSet 保存请求时间并清理窗口外记录，代价随记录量增长；令牌桶保存剩余令牌与补充时刻，在 Lua 内完成补充、判定和扣减。[[rate-limiting|限流]]还需明确 Redis 不可用时放行还是拒绝、时钟依据与热点维度，算法名称不能决定这些取舍。

## 库存预扣怎样与订单衔接

Lua 可以检查库存、检查请求 ID、扣减并记录结果，但不能原子提交外部订单。Redis 扣减后订单失败，需要可恢复的补偿；订单成功而客户端重试，需要按业务 ID 返回原结果；补偿自身也须幂等。

若不允许任何超卖，应明确最终库存约束由哪个权威存储执行。Redis 可承担流量筛选或预占，但不能把异步复制的内存状态直接当成所有故障下唯一可靠账本。

## 回答思路与追问

先说明原子步骤，再把「进程暂停、请求超时、主节点切换、外部提交失败」分别放进时间线。

追问：锁过期后旧任务仍运行，续期能否证明绝不会重复执行？不能；要看资源端约束。限流服务故障时全部放行是否合理？取决于被保护系统剩余容量和请求重要性。库存补偿重复到达怎么办？用补偿 ID 和原预占状态进行受控状态转换。
