**查询资源排查是把语句的处理量与同时间段的 CPU、内存和存储活动对齐，判断延迟来自多做工作，还是等待共享资源。** 计划合理不保证实例有足够资源；实例 I/O 高也不能直接证明某条 SQL 在等待磁盘。以下以 MySQL 8.4、InnoDB 为范围。

## 先区分工作量与资源竞争

| 观察 | 继续核对 | 对应办法与边界 |
| --- | --- | --- |
| CPU 上升，同时扫描、循环或排序量增加 | 同窗口的高频语句、代表性参数与实际计划 | 减少输入、重复计算和无用排序；若单次工作稳定而频次激增，还需控制请求量 |
| 文件读等待上升 | 语句与线程证据、物理读增量和系统存储延迟 | 减少无关扫描与分散取行，检查热点页是否被挤出；全局文件统计不能独立归因到一条 SQL |
| 写等待、待写页或日志空间压力上升 | 后台写回、写入速率和系统磁盘指标 | 平滑批量写入并匹配写回能力；扩大缓冲区只是增加缓冲余地 |
| 临时结果增加，内存或临时存储压力上升 | 物化节点、参与行数、行宽与语句级计数 | 减少中间结果；调整预算需同时考虑并发查询，不能只放大单表上限 |

文件 I/O 与语句统计的口径见[[mysql-performance-diagnostics|性能诊断导读]]。通过[[mysql-statement-tracing|语句事件追踪]]缩小到目标执行后，仍要与系统指标交叉核对；事件名称中的 I/O 不自动等于物理磁盘操作。

## 临时结果为什么会放大开销

假设查询需要先保存大量宽行，再分组或排序，最终只返回少量结果。返回行数少，前面的读取、保存与处理仍可能很多。先缩小合法过滤范围、只保留中间步骤需要的列，再检查最终计划是否减少了工作；条件不能越过会改变结果的聚合或 LIMIT 边界。

内部临时表可以在内存，也可以使用磁盘；TempTable 的单表限制与全局内存预算是不同对象。`Using temporary`、`Created_tmp_disk_tables` 都有观察边界，尤其启用内存映射文件时不能只看磁盘临时表计数，细节见[[mysql-temporary-tables|内部临时表存储与监测导读]]。调整内存预算可能减少溢出，却不减少原查询总工作量，还会改变并发下的内存占用。

## 同一计划为什么也会忽快忽慢

同样访问一批页，首次需要读入、后续已缓存时，耗时可能不同；另一个任务集中读写也会改变共享资源的可用量。[[mysql-buffer-pool-lifecycle|缓冲池]]缓存的是页，高命中率仍不能排除少量慢读或后台写回竞争；[[mysql-dirty-page-flushing|刷脏与检查点]]解释写回为何不能无限延后。

验证时分别保留冷热缓存、并发和后台任务条件，确认对应处理量或等待减少，再看请求延迟。本文给出诊断关系与假设例子，未进行压测或配置调整。
