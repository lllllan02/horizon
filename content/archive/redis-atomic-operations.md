**Pipeline 减少等待往返，MULTI/EXEC 组织不被其他命令穿插的执行，Lua 将读取、判断和修改放到服务端一次完成。** 三者都不能单凭名称保证业务只发生一次，执行结果丢失后的重试仍需判断。

## 怎样选择

| 方式 | 解决的问题 | 代价与保证边界 |
| --- | --- | --- |
| 单条原生命令 | 已有原子计数或条件写入，如 `INCR`、`SET NX PX` | 优先使用；网络超时后结果可能未知 |
| Pipeline（流水线） | 连续发送命令，减少逐条等待 RTT 和系统调用开销 | 无事务隔离保证；大批次占缓冲并增加等待 |
| `MULTI/EXEC` | 将已确定的命令排队，再连续执行 | 入队错误与执行错误不同；运行时错误不会回滚其他成功命令 |
| `WATCH` + 事务 | 根据读出的值计算，提交时检查是否被修改 | 冲突则放弃执行并重读重试；高冲突时浪费往返 |
| Lua / Redis Functions | 在服务器内完成短小的条件更新 | 占用执行时间；写入后报错也不能依赖自动回滚 |

[[redis-execution-docs|官方事务与脚本导读]]说明了这些差异。Functions 自 Redis 7.0 提供服务端函数管理；它与临时 Eval 脚本的管理生命周期不同，使用前还需核对客户端和部署流程。

## 用库存扣减看原子边界

假设库存为 1，两次独立的「读库存 → 判断大于零 → 扣减」可能都通过判断。短 Lua 可先检查库存，再在同一次执行中扣减，消除其他客户端在判断与修改之间插入的窗口。

但扣减成功后响应丢失，调用方不知道结果；盲目重发会再次扣减。需要给请求一个稳定业务 ID，并在同一个原子操作中检查已处理记录、执行扣减和保存结果。记录保留时间也要覆盖可能的重试窗口；脚本应先验证参数与 key 类型，避免写入后才发现错误而留下部分结果。

这个操作只覆盖 Redis 内的状态。数据库订单提交、支付与 Redis 扣减之间仍可能一侧成功，需要权威约束和恢复流程。Cluster 中脚本涉及的 key 还须符合[[redis-cluster|同槽限制]]。

## 回答思路与追问

回答「Redis 事务支持原子性吗」时，明确说的是执行隔离、失败回滚还是持久性，分别给条件；不要只回答「支持」或「不支持」。

追问：事务中 `SET a x` 成功，后面的 `INCR a` 报类型错误，a 会恢复吗？不会；其他已成功操作仍在。再问连接在 EXEC 后断开，应先将结果视为未知，根据业务 ID 查询或安全重试，不能以客户端报错推断服务端未执行。
