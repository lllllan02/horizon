**选 Redis 消息方案，先区分实时通知、取走任务和保留可追踪事件。** 可靠处理需要把消息保留、领取、业务提交、确认和失败接管连起来。

| 方案 | 基本能力 | 仍需处理 |
| --- | --- | --- |
| Pub/Sub | 向当前订阅者推送通知 | 断线期间无历史重放，不能承担可靠待办 |
| List | 从一端加入、另一端取出 | 简单弹出后崩溃会丢处理机会；可另建处理中列表和恢复协议 |
| Stream + 消费组 | 保留带 ID 的记录，跟踪组内已投递未确认消息 | 失败接管、幂等、裁剪、积压和底层持久化 |
| Asynq 等任务框架 | 在 Redis 上组织任务、重试、调度与工作进程 | 业务幂等、容量与部署兼容性仍需自己负责 |

这些方案处于不同层次：框架可替应用封装部分任务协议，底层仍依赖 Redis。[[redis-go-projects#Asynq 的任务状态|Asynq 源码]]展示了 List、ZSet、Hash 与 Lua 的组合，并不等同于 Stream 的封装。

## Stream 消费组怎样恢复未完成任务

在 7.2 基线下，`XADD` 追加记录，`XREADGROUP` 将消息交给消费者并记录到待处理列表 PEL（Pending Entries List）。处理成功后执行 `XACK`，移除该组的待确认记录；消息正文仍在 Stream 中，保留期需单独管理。

消费者崩溃后，其他消费者通过 `XPENDING` 观察，再用 `XCLAIM/XAUTOCLAIM` 接管满足空闲时间条件的消息。该过程需要应用或框架驱动；消费组不会替业务自动完成重试、死信与报警。[[redis-streams-docs|官方消息语义导读]]保留了对应命令依据。

## 为什么还会重复与丢失

假设数据库已完成发货状态更新，进程在 XACK 前崩溃。消息再次投递时，业务可能重复执行；应在权威业务事务内按消息或业务 ID 去重，并保留能覆盖重放窗口的记录。先 XACK 再提交业务则会制造另一种窗口：确认成功、业务尚未完成就崩溃。

重试也依赖消息仍在。过早裁剪可能删除未处理正文；故障切换丢写由[[redis-high-availability|复制与恢复策略]]决定；一个消费者长期不确认会积累 PEL。消息 ID 有序也不保证多个消费者并发完成业务的顺序。

## 回答思路与追问

回答「Redis 能否做消息队列」应给具体方案、保留与确认机制，再说允许的丢失和重复范围；不能只比较读写速度。

追问：订单事件要求长期重放、多组独立消费和严格保留管理，继续使用 Redis 还是选择专门日志系统？比较保留成本、吞吐、分区顺序与运维能力。不要从某个框架标注「至少执行一次」推导出任意 Redis 故障后都绝不丢任务。
