审批已经落盘，任务也保存了执行进度，仍可能重复发布。原因是**「远端操作成功」和「本地保存完成」发生在不同的提交点**；恢复不能只看本地是否标记成功。

## 同一个执行中状态，可能对应什么事实？

草稿发布的顺序是：`保存 executing → 发布服务完成写入 → 保存回执与 done`。

| 崩溃时点 | 检查点记录 | 实际情况与处理 |
| --- | --- | --- |
| 调用之前 | `executing` | 尚未发布，可使用原操作 ID 调用 |
| 发布成功、回执保存之前 | `executing` | 已经发布，需查询或幂等重试 |
| 完成保存之后 | `done` | 复用结果，继续后续步骤 |

前两行在本地看起来一样。更频繁地保存不能让远端效果和本地记录自动成为一个事务；必须让执行端帮助识别同一次操作。

## 怎样让重试不产生第二次效果？

[[idempotency|幂等]]让同一次操作重复调用时，不产生额外的业务效果。调用方在首次执行前生成并保存稳定的操作 ID，恢复时继续使用它；执行端根据这个 ID 识别重试：

- 已有记录且参数相同，返回原回执。
- 已有记录但参数不同，拒绝请求，避免同一 ID 被用于不同操作。
- 没有记录，执行操作并保存结果。

这样，即使发布成功后本地未保存回执，恢复时再次调用也能取回原结果，再保存完成状态。

这需要执行端支持去重，客户端单方面增加一个 ID 字段并不够。执行端还需保证去重记录与业务变更共同成立，并让去重记录的保留时间覆盖可能的重试周期。[[aws-idempotent-retries-summary|AWS 的幂等 API 设计]]说明了操作身份、参数核对与结果复用的分工。

若远端不能去重，也不能查询结果，就应进入「结果未知、等待核对」，不能把未知当成失败后自动重试。回退检查点也不能撤销已发生的外部效果；需要撤销时，应单独设计补偿操作。

## 退款超时后，客服应该回答失败还是成功？

支付服务可能已经退款，只是回执没有送达。此时本地应表达“结果待核实”，关联原业务操作继续查询；再次发起同一意图时沿用原操作身份和已冻结参数，而不是根据新的模型工具调用 ID 创建另一笔退款。

恢复路径取决于远端能力：能按操作 ID 查询，就核对真实状态；支持可靠幂等，则按其契约重试并复用回执；两者都没有，自动重做无法保证安全，应转入人工核对。查询暂时查不到也未必证明未执行，要考虑请求仍在途、记录可见性及接口约定。

重新核对期间，任务可以继续完成不依赖退款结果的工作，但不能向用户宣称资金已到账。排障需串起业务操作 ID、每次网络尝试和远端回执；单看“调用报错”的日志无法判断业务效果。若用户此时取消，应核对是否需要独立补偿，而不是删除本地任务。
