**幂等性（Idempotency）是指：在约定条件下，同一次操作重复执行，对业务产生的预期效果与执行一次相同。** 它让调用方在响应丢失、超时或消息重复投递时，能够再次尝试，而不重复创建订单、扣款或发券。

例如「把数量设为 3」连续执行多次仍是 3，「数量加 1」则会不断累加。幂等不要求程序只运行一次，也不要求每次响应完全相同；需要约束的是重复操作带来的业务效果。

## 怎样认出同一次操作

创建订单已经成功、响应却丢失时，客户端只知道超时。直接再创建可能得到两个订单；但仅比较参数也不够，因为用户可能确实要下两笔内容相同的订单。

因此，可以在首次请求前为一次业务意图生成**「幂等键（Idempotency Key）」**，重试沿用该键与原参数，新的业务操作使用新键。服务端在约定的调用方和接口范围内识别键，并核对参数，避免同一个键被用于不同操作。[[aws-idempotent-retries-summary|AWS 的幂等 API 设计]]解释了为什么明确的请求身份比猜测参数是否重复更可靠。

客户端生成键只是提供标识；服务端还必须实现对应约定。若重试跨越进程重启，操作标识也要保存下来，否则重新生成键仍可能被当成新操作。

## 认出重复以后，怎样避免重复生效

服务端通常要保存键、原请求参数或摘要、处理状态，以及结果或结果标识。重复请求到达时，已完成的返回既有结果；仍在执行的按接口约定等待或返回处理中，不能再启动一份独立操作。

难点在于**「去重记录与业务变更必须共同成立」**：先写「处理过」再执行业务，崩溃后可能漏执行；先完成业务再单独写标记，崩溃后又可能重复执行。单独的内存集合或 Redis SETNX 标记无法消除这两个操作之间的故障窗口。

以只涉及一个数据库的订单创建为例，可用事务把「插入具有唯一约束的操作记录 → 创建订单 → 记录结果」一起提交。并发请求由唯一约束和事务协调，事务回滚时两者都不生效，提交后重复请求读取原结果；若提交响应丢失，也应按原键核查。单纯「先查询不存在，再插入」仍可能被并发穿透。这是原子性要求在本地数据库中的一种实现方式，不适用于任意远程调用。

有些业务也可通过唯一业务键或条件状态迁移达到同样目标。例如只允许订单从待支付变为已支付一次；依赖这次迁移的数据库变更仍需一起提交，不能每次收到回调都执行。支付与取消并发时，还需区分订单状态与外部扣款的约束。

## 保证在哪些地方结束

去重记录有保留期限。清理以后，旧请求可能再次被当成新请求，因此保留窗口要覆盖允许的重试和重放范围；资源删除也不代表旧请求不再到达。长期停在「处理中」的操作还需通过持久状态和结果核查恢复，不能只等标记过期就假定业务未执行。

远程副作用也不受本地事务回滚保护：支付渠道已扣款后，即使本地回滚，款项仍可能扣除。需要沿用渠道支持的幂等键或查询原操作，再通过对账、必要的补偿处理未知结果。[[stripe-error-recovery-summary|Stripe 的错误恢复约定]]展示了具体边界：API v1 至少保留键 24 小时，执行后产生的 500 也可能被缓存；一直返回错误不等于一直没产生副作用。

幂等还不保证不同操作之间的顺序。「设为 3」之后执行「设为 4」，再重放旧的「设为 3」，仍可能覆盖新值。[[gcs-retry-strategy-summary|Cloud Storage 的条件幂等]]通过版本前置条件约束部分操作，使旧请求不能修改不再符合条件的资源。防重复、版本控制与顺序约束需要分别判断。

## HTTP 方法能保证多少

[[http-idempotency-summary|RFC 9110]]将 PUT、DELETE 和安全方法定义为幂等，但方法语义仍需服务端正确实现。重复 DELETE 可以返回不同状态码，只要没有因此产生额外的预期业务变更；逐次写访问日志也不违反这个约定。POST 默认没有幂等保证，但具体接口可以通过幂等键提供。

幂等解决重复操作的安全性，不保证操作最终成功。是否值得重试、重试多久以及何时查询结果，仍由[[retry-decision|错误分类与重试决策]]决定。
