**先判断现有系统缺的是状态保存、记忆形成、检索，还是整套 Agent 运行机制，再选择组件。** 这些层可以组合，不能把文件、向量库、LangGraph 和 Letta 当成承担同一职责的四个选项。

## 各方案接管哪一部分？

| 方案与依据 | 接管的主要工作 | 保留给应用的工作与取舍 |
| --- | --- | --- |
| 文件＋索引；[[claude-code-memory\|Claude Code 的具体设计]] | 以文本保存规则和经验，常驻短入口后按需读文件 | **可审阅、易起步**；规模、并发、范围与失效要另管 |
| [[langgraph-memory\|LangGraph Store＋可选 LangMem]] | 在已有图运行中组织跨线程数据，补充提取和管理工具 | **可组合、控制较细**；策略和评测仍需开发，Store 本身不会自动形成记忆 |
| [[mem0-memory\|Mem0 OSS／Platform]] | 封装消息提取、保存、搜索与显式更新 | **减少记忆服务编排**；需核对版本语义、后端组件、后台完成状态及租户边界 |
| [[letta-memory\|Letta]] | 提供状态型 Agent、常驻块与归档记忆工具 | **读写融入运行模型**；已有运行系统接入时需评估迁移，不只是换数据库 |
| [[graphiti-memory\|Graphiti／Zep]] | 围绕实体关系与变化时间形成、查询记忆图 | **适合关系和历史查询**；多出消歧、抽取与图维护，Graphiti 与托管 Zep 的周边能力不同 |

表中产品事实来自 2026-10-12 导读；粗体取舍是基于其职责的工程归纳，没有同条件性能排名。

## 哪些需求对应较小的起点？

- **只需恢复原会话**：先完善历史存储、Checkpointer 和上下文管理。无需为此额外构建自动长期记忆。
- **单人本地编程，少量稳定规则与经验**：文件和明确加载入口容易检查。目录变大、检索漏召回或并发写入增多时，再评估结构化存储与索引。
- **多用户助手，偏好字段有限**：从服务端绑定身份的结构化档案开始；确实需要从自由对话自动提取、积累大量经历时，再接入记忆形成与语义查询。
- **已有 LangGraph 工作流**：优先评估现有 Store 是否足够，自动提取层可用 LangMem 或外接服务。引入 Mem0 会接管部分形成与查询工作，但不会替换线程 Checkpointer。
- **关系频繁变化，必须回答过去状态**：评估 Graphiti 一类时序表示；只有当前属性查询时，数据库记录与版本管理通常更直接。

## 怎样验证接入值得？

先用同一组跨会话任务比较简单基线和候选方案，关注旧偏好被纠正后是否停止影响回答、换项目是否误用、后台写入延迟是否可接受，以及总成本是否下降。具体过程沿用[[agent-memory-evaluation|记忆评测]]。

若主要问题是候选提取错误，更换向量数据库通常不能修正事实；若已存正确但查不到，优先改查询和表示；若能找到却未用对，检查注入位置、条件表达和冲突处理。组件升级应对应观测到的故障，而不由“需要长期记忆”直接推出复杂架构。

## 什么时候值得引入专门的记忆框架？

如果需求只是保存用户明确设置的项目语言，带权限与版本的业务表可能已经够用。只有需要从自由对话提取、跨会话召回、处理更新和派生关系时，专门组件才可能减少编排工作。

试用应沿真实生命周期：首次记住、更正、跨项目查询、删除、后台重跑和服务故障。核对哪些语义由框架保证，哪些仍需业务实现，尤其是身份隔离、写入冲突和删除传播。演示中“记住一句话”不能证明这些边界已经成立。

同时评估迁移出口：能否导出正文、来源、范围和版本，能否重建索引，升级后是否改变更新语义。相比只比较搜索效果，持续写入成本、纠错成本和可恢复性更能决定长期接入代价。
