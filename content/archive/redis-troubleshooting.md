**调用方的 Redis 延迟包含客户端等待、网络传输、服务端排队与执行，以及响应读取；SLOWLOG 只覆盖其中的命令执行时间。** 排查先定位时间花在哪里，再选能减少该项成本的措施。

## 从现象缩小范围

| 现象与证据 | 优先检查 | 可采取的措施及边界 |
| --- | --- | --- |
| 连接池等待高，服务端负载一般 | 池容量、连接占用、调用并发、重试 | 调整并发和连接使用；只扩池可能把拥塞转移到服务端 |
| SLOWLOG 出现重命令 | 大范围读取、长脚本、大集合操作 | 限制范围、缩短脚本、拆分数据；增加 I/O 线程不能消除计算量 |
| 慢日志少但响应大、网络繁忙 | 返回字节数、带宽、跨区 RTT | 分页、按需字段、批量与就近部署；批次不能无限增大 |
| 周期性尖峰与后台任务重合 | fork、COW、AOF 刷盘、磁盘与调度 | 为内存和 I/O 留余量，调整工作安排；不能只凭时间重合认定因果 |
| 单分片特别忙 | hot key（热点 key）与流量倾斜 | 本地缓存、请求合并或业务拆分；扩容不自动拆开一个 key |
| 内存增长、频繁淘汰或拒写 | 对象大小、TTL、策略、缓冲与碎片 | 控制数据量与保留期，再评估扩容；RSS 与 used_memory 分开看 |

[[redis-memory-diagnostics-docs|官方诊断导读]]说明 SLOWLOG、INFO、延迟事件与扫描的观察范围。big key（大 key）是单对象过大，hot key 是访问集中，两者可能同时发生，也可能完全独立。

## 诊断工具如何避免扩大问题

先按实例、命令和时间窗口比较请求量、错误率、P95/P99、响应大小，再结合 `INFO`、`SLOWLOG GET` 与已启用的延迟监控。慢日志阈值过高、记录已滚动或等待发生在执行前，都可能让慢日志为空。

在大键空间里用低速 `SCAN` 增量检查，避免一次 `KEYS` 扫完；SCAN 仍有总量成本，`COUNT` 是工作量提示，结果可能重复，也不是一致快照。删除大对象可评估 `UNLINK`：从键空间摘除后在后台回收，回收工作与内存占用不会瞬间消失。

客户端也要核对超时与重试。[[redis-go-projects#go-redis 的客户端职责|go-redis]]可管理连接、事务和集群连接，但不会替业务证明 `INCR` 重试安全。多层同时重试会放大流量，应限制重试次数、总时长和并发。

## 回答思路与追问

给出「假设 → 可区分它的指标 → 小范围改动 → 对照结果」的排查顺序。措施验证同时看吞吐、尾延迟、错误和资源，不只看平均耗时。

追问：慢日志为空、P99 很高，是否证明 Redis 服务端没问题？不能，还需检查排队、fork、调度、网络及客户端。删除大量 key 后 RSS 不降，是否证明内存泄漏？先比较 used_memory 与分配器、碎片和后台释放状态，再作判断。本篇是排查方法，未声称运行过压测。
