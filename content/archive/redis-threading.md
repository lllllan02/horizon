**Redis 的常规命令主要由主线程串行执行，同时通过事件循环处理多个连接；后台工作还会使用其他线程或进程。** 「单线程」描述的是特定工作，不代表整个进程只有一个线程，也不能推导出应用的多步业务操作天然安全。

## 一次请求经过什么

客户端等待连接 → 编码与发送 → 服务端读入、解析 → 等待并执行命令 → 写出响应 → 客户端解码。I/O 多路复用让服务端只处理已就绪连接，避免为每个连接安排一个阻塞线程；连接并发与命令并行是两个维度。

以 7.2 为基线，启用 I/O 线程可以分摊网络写出，也可配置分摊读取和解析；常规数据命令仍由主线程执行。后台释放、AOF 刷盘与 RDB/AOF 重写分别由相应线程或子进程承担。[[redis-execution-docs|执行模型导读]]区分了 7.2 配置与 Redis 8.0 的新 I/O 线程实现，不能将某版默认值套给所有版本。

## 为什么通常快，又会在哪里变慢

内存访问降低数据读取成本，合适的数据结构缩小处理范围，串行执行减少共享数据的并发协调。但一次大集合操作、长脚本或大响应仍要实际执行与传输。例如一次 `GET` 读取几 MB 的值，按 key 定位可能很快，搬运结果却并不便宜。

若两个客户端各自 `GET` 计数器后再 `SET`，即使命令逐条串行，仍可能交错为 A 读 0、B 读 0、A 写 1、B 写 1。需要用 `INCR` 或[[redis-atomic-operations|事务与脚本]]表达整个条件操作。

优化要对应成本：网络等待多时可批量与流水线；执行重时缩小单次操作、拆分数据；整体工作量过大时再考虑分片。增加 I/O 线程不能自动加速 Lua 中的长循环。

## 回答思路与追问

「Redis 为什么快」应沿内存、数据结构、事件驱动和执行成本回答，并保留大 key、慢命令、网络与磁盘竞争的边界。

追问：CPU 总使用率不高，为什么仍有单核瓶颈？打开 I/O 线程后为什么无改善？应看各线程的 CPU、命令耗时、网络吞吐与尾延迟，判断瓶颈是否在网络处理；不能只比较机器平均 CPU 或一个吞吐数字。
