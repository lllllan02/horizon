**Redis Cluster 将 key 映射到固定槽，再把槽分配给不同主节点，结合副本提供分片级接替。** 它扩展总容量和可分散的负载，但一个 key 仍由一个分片处理。

## key、槽与节点的关系

常规映射为 `CRC16(key) % 16384`。客户端先算槽，再查槽归属并直连节点；有效 hash tag 会让花括号中的部分参与计算，例如 `stock:{42}` 与 `dedup:{42}:req-7` 可共置于一槽。

这是固定槽的间接映射，与[[consistent-hashing|一致性哈希环]]不同。多 key 命令、事务与脚本通常要求同槽；同一节点上的不同槽也不满足同槽要求。Cluster 只支持数据库 0，逻辑数据库或 key 前缀也不构成资源与权限隔离。

## 扩容为何还要迁移

新节点起初没有原有数据，需要迁移部分槽及其 key。客户端映射可能落后，服务端通过重定向指导它重试：`MOVED` 表达槽归属变化，可更新映射；`ASK` 表达迁移中的临时目标，要先发送 `ASKING`，不应据此永久改写槽表。[[redis-cluster-docs#槽路由与迁移|Cluster 规范导读]]保留了这一过程的依据。

把整个业务都放在 `{shop}` 标签下能方便多 key 操作，却把工作集中到同一个槽。拆成不同标签能分散负载，又会失去跨标签的本地原子执行。选 key 结构时就需要明确原子操作的范围。

## 扩展与可用性的边界

集群的总吞吐不能直接推算为单 key 吞吐。热点商品读可以用本地缓存或请求合并减少 Redis 访问；热点写的分片计数则会改变聚合成本与一致性语义。

Cluster 也使用异步复制，故障切换可能丢失已确认写入；分区时能否继续服务还取决于可达主节点多数、槽覆盖、可用副本和相关配置。不能把它描述为「任意坏一半节点都可用」。

## 回答思路与追问

回答扩容时连起「重分槽 → 搬数据 → 客户端纠正路由 → 观察负载」，再说迁移对延迟的影响。

追问：三主集群加到六主，一个热门排行榜为何仍慢？先定位它是否仍是单个 ZSet，再评估读缓存、局部榜单与聚合成本；继续增加节点不改变这个 key 的归属粒度。涉及多 key 的库或任务框架也必须核对 Cluster 兼容性，不能只凭其使用 Redis 就认定支持。
