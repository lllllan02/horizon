**执行计划（Query Execution Plan）是数据库执行一条 SQL 时采用的操作安排，包括访问路径、连接顺序与算法，以及过滤、排序和聚合方式。** SQL 描述需要什么结果，同一结果可能有多种取数方法。

**优化器（Optimizer）是根据查询条件、可用索引和统计信息，比较候选计划并选择执行方案的组件。** MySQL 8.4 使用估算成本作选择，成本值不等于毫秒；[[mysql-index-access-cost|索引选择]]只是其中一部分，连接顺序和中间结果量同样影响总代价。

## EXPLAIN 能看见什么

普通 EXPLAIN 展示计划与估算，适合确认「准备怎样执行」。表格格式便于核对字段，TREE 格式用操作树表示数据流。

优化具体 SQL 时，按[[mysql-explain-reading|EXPLAIN 执行计划读法]]从执行结构、访问范围、过滤和重复次数定位多做的工作，再检查排序等后续处理与实际耗时。该篇保留全部 12 个字段的速查，并分别展开查询块类型、访问类型和 Extra 标记。

## 用实际执行检查估算

`EXPLAIN ANALYZE FORMAT=TREE` 会实际执行查询，补充各节点的实际输出行数、循环次数与时间。先对比同一节点的估算和实际，再判断工作量是否被低估。

估算明显失准时检查统计信息；`ANALYZE TABLE` 可更新索引统计，列直方图还需检查其更新设置。估算接近但处理量很大时，按[[mysql-query-optimization|查询优化]]减少工作；执行计划解释不了的等待，则进入[[mysql-slow-query|慢查询排查]]。

## 同一 SQL 为什么从快变慢

SQL 文本相同不代表输入与执行条件相同。先保留实际参数、数据规模、表结构与索引、相关版本和配置，以及能够取得的前后计划，再区分三种变化：

| 对比结果 | 下一步核对 | 处理方向 |
| --- | --- | --- |
| 计划相近，实际匹配行数或循环明显增加 | 参数选择性、热点值与数据增长 | 减少处理范围或重复工作；增加索引也不能消除必须返回的大量结果 |
| 访问路径或连接顺序变化，且估算与实际明显偏离 | 索引可用性、统计信息和数据分布 | 针对失准依据更新统计或评估索引，再比较实际结果与代价 |
| 实际工作量相近，耗时仍大幅波动 | 锁等待、缓存状态、CPU 与 I/O 竞争 | 沿慢查询排查取得运行时证据，计划变化不能解释全部延迟 |

假设按用户查订单，普通用户只有几十条，某个热点用户却有几十万条；规范化后属于同一个指纹，工作量仍可差几个数量级。比较时要分别保留这两类参数，不能只用普通用户证明查询已优化。

统计信息影响成本估算，列直方图与索引统计又是不同对象，更新行为与适用条件由[[mysql-manual-queries#怎样知道优化器实际选了什么|官方统计与计划说明]]解释。计划改变不自动意味着退化，强制旧索引也不保证适合新分布；应比较实际行数、循环、等待和请求延迟。示例为条件推演，未做计划回归实验。
