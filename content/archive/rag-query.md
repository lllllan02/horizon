**查询处理把用户的问题转换成数据源更容易执行的查询，并保留原始意图与约束。** 它可由确定性规则、模型或二者配合完成；不是每个问题都需要改写。

## 先确定缺的是表达还是事实

假设上一轮在讨论企业版 SSO，用户追问“改完后旧会话呢”。检索时可补齐指代为“企业版 SSO 配置修改后已有会话是否受影响”，但不应擅自补入一个用户未确认的产品版本。

| 问题形态 | 可用处理 | 需要防止的偏移 |
| --- | --- | --- |
| 代词、缩写、口语表达 | 带有限对话信息重写，保留原查询 | 把历史猜测变成当前事实 |
| 同一问题有多种说法 | 多查询并行召回再去重 | 放大相同偏差、增加成本 |
| 多个独立子问题 | 拆解后分别查，再合并证据 | 漏掉子问题或合并不兼容条件 |
| 后一步依赖前一步结果 | 先查中间实体，再查关系或规则 | 中间实体错误一路传播 |
| 数值统计或精确状态 | 路由到 SQL／业务 API | 用 top-k 文本代替完整计算 |

查询重写与补查可以放在程序定义的流程中，[[langchain-rag-architectures|混合架构]]不要求把全部决策交给模型。

## 什么时候使用假想文档？

问题短且与文档写法差异大时，[[rag-advanced-papers#HyDE：查询不像文档时怎么办？|HyDE]]用生成的假想文档作为检索表示。它可能帮助找到真实证据，也可能因虚构细节带偏检索；假想文本不能直接进入答案证据集合。

## 怎样限制失败传播？

保存原始问题、改写结果、路由与召回集合；硬约束如租户和权限由应用绑定，模型只能在允许范围内提出查询。对明确歧义可请求用户补充，对同义表达可保留原查询作为并行基线。比较新增查询是否带来必要证据，并为补查设置次数和时间预算。
