**评测设计是把用户目标转成可执行任务、可核验结果和明确的比较条件。** 数据集决定测哪些能力，评分规则决定什么算成功；两者都应先于调参确定。

假设一个订单 Agent 接到「退掉订单 A」的请求。只检查回复中是否有「退款成功」，会放过没有写入账本的情况；只检查账本有一笔退款，又会漏掉退错订单或未确认就执行的问题。

## 成功条件怎样写？

把同一任务分成四类要求，分别保留分数和证据：

| 维度 | 订单任务中的要求 | 证据 |
| --- | --- | --- |
| 结果 | 符合条件的 A 被正确退款 | 订单与退款账本 |
| 约束 | 获得所需确认，其他订单未改变 | 确认事件、写入记录与状态差异 |
| 交互 | 缺信息时补问；结果不明时不宣称成功 | 会话、工具返回与最终答复 |
| 效率 | 在约定资源内完成 | 墙钟时间、调用量、费用 |

硬约束应作为单独门槛，不能让语气、速度或其他高分抵消误操作。质量分数可用于比较已满足硬约束的结果；阈值来自业务要求和可承受风险，没有通用的「80 分即可上线」。

**评测单元（Task）是一项带输入、环境和验收条件的任务。**

**试次（Trial）是该任务的一次运行。** 同一任务跑十次增加了随机性证据，却没有增加十种业务情形。

## 一条样本需要保存什么？

[[tau-bench-evaluation|τ²-bench 的任务构造]]把初始化、可行解和验收分开。自建用例可以采用以下字段；这是示意格式，不是任何 SDK 的固定协议：

```json
{
  "id": "refund-confirmed",
  "input": "请为已经确认的订单 A 退款",
  "fixture": "orders-v1",
  "policy_version": "refund-v1",
  "expected": {"refund_order": "A", "new_entries": 1},
  "invariants": ["other_orders_unchanged", "confirmation_before_write"],
  "slice": "normal",
  "split": "regression"
}
```

参考输出可以是事实、状态谓词或评分标准，无须总是一段标准回复。初始数据可由工具查询，**「expected 和隐藏验收」不进入 Agent 输入**；运行器需要它们，但被测程序不应因此获知答案。

先验证参考解通过，再用「空操作、退错订单、重复退款、正确拒绝」检查评分器。任务本身无法完成、规则有歧义或缺少必要工具时，应先修复测试。

## 从哪里收集，怎样防止只会做熟题？

从真实任务、人工检查与已确认错例起步；合成样本补充稀缺边界，经审核后才能进入可信集合。[[agent-trace#在 Langfuse 排障并回归|Trace 错例回流]]保留来源，但还要恢复环境和补齐独立验收。

切片（Slice）是按共同条件划分的任务子集，例如正常退款、缺确认或工具超时。数据同时包含常见任务、困难任务、缺信息、越界请求、工具故障和合理拒绝。故障与攻击集用于暴露问题；若被刻意超采样，其平均分不能直接代表日常流量。

按用途分开开发集、回归集和保留测试集：开发集用于反复调试，回归集守住已修复问题，保留测试集检查未针对性优化的表现。按用户、会话、问题模板或时间分组切分，避免同一任务的改写散落到训练式调试和独立验证两侧。

[[langsmith-evaluation|数据集与实验管理]]可以保存这些版本，但代表性仍需自己检查。每次新增或修改标准答案，都生成可识别的数据版本；先在固定版本比较改动，再另报扩展集结果，避免把换题造成的分差说成能力变化。

## 线上出了一个错例，怎样变成能反复使用的评测？

一条“退错订单”的聊天记录还不够：当时账户里有哪些订单、用户此前确认了什么、工具返回什么，都可能决定正确行为。直接把最后一句话放进数据集，会制造一个与原故障不同的任务。

重建触发问题所需的最小初始状态，保留相关用户事件、工具契约和真实预期，去掉无关敏感信息。验收同时检查应发生与不应发生的效果，例如 B 被处理而 A 保持不变；若故障依赖旧查询晚到，还要保存事件顺序，而不只是输入文字。

新增用例后，先确认它能识别原失败，也能接受合理的正确路径。否则可能只是在匹配某句回复或某条固定调用链。错例集用于防复发，代表性样本用于判断整体质量，两者分开报告。
