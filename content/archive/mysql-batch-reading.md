**分批读取是把大结果集拆成多次有界查询、逐批处理的读取方式。** 大 LIMIT 真正要求返回大量数据，主要要控制单次查询、传输与应用处理的资源占用；它与大 OFFSET 丢弃大量结果的问题不同。

## 按键分批，避免不断增加 OFFSET

假设 orders 的 id 是不会修改的正整数主键，任务只需按 id 升序导出。首批令 last_id 为 0，后续每批使用上次成功处理的最后一个 id：

```sql
SELECT id, created_at, amount
FROM orders
WHERE id > :last_id
ORDER BY id
LIMIT 1000;
```

`:last_id` 表示应用绑定参数，具体占位符语法由驱动决定。每批处理并持久化输出后，记录进度，再继续读取，空批次时结束。这是[[mysql-index-pagination|游标分页]]用于遍历的方式，不会像 OFFSET 逐批增长那样反复扫描前面已处理的记录。1000 只是示例，应按行宽、耗时和资源限制调整。

输出已成功但进度未记录就崩溃时，重试可能重复输出；可用稳定记录标识去重，或让输出与进度提交具备一致性。索引减少重复扫描，不能免除导出全部数据本身的成本。

## 流式读取，避免客户端缓存整个结果

**流式读取是客户端逐步接收并消费结果、而不先缓存整个结果集的读取方式。** 它可以用于单次大查询，也可以用于每批查询；与分批控制的是不同环节。

[[mysql-manual-queries#分页与结果读取|MySQL C API 的非缓冲读取]]通过逐行获取降低客户端内存占用；实际项目应核对驱动是否默认全量缓冲。边读边写文件，避免最后又把所有记录攒进列表。流式读取仍需传输全部结果，也不保证服务端无需排序或临时表；消费慢时连接会被持续占用。

交互列表可限制单页数量；确需大批量导出时，可把任务转为后台执行并提供进度与下载结果。这是处理时长与资源占用的应用设计，不是数据库自动减少工作量。

## 明确导出的数据范围

任务启动时记录 max_id，并增加 `id <= :max_id`，可以限定键范围，但不能冻结已有记录的修改、删除，也不排除较小 ID 的事务稍后提交。逐批独立事务读取，可能得到不同时刻的数据。

需要同一时点的视图时，可在 InnoDB REPEATABLE READ 的同一事务中使用一致性读；长时间保持快照会延长历史版本保留，应评估任务时长。只冻结 ID 列表仅固定成员，若字段值也要求固定，需要保存相应结果或使用合适的快照方案。

这些方案依据范围读取、非缓冲结果与一致性读规则推导，示例未运行性能测试；批大小、内存峰值、断点恢复和一致性都需按实际任务验证。
