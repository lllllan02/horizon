**记忆整合（Memory Consolidation）是比较多条已有记录，形成更易复用的概括、关联或当前认识的处理过程。** 它减少以后逐条重读的工作，同时需要保留推导依据，避免越概括越偏离原意。

单条[[agent-memory#写入|记忆写入]]解决本次信息怎样保存；整合还要判断多次经历合起来能说明什么。两者可以在同一任务中执行，不必部署成两个服务。

## 摘要、关联和归纳分别改变什么？

| 操作 | 结果 | 收益与边界 |
| --- | --- | --- |
| 摘要 | 同一段历史的简短表示 | **「减少读取量」**；可能遗漏条件，不能替代全部原文 |
| 建立关联 | 保留独立记录，补充彼此的联系 | **「补足跨条目线索」**；相近措辞不能证明因果 |
| 归纳 | 多条观察支持的较高层判断 | **「减少反复推导」**；推断必须与直接事实分开 |
| 纠正或失效 | 改变当前有效的结论 | **「停止沿用旧认识」**；要核对范围、时间与依据 |

[[generative-agents-memory|Generative Agents]]从经历生成问题，再查证据形成带来源指针的反思；[[a-mem-memory|A-Mem]]则让新条目补充关联，并改变旧条目的检索描述。这两种机制可分别用于「提前形成认识」和「让相关材料以后更容易找全」。

## 怎样避免把局部事实整合成错误规则？

假设记录 A 是「项目甲的示例使用 Go」，B 是「项目乙使用 Python」。正确整合应保留两个项目范围；「用户总是偏好 Go」没有得到共同支持。后来 C 明确说项目甲改用 Python，只改变甲的当前事实，不能把乙当成纠正证据。

可采用以下处理顺序：

「取同一范围的候选 → 回读来源及有效状态 → 模型提出摘要或关联 → 程序校验引用和版本 → 保存派生记录 → 更新检索入口」。

程序能检查 ID、权限和版本，但不能仅凭字段合法证明归纳正确。模型还应标明哪些是原话、哪些是推断；冲突不明时保留分歧，重要推断用后续反馈核实。

## 原始记录为什么还需要保留关系？

可把证据看作原记录，摘要与归纳看作派生视图。派生记录至少能回到所依赖的来源及版本；来源纠正或删除后，相关摘要需要重新计算、失效或删除，具体传播由[[agent-memory-maintenance|记忆维护]]处理。

归纳结果重新成为输入时，尤其要防止「重复出现」被误认为多份独立证据。一个错误摘要被三处引用，仍只有同一条证据来源。

工程上可在任务完成、明确纠正或候选累积到一定规模时触发整合。若每天全库重写只增加成本，却没有减少重复、改善召回或纠正错误，就应缩小处理范围。验收要同时看压缩后的任务表现、条件遗漏及证据可追溯性。

## 多条经历怎样才能支持一条通用经验？

三个任务都通过重试恢复，整合器可能归纳为“请求失败就重试”。但其中可能都是只读查询，不能推广到扣款、发信或发布操作；重复出现的结论也可能都来自同一条错误来源。

整合时保留成功所依赖的条件、失败反例和来源独立性，把经验写成有适用范围的候选做法。先限定到已验证场景，再通过新任务扩大范围，不把频次直接当成可信度。不同项目的规则应保持范围，不能为了减少条目合成一个全局偏好。

合并后仍要知道结论依赖哪些原始记录。某个来源被纠正或删除时，重新检查相关摘要与经验；否则主记录虽然已更新，派生结论仍会持续传播旧错误。
