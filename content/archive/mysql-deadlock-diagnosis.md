**死锁（Deadlock）是多个事务持有资源、又相互等待对方释放资源，形成等待环而无法继续的状态。** InnoDB 默认检测到死锁后会回滚其中一个事务，让其他事务继续；排查的目标是还原等待环，找出哪些业务操作和访问路径造成冲突，再减少冲突并正确处理失败。

以下以 MySQL 8.4 InnoDB 为准，诊断接口也适用于常见 MySQL 8.0 环境，实际使用前核对版本、权限与采集配置。机制和公开案例依据保存在[[mysql-deadlock-reading|官方手册与 Percona 排障导读]]；本篇将其组织为处理步骤，未执行数据库并发实验。

## 先确认错误与影响

先看应用原始错误码、发生时间、接口、业务键和重试结果，再判断是否仍有请求阻塞。

| 现象 | 判断与处理边界 |
| --- | --- |
| `1213 / SQLSTATE 40001` | 常见 InnoDB 死锁错误；被选中的整个事务已回滚，需要重新开始事务 |
| `1205 / Lock wait timeout exceeded` | 等待锁超时，不证明存在等待环；默认只回滚当前语句，原事务可能仍持锁 |
| SQL 一直等待、尚无错误 | 先查当前阻塞关系；也可能涉及元数据锁等其他等待，不能直接叫死锁 |

死锁往往已经被引擎解除，应保留现场并修复重复触发的路径。高峰期若业务持续失败，可先降低冲突入口的并发或暂停重叠批任务；这只是减少竞争。仍有长事务阻塞时，再核对业务后决定回滚或终止连接。`KILL QUERY` 只停止当前语句，不保证结束事务；连接终止后的回滚和清理也可能需要时间。

## 保存证据，再补齐事务历史

1. 保存 [[mysql-innodb-status|SHOW ENGINE INNODB STATUS]] 的完整输出，定位 `LATEST DETECTED DEADLOCK` 并核对时间。它只有最近一次死锁报告，不能假定对应当前这次应用错误。
2. 反复发生且报告容易被覆盖时，记录原配置，在排查窗口开启 `SET GLOBAL innodb_print_all_deadlocks = ON`，从错误日志保留报告，结束后恢复原配置。这需要相应管理权限。
3. 同时记录表结构、主键／二级索引、外键、SQL 参数、相关事务的隔离级别、事务边界及执行计划。`SHOW CREATE TABLE` 与普通 `EXPLAIN` 用于核对结构和访问路径；诊断连接的隔离级别不能代表发生故障的业务连接。
4. 仍在等待时，先查 `sys.innodb_lock_waits` 找等待连接和阻塞连接，再关联 `performance_schema.data_lock_waits`、`data_locks` 看锁对象与模式，结合 `INFORMATION_SCHEMA.INNODB_TRX` 看事务持续时间。[[assets/mysql-deadlock-diagnostics.sql|诊断查询]]按这些步骤组织，需按现场选择执行；当前等待为空不能推翻历史死锁。
5. 用报告中的连接 ID、时间和应用 Trace 找回该事务从开始到失败的操作。已有采集可补查 `events_statements_history`，但历史会覆盖，连接退出也会丢失；连接池复用时要区分多次事务。Binlog 无法补回被回滚事务的完整 SQL 历史。

**「当前 SQL 不等于取得锁的那条 SQL。」** 前面的更新可能已经持锁，最后一条只是触发等待；阻塞连接即使处于空闲状态，`blocking_query` 为 NULL，也可能仍有未提交事务。只有把持锁来源接回业务代码，才能决定应修改哪一处。

## 把报告还原为等待环

逐个事务整理「已经持有什么锁 → 请求什么锁 → 被谁阻塞」，对照 `HOLDS THE LOCK(S)`、`WAITING FOR THIS LOCK TO BE GRANTED` 和回滚结果。核对的是表、索引、记录或间隙及锁模式，不能只比较两条 SQL 的文本。

[[mysql-deadlock-reading#官方示例：怎样从报告还原等待环|官方双会话示例]]中，A 先持有 Animals 记录的共享锁，再请求 Birds 的排他锁；B 的持有与请求方向相反。两条等待边连成环后，统一两个事务的访问顺序才有明确的修复依据。复杂场景可能涉及更多事务，不能预设永远只有两方。

锁范围按实际访问路径判断：记录锁保护索引记录，间隙锁阻止向间隙插入，临键锁同时保护记录及其前方间隙。RR 下范围搜索可能锁住超出最终命中行的范围；二级索引排他访问还会涉及聚簇记录，唯一键和外键检查也可能参与。因此，WHERE 看似只针对一行、甚至只有一条 INSERT，都不能据此排除死锁。表上的 IX 是意向锁，也不能直接解释成整表独占。

## 根据环上的原因选择修复

| 证据指向 | 改动及其作用 | 需要保留的边界 |
| --- | --- | --- |
| 相同资源以相反顺序访问 | 统一跨表、跨行顺序；多账户操作可按稳定主键顺序逐条锁定，再修改，减少形成环的机会 | 所有相关入口都要遵守；仅排序 `IN` 参数不能作为实际加锁顺序的证据 |
| 计划扫描过多记录或范围 | 根据过滤条件和实际计划设计合适的[[database-index\|索引]]、缩小搜索范围，减少接触的锁对象 | 无索引导致广泛记录锁，不宜说成「行锁自动升级为表锁」；新索引还会增加写入维护成本 |
| 事务持锁期间夹杂 RPC、等待或大量计算 | 将无关工作移出事务，及时提交／回滚；允许部分提交的批任务可分批，缩短持锁时间 | 不能把必须共同生效的[[transaction\|事务]]操作随意拆开 |
| 不必要的锁定读，或先 S 后升级 X | 允许快照时使用普通读；确实需要先读后改时，评估直接 `FOR UPDATE`，避免双方先共享再升级 | 必须保留业务所需的并发保护，不能直接删锁 |
| RR 范围锁与插入冲突 | 先优化范围；业务允许时评估 RC，减少搜索／扫描中的间隙锁 | RC 改变快照语义，外键与重复键检查仍有间隙锁例外，记录锁死锁也仍可能发生 |
| 同一热点被大量并发事务访问 | 按业务键限制并发或串行处理；必要时调整热点数据设计，减少同时争抢 | 串行规则要覆盖全部写入口，并评估吞吐与排队延迟 |

调大 `innodb_lock_wait_timeout` 不会解开等待环；死锁检测开启时，也不能靠它避免检测后的回滚。关闭 `innodb_deadlock_detect` 只适合确认检测成本成为瓶颈后评估，会改为依赖超时等机制恢复。两者都不能代替上表中的原因定位。

## 重试与验收一起完成

重试是失败恢复的一部分。收到 1213 后，重新开启事务，重新读取和判断，再执行完整业务并提交；不能在旧事务中只重发最后一条 SQL。收到 1205 时，若应用决定整笔重试，应先明确回滚原事务，避免遗留锁。限制尝试次数与总时限，并采用带随机扰动的退避；具体等待与停止原则沿用[[retry-decision|错误分类与重试决策]]。

数据库回滚只覆盖事务内的数据库修改。事务中已经发出的扣款或消息不随之撤销，重试前要确认[[idempotency|外部副作用的幂等与结果核查]]；提交时断连、结果未知也应先核查，不能当成明确死锁回滚处理。

验证先用相同版本、表结构、隔离级别和数据构造交错执行，确认修改前能形成原等待环，修改后该环被打断，并核对业务最终状态。再以相近负载比较死锁计数增量、每单位业务请求的死锁比例、重试耗尽率、事务耗时及吞吐，防止仅靠降吞吐或无限重试让报错减少。可查询 `INNODB_METRICS` 中 `NAME = 'lock_deadlocks'` 的计数，在同一统计窗口比较增量，并确认计数器启用、没有跨重启或重置。

这些是验证方法，尚未在具体业务或 MySQL 实例中实测；某次未复现也不足以证明所有路径都不再死锁。
