**数据类型决定能执行什么操作，底层编码决定怎样花费内存和 CPU。** 选型先看访问方式，再看规模与操作成本；同为 Hash，几项短字段和几十万项长字段的内存布局可能不同。

## 按访问方式选择类型

| 需求 | 合适的起点 | 需要解释的边界 |
| --- | --- | --- |
| 整体读写商品详情、计数 | String：`GET/SET/INCR` | JSON 字符串修改字段通常需整体读改写；`INCR` 超时重试可能重复增加 |
| 频繁读取或修改对象字段 | Hash：`HGET/HSET` | 一个大 Hash 仍是一个 key；7.2 中字段不能独立设 TTL |
| 两端进出、简单待办列表 | List：`LPUSH/RPOP` | 弹出即移除，处理崩溃的恢复要另加协议 |
| 去重与成员关系 | Set：`SADD/SISMEMBER` | 全量取出或大集合运算仍有成本 |
| 排行榜、按分数取区间 | Sorted Set（有序集合，ZSet） | member 唯一；分数相同还需约定业务排序规则 |
| 保留事件并分组消费 | Stream | 消费确认、失败接管与裁剪需一起设计，见[[redis-streams\|消息处理]] |

Bitmap 适合稠密编号的布尔状态；编号很稀疏时，按最大偏移分配空间可能浪费内存。HyperLogLog 适合允许误差的去重计数，不能还原成员列表。GEO 用于位置索引。它们的 API 能力与内部 Redis 类型不必一一对应；[[redis-data-model-docs|官方数据模型与实现导读]]保留了对应依据。

## 为什么同一类型需要不同编码

为每个小字段都维护指针和哈希节点，结构开销可能大于实际数据。紧凑编码把内容放得更连续，以少量线性查找换取更低内存开销；对象变大后，继续线性扫描或搬移就不划算，需要转换结构。

以 7.2 系列为例：

- String 可采用 `int`、`embstr`、`raw` 等编码。SDS（Simple Dynamic String，简单动态字符串）记录长度与容量，能处理含零字节的内容，取长度无需扫描到字符串结束符；追加时仍可能扩容与复制。
- Hash 小对象可用 listpack，大对象使用哈希表；Set 可按条件使用 intset、listpack 或哈希表。listpack 记录元素自身的长度信息，避免旧 ziplist 的前项长度字段变化引发连锁更新。
- List 在该基线中可用 listpack 或 quicklist；quicklist 把多个紧凑块组织为链表，兼顾两端操作和局部空间利用。不能将旧资料中的「双向链表」直接当作当前完整实现。
- ZSet 小对象可用 listpack；一般编码组合字典与跳表（skip list）：字典按成员找分数，跳表按分数定位并遍历范围，层间跨度还支持排名计算。一次返回 M 项仍要付出输出 M 项的成本。

底层字典扩容还可能采用渐进式 rehash：新旧表短暂共存，分批迁移桶，查找兼顾两张表，新条目进入新表。它分摊集中迁移的停顿，但仍有额外 CPU 和内存开销。

## 怎样回答与验证

回答「为什么排行榜用 ZSet」时，先给出按成员更新、按分数取区间这两个需求，再解释两套结构如何配合；不能用「跳表比所有树都快」替代具体取舍。

追问可以改成：排行榜只需 Top 100，为什么还要保留所有成员？一次取几十万条会慢在哪里？商品字段增多后 Hash 变大，是否仍比 JSON String 合适？判断取决于完整榜单需求、更新方式与实际对象大小。

验证时观察 `TYPE`、`OBJECT ENCODING` 和 `MEMORY USAGE`，在相同数据上比较操作延迟与内存。编码阈值取决于版本、配置和内容；Redis 7.4 起已有 Hash 字段过期命令，不能把 7.2 的限制泛化到所有版本。本篇未执行基准测试。
