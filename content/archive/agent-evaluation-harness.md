**Evaluation Harness 是组织任务初始化、被测 Agent 执行、证据采集、评分和汇总的运行系统。** [[agent-harness|Agent Harness]]负责完成任务；评测运行系统负责在明确条件下检验它。

没有这层编排，手工试几次容易混用环境、漏记失败或把测试答案交给 Agent。最小链路是「加载任务 → 创建独立环境 → 运行 Agent → 冻结证据 → 评分 → 保存结果 → 清理」。

## 谁能看到哪些数据？

| 组件 | 输入与职责 | 边界 |
| --- | --- | --- |
| 任务加载器 | 读取输入、环境配置、验收标准 | 给 Agent 的输入和给评分器的答案分开 |
| 环境管理器 | 从初始环境数据（Fixture）创建状态，提供工具 | 每个 trial 独立；外部写操作不能共享生产目标 |
| Agent 适配器 | 用真实产品入口执行任务 | 不为提高分数偷换更强工具或隐藏提示 |
| 证据采集器 | 保存消息、动作、状态和用量 | 以工具侧记录核对副作用，不能只信自述 |
| 评分器与汇总器 | 独立评分，归约为任务和切片指标 | 失败、缺失、取消分别记录 |

[[inspect-agent-evaluation|Inspect]]提供任务、执行器、评分器和沙箱组件；[[harbor-evaluation|Harbor]]把环境与验收封装为任务包。两者能减少基础编排，但业务数据和检查条件仍需自己提供。

## 模拟工具还是连接真实服务？

| 环境 | 收益 | 不能证明什么 |
| --- | --- | --- |
| 固定或有状态模拟工具 | 便宜、可控，便于注入故障 | 真实协议、延迟和服务集成正确 |
| 容器、数据库或应用快照 | 能检查真实实现与状态变化 | 外部线上环境完全等价 |
| 独立测试账号与服务 | 覆盖真实集成链路 | 完全可复现，且通常成本更高 |

模拟工具应按参数和当前状态返回，不能按「第几次调用」喂旧响应。既要恢复数据库，也要处理文件、缓存、记忆、检索索引和模拟用户状态；有意测试跨会话记忆时，在一个场景内部保留状态，在场景之间隔离。

## 怎样保证比较条件可追溯？

每次运行保存任务版本、Agent 代码与提示版本、模型配置、工具 schema、环境镜像或 fixture、评分器版本和资源限额。随机种子可以帮助复现部分组件，不能保证远程模型完全确定。

[[agent-evaluation-infrastructure|资源限制实验]]表明 CPU、内存与执行限制方式会影响结果。并发度既改变吞吐，也可能引入限流和资源争用，应作为实验配置记录。预算耗尽如何评分须事先说明，避免看到失败后无限补跑。

## 重跑、重放与重新评分有何区别？

重新评分只读取旧输出和证据，适合修复裁判；重新执行会调用 Agent 并生成新轨迹；重放固定工具响应则只覆盖被保留的环境行为。三者要用不同操作记录，不能把新评分写成新成功尝试。

评分器、参考解和奖励文件也需要隔离。若被测 Agent 可修改验收程序或直接写最终分数，就可能绕开任务。读取终态后从受保护的位置执行检查，清理失败也保留结果状态。受控环境并不自动提供这些保证。

## 为什么同一用例第二次运行更容易通过？

第一次创建的文件、修改的订单、写入的记忆或热缓存影响了第二次。评测环境没有恢复到规定初态，就把学习效果、缓存效果和状态污染混在一起。

每个试次创建独立数据范围，明确哪些缓存允许复用，结束后清理副作用并核对初态。需要测跨会话记忆时，把整个会话序列作为一个试次，在试次之间隔离；不能一边清空记忆一边声称验证了长期能力。

外部服务难以重置时，使用隔离账号、测试资源或受控替身，并说明替身没有覆盖的行为。失败后保留足够的诊断产物，但不能让这些产物意外成为下一次的提示。环境故障和 Agent 失败分别记录，才能判断分数变化是否来自被测系统。
