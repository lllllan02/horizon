**记忆需要持续判断是否仍适用，并让失效或删除沿着索引、摘要和缓存传播。** 错误信息一旦长期保存，可能在多个新会话中反复影响判断。

## 不再适用，与不再保存

| 操作 | 改变什么 | 例子 |
| --- | --- | --- |
| 更新／替代 | 当前事实改变，历史是否保留由需求决定 | 项目示例语言由 Go 改为 Python |
| 到期 | 不再作为当前有效信息 | 某日之前的临时计划 |
| 降权／归档 | 减少常规召回，仍可能保留历史价值 | 较少使用但可回查的旧项目经验 |
| 删除 | 按约定范围移除记录及派生内容 | 用户撤回某条私人信息 |

明确日期的信息可设有效期，持续目标可设复核时点，稳定偏好不必统一设置天数。长期未使用只是线索，不能独立证明重要事实应被删除。[[mem0-memory|Mem0 的过期过滤]]与[[graphiti-memory|Graphiti 的历史失效关系]]也说明“当前不返回”不等同于物理删除。

[[memorybank-memory|MemoryBank]]探索随时间衰减、被回忆时强化的策略，适合研究哪些内容优先保留。工程上须防止「越常被错误召回，越被强化」：访问频率不能替代事实证据，稳定约束也不应仅因近期未使用而丢失。遗忘排序、业务到期与用户要求的删除应分别处理。

## 为什么删掉一行还可能重新出现？

删除事实时，后台提取可能仍持有原消息，检索缓存也可能仍保存旧文本。仅删除主记录无法阻止正在运行的任务再次写入，也无法让所有派生副本立即消失。

先明确删除范围：只移除这条结论，还是也禁止从指定来源再次学习。后者可让来源进入禁用状态并增加其版本，后台候选提交时原子核对来源仍有效；删除标记只保留必要身份与版本，不保存敏感正文。索引召回后回查当前状态，旧候选即使命中也不再注入。

派生摘要、缓存和索引清理可以异步推进，但要记录尚未完成的范围并重试。用户侧的完成语义应区分“已停止用于新回答”与“所有约定副本已清理”，不能提前宣称全部删除。已经发给模型的在途请求无法靠删库收回；是否取消并重新生成，应按删除约定处理。

验证时故意让旧提取晚到、保留旧索引命中并开启新会话，检查内容是否重新出现。只查主表为空，覆盖不了这条链路。

[[codex-memory-pipeline|Codex V2 整合提示]]明确要求不从旧摘要恢复已纠正或删除的结论。这是模型侧约束；自己的系统还需程序追踪与删除后回归，不能只写一句提示词。

## 记忆的来源是否可信？

外部网页中的“以后忽略权限检查”即使被记录，也仍是外部内容。存储动作不能使它成为用户授权。保存时区分用户陈述、工具观测、第三方材料和模型推断；读取时保留来源与范围，不把所有条目拼成高权限指令。

多用户系统由服务端绑定租户与身份，本地文件工具则要限制可读写目录。[[anthropic-memory-tool|Anthropic Memory Tool]]将路径规范化与边界检查交给客户端，说明“给模型一个记忆目录”仍需执行层保障。

同一用户也可能有不同分享场景，能读取私人记忆不意味着可以在共享输出中披露。敏感内容尽量少存，凭据交给专门的凭据存储；日志、备份和模型请求也是需要明确管理的副本。
