**评测报告应同时说明任务覆盖、重复次数、分母和不确定性。** 单次成功说明这次做成了，平均分提高也可能来自采样波动、环境变化或特定切片的退化被掩盖。

## 多次运行究竟测什么？

[[anthropic-agent-evals-summary|Agent 评测方法]]区分两种问题：`pass@k` 衡量 k 次中至少一次成功，`pass^k` 衡量 k 次全部成功。前者接近多次寻找可用解，后者关注重复服务的稳定性。

对同一任务，若各次独立且成功概率固定为 p，则至少一次成功概率为 `1-(1-p)^k`，全部成功为 `p^k`。这是数学模型，不是对真实调用独立性的保证。不同任务难度不同，应先按任务计算再平均，不能把全库平均成功率直接代入幂函数。

有 n 次独立同分布试次、其中 c 次成功时，可用组合计数估计：

- `pass@k = 1 - C(n-c,k) / C(n,k)`。
- `pass^k = C(c,k) / C(n,k)`。

这里 `n ≥ k`，可选成功或失败数不足 k 时，相应组合数为 0。它们来自从已有试次选择 k 个的组合计数。报告应说明用的是该估计、固定 k 次的实测比例，还是单次成功率；不能只写「通过率」。

多试一次还增加时间、费用和重复副作用风险。只有能可靠识别成功结果，并且允许多次尝试，pass@k 才能对应实际产品收益。

## 新旧版本怎样公平比较？

基线（Baseline）是作为对照的已有方案。除了现有 Agent，也可保留能完成同类任务的简单工作流，判断新增自主决策是否带来足够收益；用理想证据作诊断对照时，则不能把它当成可部署产品。

让 A、B 处理相同任务和独立初始化的环境，固定评分、模型配置及预算；若比较完整系统，可以允许各自策略不同，但需明确比较的是系统组合。交错运行版本，减少日期、服务负载与缓存差异的影响。

按任务记录差值：哪些从失败变成功，哪些反向退化，哪些不变。相同任务上做配对比较比只看两个孤立均值更能利用共同难度信息；根因判断还需局部消融和轨迹核对。

[[inspect-agent-evaluation|Inspect 的统计组件]]支持置信区间与聚类处理。对独立二元样本可使用 Wilson 区间；对重复试次、同一会话或模板派生的数据，应保留组内关联。配对自助法（Paired Bootstrap）可按任务或来源组重采样，并始终把 A、B 配对保留，估计平均差值的区间。这是面向这种数据结构的统计设计，不是保证显著的公式。

## 分母与切片怎样报告？

同时报告计划运行数、实际执行数、可评分数、通过数，以及设施错误和预算失败。把结果限定为「可评分样本成功率」时，也要显示评分覆盖率；如果错误集中在困难任务，排除它们会产生选择偏差。

切片按预先定义的维度划分，例如正常退款、缺确认、重复请求和超时恢复。总分改善但未确认写入变多，仍可能不满足发布要求。样本数量不同的类别，宏平均强调类别等权，按流量加权强调预计线上分布，含义应分别说明。

## 质量与成本如何一起比较？

完整任务的墙钟时间从接收请求到产生可用结果，不能只累计模型耗时；并行分支的时长不能简单相加。另报中位数和尾部延迟，并说明超时任务如何计入；只看成功任务的延迟会漏掉慢到失败的请求。

费用包含全部模型轮次、工具、重试、记忆后台处理和必要计算资源。开发阶段的评分器费用可单列，避免混入产品单次执行成本；若线上每次运行都依赖裁判，其费用又属于服务成本。

「成功任务平均执行费用」只看成功样本；「单位成功交付成本」则是全部尝试费用除以成功交付数，包含失败损耗，两者不能混称。没有成功交付时不报一个虚假的有限值。比较策略时可固定预算看成功率，或在同等质量要求下比较费用与延迟，不凭 Token 变少就宣布优化。

## 多少样本才够？

没有固定通用数量。预期差异越小、任务差异越大，通常需要更多独立任务；想判断同一任务是否稳定，则需要重复试次。先试运行估计波动，再按希望检测的改善幅度规划规模。

反复试提示、不断查看保留集再挑最高分，会把保留集变成开发集。事先确定主要指标、比较对象和停止规则；探索性结果另报，并用未反复使用的数据确认。即使统计差异明确，仍要判断收益是否足以抵消新增费用和延迟。
