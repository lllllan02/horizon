**行为约束通过执行前后的检查点落实：检查器返回判定，运行程序决定是否调用工具、怎样处理结果以及能否继续。** 只记录违规或提醒模型，不能保证动作被阻止。

## 检查应该接在哪里？

Agent Loop 通常把模型提出的工具名与参数交给执行器，再将结果送回模型。如果执行器直接调用退款服务，提示词中的「不得超额退款」就没有独立的执行保障。

[[langchain-guardrails-summary|LangChain 的中间件机制]]提供一种接入方式：用包装器接收请求和后续执行函数，检查通过才调用后者。输入过滤与最终回答检查则接在各自的数据出口。

| 检查点 | 能看到什么 | 能控制什么 |
| --- | --- | --- |
| 输入进入模型前 | 用户请求、待传入的资料 | 拒绝超出职责的请求，移除不必传入的敏感字段 |
| 工具执行前 | 确定的工具、参数及服务端上下文 | 不调用工具，或暂停等待缺失的批准 |
| 工具结果进入模型前 | 工具实际返回的数据 | 筛除内部字段、脱敏；不撤销已发生的操作 |
| 最终回答交付前 | 候选回答、可核对的执行结果 | 拦下泄露信息或错误承诺的回答 |

入口必须覆盖实际执行路径。[[claude-permissions-summary|Claude SDK 的权限回调顺序]]说明，某些自动批准路径会跳过审批回调；必须逐次执行的检查不能只放在这类回调里。

## 一次退款需要哪些输入？

以下是自拟业务示例：用户申请退还订单 A123 的 800 元；同一退款申请超过 500 元需主管批准，拆成多次调用不免除审批。门槛仅用于解释机制。

模型提供订单号、申请标识和金额。执行器解析参数后，从可信系统取得当前用户、订单归属、剩余可退金额、申请总额与审批记录；不能接受模型自报的身份、额度或「已批准」。匹配原则由[[tool-permissions|权限规则设计]]展开。

同一个调用可能得到不同处理结果：

| 条件 | 判定与后续动作 |
| --- | --- |
| 金额格式错误或不为正 | 返回参数错误，允许有限纠正后重新校验 |
| 订单或退款申请不属于当前用户，或金额超出可退范围 | 拒绝调用，不进入审批来覆盖禁止项 |
| 需要审批但没有匹配的有效批准 | 保存待处理调用，暂停；恢复时重新检查 |
| 查询订单或审批系统超时，无法完成必要核验 | 保持未执行，记录「检查失败」，不能当作通过或业务拒绝 |
| 全部条件满足 | 调用退款服务，保留真实执行状态 |

语义检测器也应向运行程序交回明确结果，例如允许、拒绝或无法判定，附带规则与理由。它可以发现可疑输入，但不能替代上述身份和金额校验；检查器报错与「检测到违规」也应分别记录。

## 程序怎样保证未通过就不调用？

下面是执行器中的 Go 风格伪代码，展示自建工具入口的控制分支，不是某个 SDK 的现成接口，未运行。`rt` 由服务端注入，提供认证身份、查询服务、审批存储与退款服务；Agent Loop 将模型调用交给此函数，把返回状态写回任务。

```go
func DispatchRefund(rt Runtime, call Call) Outcome {
    req, err := ParseRefund(call.Args) // 金额按分，校验类型及正数
    if err != nil {
        return InvalidArguments(err)
    }
    facts, err := rt.LoadRefundFacts(req) // 订单、申请、可退余额
    if err != nil {
        return CheckFailed("无法核验退款条件")
    }
    if facts.OrderOwner != rt.UserID || facts.RequestOwner != rt.UserID {
        return Denied("资源不属于当前用户")
    }
    if req.Amount > facts.Refundable {
        return Denied("超出可退范围")
    }
    if facts.RequestTotal > 50000 {
        approved, err := rt.CheckApproval(call)
        if err != nil {
            return CheckFailed("无法核验审批状态")
        }
        if !approved {
            return PauseForApproval(call)
        }
    }
    if !rt.ReserveBudget(call) {
        return Stopped("预算不足")
    }
    return rt.Refund.ExecuteChecked(rt.UserID, req)
}
```

`CheckApproval` 按[[tool-approvals|工具审批流程]]核对服务端保存的审批者权限、动作及参数、有效期和使用状态。批准后仍从检查入口继续，不能直接跳到最后一行。

`ExecuteChecked` 是退款服务的业务边界：重新核对申请与订单的关联、当前授权和可退金额，并防止并发超退与重复退款。执行器的预检查无法替代这些服务端保证，因为检查后记录仍可能变化。返回值应区分成功、失败与结果待确认；网络响应丢失时，不能把整段代码直接重跑当作安全重试。

## 能否边检查边执行，以减少等待？

[[openai-guardrails-summary|OpenAI SDK 的输入检查]]允许与 Agent 并行，以减少等待；代价是拒绝结果返回前，模型甚至工具可能已经执行。因此，并行检查适合什么场景，取决于提前开展的工作能否接受。必要授权和业务检查必须在退款发生前完成。

结果检查也有同样的时间边界：退款后拦下回答，不会撤销退款。若要求未经检查的内容不能展示，应用需要先缓冲待检查的输出，再发布通过的内容；已经推送的流式片段不能靠最终拒绝收回。具体 SDK 的流式检查范围需另行核对。

## 被拦截后怎样继续，怎样验证？

参数错误可进入有限的[[agent-self-correction|纠正]]；敏感字段可按规则脱敏后再检查；明确拒绝则结束该动作或转向获准方案。必要检查不可用时，本例暂停退款，但可保留不依赖该检查的查询。未回复不算批准，换工具或拆单也不能绕过原规则。

次数、期限与费用由运行程序计数并限制；并发调用还需避免同时占用同一份剩余预算。停止继续调度不等于取消正在运行的工具，工具自身仍需超时或取消机制。

用[[agent-trace|Trace]]关联调用、检查判定、审批与实际结果，敏感字段按需脱敏。最小验收既要确认合法调用成功，也要核对拒绝和检查故障时退款服务未被调用，并覆盖审批后条件变化、重复提交与结果未知。安全与鲁棒性的验收沿用[[agent-evaluation#任务与验收|评测设计]]，不能只凭最终回复含有「拒绝」就认定约束生效。
