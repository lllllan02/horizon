这份岗位围绕「**面向视频自动化业务，开发可复用、可观测的 Agent 运行与交互能力**」展开。准备重点是把任务拆解、工具组件、对话体验和后端系统连接起来，说明一次任务怎样执行、失败后怎样处理，以及如何判断交付效果。

依据为 2026-10-20 保存的[引力传媒后端开发工程师-Agent JD](https://www.zhipin.com/job_detail/997249a47f8e928e0nx409u_FFtQ.html)，本地原件为 `content/sources/「后端开发工程师-Agent招聘」_引力传媒招聘-BOSS直聘.md`。已核对职位职责、任职资格和优先条件；以下问题、顺序与完成证据是准备建议，不是公司真实考纲。薪资、公司介绍等信息只代表本地剪藏，未核实当前招聘状态。

## 要求性质与准备顺序

正文任职资格要求计算机相关专业本科及以上、1 年以上后端研发经验；页面概要却写「经验不限」，年限需向招聘方确认。页面标示杭州、20–40K·14 薪，地址为余杭区鼎创财富中心 B1 幢 6 层。

Golang、MySQL、Spring 出现在页面标签中，正文未将其逐项列为硬门槛。LangChain、Dify、Coze 是框架举例，要求是熟悉主流框架的设计理念，不据此要求三套全会。

| 顺序 | 原文依据 | 准备目标 |
| --- | --- | --- |
| P0：真实经历与执行主线 | 任职 1–4；职责中的运行时、任务工作流和执行策略 | 证明后端与 Agent 研发经历，讲清任务如何从输入推进到结果 |
| P1：复用与交付质量 | 职责中的技能组件、交互工具、性能稳定性与可观测性；任职 2、6 | 说明组件边界、用户反馈和线上问题处理 |
| P2：优先经历 | 任职 5 与「优先条件」 | 按真实经历选择多 Agent、内容生成、多模态或规模化部署深入 |

P1 仍属于职责范围；优先级只表示准备顺序。以下恢复、测试与发布问题是为完成职责推导的工程准备点。当前没有简历和实操评估，勾选只表示完成准备，不代表已经掌握或符合岗位。

## P0：用真实项目证明职责范围

对应：任职 1、2、4、6，以及「将技术创新转化为业务价值」的优先条件。

- [ ] **说明自己的后端与 Agent 经历**：用户要完成什么任务，自己负责哪些模块？哪些是框架已有能力，哪些由自己设计或修改？学历、专业与研发年限按实际履历核对。
- [ ] **复盘一次系统设计取舍**：高并发、任务耗时、外部模型费用或可用性中，哪项约束实际影响了设计？候选方案、选择理由与结果证据分别是什么？
- [ ] **准备一次技术跟进记录**：选择实际读过、试过的模型或框架变化，说明是否适用于原项目，以及怎样验证，而不只罗列产品名称。

完成证据：项目架构、个人负责范围、一条任务记录和一次故障或取舍复盘。没有真实业务数据时如实说明，个人练习标为练习。

## P0：运行时、任务拆解与执行边界

对应：设计运行时框架、任务工作流，定义执行策略、拆解逻辑和能力边界；任职 3、4。

- [ ] **画出一个视频任务的执行过程**：以「根据素材生成候选视频、人工确认后导出」为自拟场景，输入、阶段、产物和完成条件是什么？哪些步骤由[[agent-vs-workflow|固定工作流]]推进，哪些需要模型动态决策？
- [ ] **说明模型与程序怎样分工**：结合[[react-interview|ReAct 循环]]，谁选择动作、校验参数、执行工具、接收结果并决定停止？模型输出错误参数或持续循环时怎样处理？
- [ ] **解释 LLM 应用中的基本机制**：Prompt 约束什么，RAG 补充什么信息，Function Calling 怎样连接业务工具？检索为空或工具返回失败时，后续判断需要哪些信息？此处先检查概念与任务的联系，不要求每项都已有独立项目。
- [ ] **对照一个熟悉框架解释设计**：任务状态、节点或步骤、工具执行和扩展接口在哪里？框架与自写部分怎样配合，为什么适合该任务？
- [ ] **检查失败与恢复**：素材读取失败、生成任务超时、用户取消、进程重启时，任务状态和已有产物怎样保留？哪些操作可以重复，哪些需先核实结果？

完成证据：执行图、状态与产物说明，以及成功、工具失败、取消和重启后的处理记录。可从[[agent-design-interview|Agent 设计的整体主线]]检查是否遗漏上下文、运行控制与评测。

## P1：可复用技能、工具与能力组件

对应：搭建维护面向视频自动化的可复用技能与能力组件，开发集成 AI 交互工具。

- [ ] **定义组件契约**：素材查询、内容生成、渲染和结果检查各接收什么、返回什么？哪些是业务服务，哪些封装为模型可调用工具，哪些是预设任务步骤？原文未指定技能必须采用某种文件格式或协议。
- [ ] **说明调用与版本边界**：依据[[tool-calling|工具调用流程]]，怎样校验参数、绑定调用结果、表达错误？组件升级后，旧任务与已有产物如何兼容？
- [ ] **证明复用没有丢失业务约束**：两个视频任务共享同一能力时，素材权限、输出规格和失败策略怎样传入？如何分别检查通用组件与具体任务？

完成证据：一份组件接口说明、两个复用场景和关键失败用例，能指出哪些代码复用、哪些规则由业务层决定。

## P1：对话体验与跨团队交付

对应：AI 辅助交互、对话式界面、产品整体 AI 使用体验；优先条件中的产品、UX、工程协作。

- [ ] **处理输入不完整与需求变化**：用户没有提供素材、要求存在歧义或[[agent-followup-interview|中途修改规格]]时，怎样澄清、更新任务并保留有效约束？用[[agent-context|上下文管理]]检查后续调用实际拿到了什么信息。
- [ ] **[[agent-progress-interview|设计长任务反馈]]**：界面如何区分排队、执行、待确认、部分完成和失败？用户怎样查看产物、取消或从失败处继续，怎样避免把模型的成功表述直接显示为业务完成？
- [ ] **明确协作验收**：产品、UX 与工程怎样约定输入、状态、错误提示和交付标准？意见冲突时用什么用户反馈或任务记录作判断？

完成证据：一条交互流程或界面草图，附需求变更、取消与失败反馈的验收示例。无需为准备清单重新开发完整前端。

## P1：系统设计、性能与效果验证

对应：高并发、分布式架构和抽象建模；性能、稳定性、可观测性与使用体验。

- [ ] **定位并发瓶颈**：任务增多时，模型调用、素材处理、渲染和存储分别怎样排队、限制并发和分配资源？哪个阶段慢，用什么观测证据定位？
- [ ] **还原一次失败任务**：怎样关联用户请求、模型调用、工具执行和产物，判断失败发生在哪一步？错误重试后如何检查业务结果？
- [ ] **验证改动收益**：结合[[agent-evaluation-interview|结果与过程评测]]，怎样检查任务完成、产物质量、耗时、费用和重复执行？Prompt、RAG 或框架变化后，用什么相同任务比较？

完成证据：容量假设、一次故障定位记录及同批任务的改动前后比较。测试数据、样本范围和未验证部分应明确记录，不编造生产指标。

## P2：从优先项选择深入方向

- [ ] **多 Agent、任务规划与内容生成**：选实际做过的方向，解释为何需要该方案。采用[[multi-agent-benefits|多 Agent 协作]]时，怎样分工、交换产物并核对结果，增加了什么协调成本？
- [ ] **AI 原生产品、对话界面与多模态**：用一个实际产品片段说明输入输出、失败处理、用户反馈和个人贡献；仅有文字生成经验时明确范围。
- [ ] **大规模部署与业务价值**：有相关经历时，说明部署、容量、发布或故障恢复中的具体责任，以及功能如何影响业务结果；没有则标为尚无经历。

这些是原文明示的优先方向，不要求全部补齐。面试前仍需确认实际语言与框架、岗位负责的产品、视频处理范围及年限口径。
