我会先从两个方向想：**一次请求本身要花多久，以及多个请求同时到来时，资源能不能承受。**

## 单个请求本身耗时长

即使并发不高，一次请求也可能很慢，可以继续分成两种情况：

- **「接口设计或实现不合理」**：单次处理的数据太多、计算或序列化太重；循环里逐条查数据库，或者串行调用太多下游，耗时就会累积。SQL 缺少合适索引、扫描或排序过多，以及 Redis 的[[redis-performance-sources|慢命令]]，也属于一次操作本身开销大的情况。
- **「依赖或运行环境变慢」**：代码处理量没有增加，但数据库、下游服务响应慢，或 DNS、建连、网络传输变慢，请求也会等更久。所以单次请求慢，还要区分自身处理与外部等待。

## 并发超过资源处理能力

单个请求的处理时间可能正常，但同时到来的请求太多，**有限资源被占满，后续请求就要竞争或排队**：

- **「执行资源不够」**：CPU、磁盘 I/O 或工作线程忙不过来，内存压力和 GC 开销也可能增加，具体表现取决于运行时。
- **「连接或锁成为瓶颈」**：连接池达到上限、长事务迟迟不释放连接或锁，后续请求只能等待；多个请求争用同一把锁，也会限制同时处理的数量。

这里要比较的是**请求压力与处理能力**。流量洪峰会增加压力，实例减少、资源被其他任务占用也会降低处理能力，所以 QPS 没涨也可能出现排队。

## 两类原因怎样相互放大

两类原因会互相影响。比如缓存命中率下降，尤其是[[cache-avalanche-interview|缓存集中失效]]或缓存服务故障时，会有更多请求回源；数据库压力增加后，可能继续出现：**数据库变慢 → 连接占用更久 → 连接池满 → 后续请求排队。**

如果此时[[aws-retries-summary#怎样限制等待与额外负载|超时和重试设置不合理]]，过长的等待会延长资源占用，过短的超时和多层重试又可能增加请求量，进一步放大压力。

这是可能的[[sre-cascading-failures|相互放大过程]]，是否发生还要沿[[api-latency-interview|排查流程]]核对证据。
