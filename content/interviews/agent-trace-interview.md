我会用 [[trace-and-span|Trace]] 把一次 Agent 任务的执行过程串起来，让线上报障能查到具体哪次运行、哪一步出了问题。主要分三步：

1. **把调用串起来**：一次运行建根 Span，每次模型调用、工具执行和子 Agent 调用分别建 Span，用 `trace_id` 关联整条链路，`span_id` 区分操作，父子关系表达调用归属。再关联业务 `task_id` 和会话 `session_id`；跨服务或异步任务要[[otel-trace-collection#调用关系怎样传到另一个执行单元？|传递追踪上下文]]，日志也带上 Trace、Span ID，才能互相查找。
2. **记录关键现场**：每一步保留起止时间、状态、错误和必要的输入输出，以及模型、Prompt 和代码版本。工具用 `tool_call_id` 对应模型请求与执行结果；每次重试单独记录，保留尝试次数。异常、超时或工具返回失败，都要明确记录错误和状态；内容按需脱敏，避免最后一次成功覆盖前面的失败。
3. **先找任务，再找异常步骤**：拿到报障的任务 ID，查出对应 Trace，用调用树看哪一步失败，用时间线看慢在哪里，再结合该 Span 的日志、输入输出和下游错误定位原因。父层报错可能只是子调用失败的结果，需要往下追到具体异常，核对是参数错误、模型限流、工具故障还是超时。

如果所有接口都正常返回，但答案不对，就沿[[agent-trace#在 Langfuse 排障并回归|实际执行内容]]检查「模型输入 → 工具参数 → 原始结果 → 加工后的上下文 → 最终回答」，找到第一次偏离预期的位置。**技术调用成功不代表任务做对了。** 如果链路缺记录，还要检查埋点、上下文传播、采样和导出是否丢失。
