InnoDB 默认开着死锁检测。发生死锁后，它会[[mysql-deadlock-victim|选择一个较轻的事务回滚]]，一般会参考修改了多少行、持有多少锁，尽量选择回滚代价较小的一方，让其他事务有机会继续执行。

排查时，可以用 SHOW ENGINE INNODB STATUS 看最近一次死锁报告，看看报告里的时间和 SQL 能不能对应上这次错误，再找到相关代码结合分析。还要看看事务前面执行了哪些 SQL，因为锁可能早就拿到了。

如果没抓到这次报告，或者死锁比较频繁，可以打开 `innodb_print_all_deadlocks`，把后续每次死锁的信息记到 MySQL 错误日志里，再结合 SQL 和代码排查。查完后，恢复原来的设置。

主要的排查和修复方向有几个：

1. 尽量按同一个顺序拿锁。不管是不是同一个业务，只要会操作同一批数据，就尽量都先锁 A，再锁 B。

2. 事务尽量短。一些不需要事务保护的业务处理，可以先放在事务外执行，处理完再开启事务，数据库操作做完就尽快提交。需要保证一致性的检查和修改，还是要放在事务里。

3. 看看是不是锁得太多。SQL 写得短，不代表扫描的记录少、拿的锁少。可以结合索引和执行计划，看看有没有扫太多记录，能不能减少不必要的加锁。

4. 可以补充少量重试，让业务更健壮。死锁回滚的是整个事务，所以要[[mysql-transaction-retry|重新开启事务重试]]，把事务里的读取、判断、修改重新执行，不能只重试最后一条 SQL。重试要限制次数，稍微[[retry-backoff|退避]]一下，避免马上又撞在一起。
