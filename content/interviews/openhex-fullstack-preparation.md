这份岗位要求「**独立交付 Agent 平台的 Web 全栈功能，从数据库、API 到前端交互，并参与 Agent 能力与生产可靠性的打磨**」。准备主线是一项完整功能的交付经历，前后端能力都要有具体证据，再说明怎样把模型、工具、知识库和协作能力接入产品。

依据为 2026-10-20 保存的[杭州迷境智塔高级全栈工程师 JD](https://www.zhipin.com/job_detail/eea1ec1eb6e0fe5d0nx709S9E1tV.html)，本地原件为 `content/sources/「高级全栈工程师招聘」_杭州迷境智塔科技招聘-BOSS直聘.md`。已核对完整职位描述；下列问题、准备顺序与完成证据是准备建议，不是公司真实考纲。未重新核实招聘状态、薪资和公司介绍。

## 要求性质与准备顺序

| 原文性质 | 要求与边界 |
| --- | --- |
| 页面条件 | 杭州、15–30K·14 薪、3–5 年、本科；地址为余杭区关瑞大厦 C 栋 208 室 |
| 必须：经历与办公 | 3 年以上专业全栈经验，能独立负责功能从设计到上线；杭州现场办公，不支持远程 |
| 必须：前后端基础 | 熟练使用 React / Vue，熟悉 TypeScript；Node.js / Python / Go 任一，熟悉 REST / [[graphql\|GraphQL]] API 设计；熟悉 SQL 和／或 NoSQL、Git，有务实的技术判断力 |
| 必须：主动性与 AI 使用 | 对 AI / LLM / Agent 有兴趣，已在使用相关产品；学习快，能先定位问题再讨论，能快速上手工具和平台 |
| 工作职责 | 全栈功能、可维护代码、后端服务与 API、代码评审；工具调用、浏览器自动化、RAG、多 Agent 编排；与产品及 prompt 同学协作、生产监控调试和性能优化 |
| 加分项 | LLM 应用实践；浏览器自动化或自动化工作流；向量数据库；云平台、Docker、CI/CD；创业公司或快节奏团队经历。满足任意一条即可作为加分证据 |

先准备完整交付、前端与后端基础（P0），再串起 Agent 工作链路、可靠性与协作（P1），最后选择已有经历中的加分方向（P2）。P1 仍属工作职责；优先级只表示准备顺序。LLM 开发经验是加分项，不能改写成必须已有 Agent 生产项目，但需要能讨论岗位将承担的 Agent 工作。

后端语言、数据库和产品示例保留原文的选择关系，不要求列出的工具全部会用。React / Vue、REST / GraphQL 仅以斜杠并列，具体要求待确认；下文选主要方案准备是练习安排，不替公司解释门槛。页面标签中的 Node.js、React 不足以推断公司唯一技术栈。以下权限、重试、取消、测试与发布问题，是从交付职责推导的工程准备点。尚未核对个人履历与实操；勾选仅表示已完成对应讨论和回答整理。

## P0：完整功能交付与真实履历

对应：必须项中的全栈年限、独立交付和技术判断力；职责中的端到端开发与代码质量。

- [ ] **核对履历与现场条件**：实际全栈工作年限、学历和杭州现场办公条件分别是什么？哪些功能由自己独立负责，哪些只参与其中一层？
- [ ] **讲清一项功能从设计到上线**：需求解决什么问题，怎样拆成页面、API、数据模型和服务？说明个人负责的设计、实现、联调、上线与后续维护，不把团队成果全部算作个人贡献。
- [ ] **复盘一次技术取舍**：交付时间、数据规模、性能和维护成本怎样影响方案？为什么选择当前框架、数据库和模块边界，什么变化会促使调整？

完成证据：一项真实项目的需求、架构或请求流程、核心代码与上线结果。练习可补能力证据，但不能代替 3 年以上专业全栈经历。

## P0：前端交互与 TypeScript

对应：React / Vue、TypeScript；Agent 创建与编排、对话交互、知识库管理等 Web 功能。

- [ ] **展示一个完整业务页面**：选熟悉的 React 或 Vue 项目，解释组件划分、状态与数据流、表单校验、接口请求和错误反馈；用户怎样完成一条业务流程？同时说明另一框架的熟悉范围。
- [ ] **解释 TypeScript 怎样支持维护**：沿页面、请求参数和返回数据说明类型边界；接口变更或收到异常数据时，怎样发现问题并避免错误继续传播？用实际代码说明判断。
- [ ] [[agent-progress-interview|展示 Agent 的执行进度]]：以一次 Agent 任务为场景，页面怎样区分刚提交、运行中、失败与完成？后端发送哪些阶段事件，前端展示到什么粒度？
- [ ] 等待用户补充或审批后恢复执行：页面怎样展示待回答的问题或待审批的操作？怎样关联原任务，通过同一套中断与恢复流程处理用户回答或审批决定，并按各自语义校验？
- [x] [[agent-stream-recovery-interview|处理断线与刷新后的状态恢复]]：页面失去连接或刷新后，怎样找回原任务、查询真实状态并恢复展示？重连后怎样处理遗漏或重复事件？
- [ ] [[agent-cancellation-interview|处理取消与服务端状态同步]]：用户点击取消后，页面怎样表达请求已提交、正在停止与最终结果？服务端未确认前能否显示已经取消，迟到结果怎样处理？

完成证据：可演示的页面、组件与接口代码，以及正常、输入错误、请求失败和重复操作的验证记录。已有业务页面与 Agent 场景练习可以分开提供，明确各自来源。

## P0：后端 API、数据库与工程质量

对应：Node.js / Python / Go 任一；REST / GraphQL API、SQL 和／或 NoSQL、Git；后端服务性能、稳定性与可扩展性。

- [ ] **沿一次请求解释服务实现**：使用最熟悉的后端语言，从 API 输入、校验、业务处理到存储与响应说明职责边界。用实际采用的 REST 或 [[graphql|GraphQL]] 方案解释接口设计，说明另一方案的了解程度与取舍。
- [ ] **设计并维护数据模型**：Agent 配置、对话、知识文档与执行记录需要哪些数据和关联，[[agent-upgrade-interview|配置升级后怎样处理旧任务]]？怎样依据访问模式选择 SQL 或 NoSQL、设计索引及一致性边界，变更 schema 时怎样兼容已有数据？不要求两类数据库都有生产经历。
- [ ] **证明代码可测试、可维护**：哪些逻辑需要隔离，哪些输入和失败路径值得验证？展示 Git 差异、一次代码评审及修改结果，说明如何在性能、扩展性与当前交付成本之间取舍。

完成证据：接口契约、数据模型、核心实现和必要测试，能把前端操作追到数据库中的业务结果。原文未指定后端框架、数据库产品或吞吐门槛。

## P1：把 Agent 能力接入产品

对应：职责中的工具调用、浏览器自动化、RAG、多 Agent 编排，以及与产品、prompt 同学一起提升任务完成效果。

- [ ] **说明实际 AI 产品使用**：选正在使用的 ChatGPT、Claude、Cursor、Coze、Dify 或同类产品，展示它怎样帮助完成具体任务、哪里失败、自己怎样检查结果；不要求每款都使用。
- [x] **串起一次 Agent 任务**：参考[[agent-design-interview|Agent 设计主线]]，说明用户输入、上下文、模型、工具、结果与停止条件怎样配合。沿[[tool-calling-interview|工具调用与失败处理]]解释参数校验、权限、超时和结果回传；框架现成能力与自写部分分别在哪里？
- [x] [[rag-workflow-interview|说明知识库与检索怎样参与回答]]：文档怎样导入、更新和检索，结果怎样进入模型上下文？检索为空、[[rag-document-validity-interview|资料过期或用户无权访问]]时，怎样检查并处理？向量库具体产品经验留作加分证据。
- [ ] **设计浏览器任务的验证**：页面定位、登录状态、等待和提交怎样控制？元素变化、操作超时或提交后没有收到反馈时，怎样判断真实结果，避免误报成功或重复操作？可以先做方案说明，已有自动化经历另作加分证据。
- [ ] **解释多 Agent 的分工与交接**：参考[[multi-agent|多 Agent 协作]]，[[agent-delegation-interview|什么任务值得拆分]]，[[agent-communication-interview|各成员交换什么输入、状态和产物]]，怎样处理[[agent-conflict-interview|冲突]]、失败与最终验收？公司介绍中的 A2A 闭环不等于明确要求使用[[a2a-interview|A2A 开放协议]]，具体实现待确认。

完成证据：一条任务流程及成功、工具失败、检索不足、浏览器结果不确定等路径的说明。已有项目提供执行记录；尚无经历时标为设计或练习，不把每项都升级为必须已有生产项目。

## P1：生产可靠性、效果与团队协作

对应：监控、调试、性能优化、平台可靠性；代码评审、主动定位、快速学习与产品／prompt 协作。

- [x] [[contest-bottleneck-interview|复盘一次线上排障]]：从用户操作追踪到前端、API、数据库、模型与外部工具，怎样找到慢或失败的环节？用哪些日志、指标或任务记录支持判断，怎样止血、修复并验证？
- [ ] **与产品共同定义完成标准**：用户说「跟进客户需求」时，哪些产物和业务状态才算完成，什么时候要补充输入或人工确认？参照[[agent-evaluation-interview|Agent 效果评测]]准备同一批任务的改动前后比较，区分功能正确、任务效果、耗时与成本。
- [ ] **展示主动学习与协作过程**：遇到不熟悉的工具时怎样定位、试验和提问？产品、prompt 与工程意见不同，怎样通过任务记录、用户反馈和评审形成可验收的方案？

完成证据：一次排障或明确标注的故障练习、一组验收样例和一次真实协作记录。保留环境、输入与结果，不编造生产指标或个人贡献。

## P2：选择已有经历中的加分方向

以下五类均来自原文加分项，任选有真实证据的方向深入，不设全量完成门槛。

- [ ] **LLM 应用开发**：展示 system prompt、tool use、RAG 或编排的实际改动，解释失败原因、方案取舍及效果证据，而不只演示成功回答。
- [ ] **浏览器自动化或工作流**：有 Playwright、Puppeteer 或自动化工作流经历时，展示输入、执行、结果检查及失败恢复；保留原文的「或」关系。
- [ ] **向量数据库**：选实际用过的 pgvector、Milvus、Pinecone 或同类产品，解释导入、更新、检索与效果检查，说明选型依据和未用过的能力。
- [ ] **云平台、Docker 与 CI/CD**：有相关经验时，说明自己负责的环境、构建、配置、部署与回退，展示一次实际发布及验证记录；云产品名称是举例。
- [ ] **创业或快节奏团队经历**：复盘需求变化、资源有限或从 0 到 1 的项目，说明怎样缩小交付范围、处理不确定性并对结果负责；没有则如实保留缺口。

## 面试前待确认

- [ ] **确认工作与技术边界**：实际前后端比例、框架与语言、数据库、Agent 编排方案，微信／飞书接入和 A2A 的具体含义，以及入职后首先负责的功能。
- [ ] **确认招聘条件与公司信息**：薪酬及 14 薪构成、年限与学历口径、现场办公安排和考察方式。页面显示「A 轮」，正文自述「千万级种子轮」，融资阶段需确认；客户与团队背景同样仅来自招聘方介绍。

本清单覆盖全栈开发、Agent 系统打磨两组职责，7 项必须条件和 5 类加分项；尚未评估个人能力、执行练习或核实公司面试流程。
