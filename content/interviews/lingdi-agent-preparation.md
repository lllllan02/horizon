这份岗位要求围绕「**能交付生产级 Agent 平台**」展开：既要完成模型与工具的执行循环，也要处理持久化、权限、故障、网关、客户端与消息渠道。本清单把 JD 转成可练习的问题和可检查的成果，供学习、项目复盘和面试前自查使用。

依据为 2026-10-20 保存的[凌迪科技资深 Agent 开发工程师 JD](https://www.zhipin.com/job_detail/e7c8db2a65c3da420nJ70t64FFtW.html)，本地原件为 `content/sources/「资深Agent开发工程师招聘」_凌迪科技招聘-BOSS直聘.md`。以下“职责、硬性、加分”编号沿用原文；问题、优先级与验收要求是准备建议，尚无该公司的真实面试题、轮次或评分标准。

## 怎样使用与安排顺序

采用「**要求 → 能力 → 问题 → 证据**」的编排：每项既要能讲清，也要能指出设计、代码、测试或实际经历中的依据。勾选表示已经完成该准备项，不自动代表知识库学习状态或岗位匹配度；当前没有简历和实操评估，所有能力均待自查。

| 顺序 | 本轮准备重点 | 为什么先做 |
| --- | --- | --- |
| P0：先建立主线 | 真实项目、Agent 运行时、模型网关、权限安全、Go/TS 执行与故障测试 | 对应明确硬性要求，支撑其余平台能力 |
| P1：补齐交付面 | 存储、消息渠道、本地/远程进程、Web/桌面工作流、观测与发布 | 同样属于职责或硬性要求，应在主线跑通后补齐 |
| P2：形成差异 | 选一个框架或开源项目深入，选一项桌面、网关、评测或多 Agent 能力扩展 | 原文列为加分项，按真实经历和目标选择深入方向 |

优先级表示准备先后，不改变 JD 的硬性与加分分类。先用项目材料定位哪些已有证据，再按“模型请求与工具执行 → 状态与恢复 → 接口与持久化 → 多入口与运维”补足相互依赖的内容；测试和观测从第一步就加入。

## 先准备真实项目证据

对应：硬性 1–3、5、11；职责 9。计算机相关专业本科及以上或可证明的同等工程能力、研发年限和真实用户项目经历，均需按实际履历核对，不能用短期练习替代。

- [x] [[learning-plan-agent-interview|整理一个真实 LLM/Agent 项目]]：说明用户是谁、解决什么问题、自己负责哪些模块、实际交付到哪一步。区分个人实现、团队成果、使用现成框架与自己修改的部分。
- [x] [[assets/learning-plan-agent.png|准备一张架构图与一次完整任务记录]]：能沿用户入口、运行时、模型网关、工具、存储、沙箱、结果展示逐段说明；未做过的模块明确标出。
- [x] [[learning-plan-agent-fallback|复盘一次失败与一次取舍]]：讲清触发条件、观察证据、排查假设、修改和验证；结果数字注明样本、时间窗口和比较条件，没有可靠数据就说明现象。
- [ ] **准备技术沟通材料**：用一页设计说明写清约束、方案、替代方案、接口、测试和发布风险；从实际读过的英文文档或源码定位一个影响实现的判断。

完成标准：能用简短介绍讲清项目，再接受沿架构和故障路径的连续追问。个人练习可证明动手过程，必须如实标为练习；真实用户使用经验仍需单独提供。

## P0：Agent 执行、上下文与恢复

对应：职责 1；硬性 4–6；加分 7。

- [x] [[agent-loop|画出会话与执行状态]]：[[history-storage|会话]]、一次运行、[[agent-checkpoint-runtime|步骤]]、[[tool-calling|工具调用]]分别保存什么？等待模型、等待工具、[[agent-human-in-the-loop|等待审批]]、取消、失败和结束怎样转换？
- [x] **[[tool-calling-interview|解释模型与工具的契约]]**：谁生成工具名与参数，谁校验和执行，结果怎样按调用 ID 配对？流式参数还没收全、结构化输出不合法、模型拒绝或工具返回错误时分别怎么办？
- [x] [[context-budget|设计上下文预算]]：[[claude-context-budget-summary|Token、上下文窗口、最大输出]]与调用额度有什么区别？[[agent-context-input|历史和工具结果]]变长时保留什么、[[context-trimming|裁剪什么]]、[[context-loading|怎样回查]]？能结合[[agent-context|上下文管理]]解释[[context-compaction|压缩]]等策略及其信息损失。
- [x] [[agent-checkpoint-failures-interview|走通中断恢复的失败窗口]]：进程在工具执行前、外部写入成功后但进度未落盘、等待人工审批时退出，重启后各从哪里继续？[[agent-checkpoint-interview|Checkpoint]]保存的执行位置，如何与会话历史、任务状态和外部业务结果配合？用 [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) 对照一种节点重跑的实现，说明哪些副作用可能再次执行。
- [ ] [[agent-cancellation-interview|设计用户取消与停止确认]]：用户取消怎样传播到模型、Go goroutine、Node 请求和子进程？无法确认远端是否停止时返回什么状态？
- [ ] [[agent-approval-interview|设计人工介入与审批恢复]]：怎样保存待审批调用并恢复执行？如何处理重复提交与批准后的崩溃？审批有效期与改参能力按业务需要选择。

完成标准：提供状态图与一份恢复记录示例，逐个标出持久化时点和未知状态的处理。能够说明「**保存检查点与防止重复业务效果需要分别设计**」，不能仅靠重跑函数解释恢复正确性。

## P0：模型网关与流式协议

对应：职责 3；硬性 4、6；加分 4。

- [ ] **定义兼容范围**：所说的 OpenAI 兼容究竟兼容哪个端点、字段、事件、错误和用量信息？怎样适配不支持某种 Tool Calling 或 Structured Output 的供应商？
- [ ] **处理流式异常**：上游事件被拆成多个网络分片时怎样解析？首段迟到、输出到一半断流、工具参数不完整、客户端断开时，已发送内容与最终任务状态怎样对应？
- [ ] **制定路由与重试规则**：模型按能力、可用性、额度还是成本路由？429、鉴权错误、超时与部分输出后的失败分别能否重试或切换？依据[[agent-timeout-interview|分层超时、熔断与背压]]给出总预算和停止条件。
- [ ] **设计鉴权、额度与计费账本**：入口租户身份怎样绑定到供应商凭据？并发请求如何预留与结算额度？流中断、用量缺失和重复回调怎样处理，如何区分估算与确认用量？

完成标准：给出网关接口、供应商能力表和错误处理表；用可控的模拟上游测试正常流、碎片流、限流、半途断流与缺失用量，核对输出、状态、取消和账本。以上是练习验收要求，不预设供应商具有相同的重试或计费语义。

## P0：扩展机制、权限与安全

对应：职责 2、5；硬性 5、10；加分 2。

- [ ] **划清 Skill、Plugin 与 MCP 的职责**：在自己设计的平台里，方法说明、安装与扩展单元、外部能力协议各负责什么？哪些是平台自定约定？从[[mcp-integration-interview|MCP 发现与调用流程]]和[[anthropic-agent-skills-summary|Skill 分层加载]]说明如何配合。
- [ ] **设计扩展的完整生命周期**：注册、配置校验、发现、加载、禁用、升级、版本兼容、分发和回滚怎样实现？旧任务恢复时遇到工具版本变化怎么办？
- [ ] **验证权限而非相信模型**：谁可以调用哪个工具、访问哪个工作区、使用谁的凭据？审批绑定的身份、参数、资源和有效期是什么？提示注入或 MCP 返回的文本能否改变真实授权？按 [MCP 2025-11-25 授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) 区分 HTTP 与 stdio 的凭据获取，并检查 token 是否发给正确的服务。
- [ ] **明确沙箱边界**：根据[[agent-sandbox-interview|沙箱与工具权限的分工]]，列出文件、网络、进程、CPU/内存、执行时间与密钥边界；说明路径穿越、符号链接、宿主挂载、日志泄密怎样进入检查范围。

完成标准：给出一份扩展清单、一条权限判定链和一个被拒绝的越权案例。能解释哪项限制由应用、MCP 服务、操作系统或容器承担，未知隔离保证应保留为待核实。

## P0：Go、TypeScript 与故障测试

对应：硬性 3、6、8、9；职责 8。

- [ ] **完成 Go 有界并发练习**：为工具执行设置并发上限、排队限制、总截止时间与取消；解释错误、panic、关闭和资源释放如何处理。结合[[go-context-interview|Context]]说明通知取消与实际退出的区别。
- [ ] **完成 TypeScript/Node.js 流处理练习**：处理异步异常、请求取消、慢消费者和进程退出；给出运行时参数校验，说明类型定义能保证什么、还需校验什么。
- [ ] **给两端定义一致的契约**：REST 接口的鉴权、错误码，以及流式事件、工具参数和任务状态怎样共享或生成？协议升级后，旧客户端和持久化数据怎样兼容？
- [ ] **分层安排测试**：状态转换、计费和权限用单元测试检查；模型/工具、数据库和子进程用集成测试检查；“开始任务—审批—恢复—取得产物”用端到端测试检查。哪些应使用固定响应，哪些需要真实模型评测？

完成标准：保留可运行代码、执行命令和失败用例结果。至少能针对模型波动、工具失败和网络中断分别说明注入点与断言，不用“最后返回成功”替代对业务状态与副作用的检查。

## P1：存储、消息渠道与多端一致性

对应：职责 6；硬性 6、7；加分 5。

- [ ] **设计持久化模型**：画出用户/租户、渠道身份、会话、运行、事件、审批、工具执行和产物之间的关系；明确哪些是可靠记录，哪些是缓存、锁或临时数据。
- [ ] **说明 MySQL、Redis、SQLite 的分工**：远程服务与本地客户端分别有什么并发、事务、备份和恢复需求？缓存丢失、数据库不可用或本地数据迁移时怎样处理？按使用场景比较，不要求三种存储全部用于同一任务。
- [ ] **处理消息回调与重投**：渠道账号怎样映射到平台用户且避免串租户？如何验签、持久化、确认接收、去重、重试并处理乱序？“业务提交成功、回复渠道失败”后如何避免重复执行工具？
- [ ] **恢复多端视图**：Web、桌面和消息端对同一任务并发发指令时怎样决定顺序？[[agent-stream-recovery-interview|重连后怎样获取快照和后续事件]]？两端同时批准一次动作时如何确保审批与执行状态一致？

完成标准：提交表结构与一个消息处理时序，测试同一消息重投、身份不匹配、两端竞争审批和重连补事件。能给出可保证的一致性范围及失败后的对账方式。

## P1：本地/远程运行环境与客户端交付

对应：职责 4、5；硬性 3、6、8、10；加分 3、6。

- [ ] **管理进程与工作区**：Agent 执行在哪个进程、哪台机器？Sidecar（伴随进程）怎样启动、就绪检测、退出、重启和清理？工作区路由、文件归属与产物访问怎样关联到任务及租户？
- [ ] **比较 Docker/Kubernetes 运行方案**：隔离单元、挂载、网络出口、资源限额、超时清理和残留任务怎样管理？本地执行迁到远端时，哪些路径、权限、协议和恢复假设需要改变？
- [ ] **交付 React 工作流**：最小页面呈现会话、计划、执行进展、权限请求、产物与调试信息；连接中、等待审批、失败、取消和已完成应能区分。依据[[websocket-sse-interview|SSE 与 WebSocket]]说明传输选择和断线后的恢复方案。
- [ ] **理解桌面边界**：若采用 Electron，主进程、预加载脚本、渲染进程与本地运行时如何通信并限制权限？对照 [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security) 检查上下文隔离、预加载 API 与 IPC 调用方。跨平台打包、运行时依赖和升级失败怎样处理？基础工作流先讲清，Electron 深入实现按加分方向选择。

完成标准：给出部署/进程图与一份页面状态说明；在练习中断开连接或终止 Sidecar，检查是否误报成功、留下孤儿进程或暴露其他工作区文件。容器配置应说明具体边界，不能仅用“上了 Docker”作为安全证明。

## P1：观测、排障与工程交付

对应：职责 7–9；硬性 8、9、11；加分 6、7。

- [ ] **关联日志、指标与 Trace**：哪些 ID 能串起入口、模型、工具、重试、子进程和恢复后的任务？依据[[agent-trace|执行追踪]]区分一次逻辑任务和多次调用尝试；Token、成本、敏感输入与导出失败分别怎样记录？
- [ ] **定位一次“任务很慢”**：怎样区分队列等待、首段等待、生成、工具耗时、数据库等待与客户端展示延迟？先查什么证据，怎样验证瓶颈假设？
- [ ] **区分软件测试与 Agent 效果评测**：从[[agent-evaluation-interview|任务验收与过程评测]]出发，设计成功条件、固定环境、失败样本和回归比较；能说明日志完整与任务正确为何需要分别验证。
- [ ] **完成基础环境排障**：在 Linux 上怎样检查进程、文件权限、资源和网络连接，区分进程内错误、跨进程通信和网络链路故障？怎样用 Git 定位运行版本、比较改动并安全回退？
- [ ] **说明上线与协作流程**：CI/CD 怎样运行契约、集成和端到端检查？模型、Prompt、工具、数据库和客户端版本怎样追踪与回滚？准备一次需求拆解、接口协商或故障沟通的真实案例。

完成标准：以一个失败任务展示“现象—关联记录—定位—修复—回归”的证据链，并说明指标口径、采样限制、脱敏范围和未验证部分。工具可以选 OpenTelemetry、Prometheus、Langfuse 中适合的组合，不要求全部接入。

## P2：选择一个方向深入

加分项用于证明深度。职责中已有的网关、MCP、运行环境和观测基础仍需覆盖，深入某个产品或框架再按下列方向选择。

| 方向 | 对应加分项 | 可准备的证据与追问 |
| --- | --- | --- |
| 一个开源 Agent 实现 | 1、8 | 从 OpenCode、Codex、Claude Code、Agents SDK、LangGraph、AutoGen 中选一个有可读源码的实现；固定版本，跟踪一条调用到工具执行与恢复的路径，解释一次修改或真实贡献；复杂 Monorepo 说明模块边界与依赖治理 |
| 扩展或自动化 | 2 | 深入 MCP、Skill、Plugin、Computer Use 或 Browser Automation 的一个实际功能；说明观察、动作、权限和结果验证；多 Agent 方向说明拆分收益、消息关联、失败与取消传播 |
| 桌面或消息接入 | 3、5 | 选 Electron 或一个 Bot/Gateway，展示进程/身份边界、重连、升级或重投处理，不需要接入所有平台 |
| 网关与质量优化 | 4、7 | 深入多供应商适配、路由、计费、Rerank、上下文压缩、长期记忆、任务规划或工具选择之一；解释目标、基线、质量与成本代价，实际结果与设想分开 |
| 云原生与观测 | 6 | 深入 Kubernetes 或一种观测工具，展示可复现的部署/诊断与故障恢复；说明配置、版本和可观察的失败现象 |

完成标准：选定方向至少能从现象追到接口或源码，再回到自己的设计取舍；读过项目介绍只能证明了解，不能代替开发经历。

## 用一个综合练习串起清单

需要动手补证据时，可做一个「**读取工作区资料，经批准后生成文件产物**」的 Agent。这是自拟练习，不是公司真实业务或指定作业；已有真实项目能提供证据时，优先复盘已有实现。

输入包含工作区、任务目标和用户身份；工具使用本地测试目录与模拟业务接口。选择一个实际模型供应商，另加可固定响应与故障位置的模拟供应商；网关与运行时可从 Go 服务开始，TypeScript/React 负责客户端或一个扩展，不先搭建全部基础设施。

| 验证场景 | 要观察的结果 |
| --- | --- |
| 正常执行、工具参数非法、模型返回不符合结构 | 合法请求得到可核验产物；无效参数被拒绝，界面与持久化状态一致 |
| 人工审批与拒绝 | 审批前不发生目标写入；拒绝与重复提交有明确结果；若设置有效期，过期不能视为批准 |
| 外部写成功但确认丢失 | 恢复时核对执行记录和业务状态；不能确认的调用进入明确的待核实/补偿流程，不能盲目重复 |
| 断流、限流、取消与服务重启 | 遵守预算与停止规则，未完成任务不误报成功；能说明请求是否可能仍在远端执行 |
| 断线重连与消息重投 | 客户端恢复任务视图，重复事件不导致重复业务效果 |
| 越权访问、工具超时与观测导出失败 | 拒绝越权、按策略终止并清理；诊断采集失败可被观察，业务结果另行检查 |

练习成果保留架构图、关键接口/表结构、可运行代码和测试记录即可。测试记录写明环境、版本、输入、实际输出与未通过项；没有执行过的场景保持未完成，不把这张表本身当作验证结果。

## 面试前收口与待确认事项

- [ ] **口述材料**：一次简短项目介绍、一次沿完整链路的设计讲解，以及一次有证据的故障复盘；追问时能解释取舍和失败窗口。
- [ ] **工程材料**：架构/状态图、关键接口与持久化设计、可核验代码和测试结果；机密材料脱敏，不编造用户数、性能收益或个人职责。
- [ ] **岗位确认**：页面“1–3 年”与正文“3 年及以上”冲突；公司显示凌迪科技，职责开头却写“BOSS直聘负责”。向招聘方确认年限、实际雇主/团队及 JD 是否准确。
- [ ] **工作范围确认**：StyleWork 当前形态、已有架构、Go 与 TS 的分工、本地与云端比例、上线责任、真实用户与主要故障，以及面试是否包含编码或系统设计，均需进一步确认。
