这份岗位要求「**使用 Go 和 Python 交付后端与 AI 应用，重点展示 Agent 项目和结构化 AI 编程经验**」。准备应围绕一项真实功能，串起需求判断、代码实现、模型与工具集成、验证和迭代，说明自己的责任与实际结果。

依据为 2026-10-22 保存、2026-10-23 完整核对的[壹零中枢后端开发工程师 JD 本地原件](../sources/「后端开发工程师（AI%20agent行业go语言）招聘」_壹零中枢招聘-BOSS直聘.md)。下文编号沿用原文职责 1–5、任职 1–6；问题、准备顺序与完成证据是准备建议，尚未核实公司实际考纲或当前招聘状态。

先准备 Go/Python、Agent 项目和 AI 编程证据（P0），再补架构、部署与协作（P1），最后整理已有的 0–1 经历（P2）。排序依据岗位语言要求和明示项目重点；**P1 仍属于工作职责**。页面「3–5 年」与正文「至少 1 年 Go」分别保留，不能推定总年限可直接降至 1 年。

公司介绍提到 Agent-to-Agent（A2A）协作与编排平台，职位正文未指定协议、框架或自托管模型要求。下列并发控制、故障处理、测试与发布是为履行职责推导的准备点。当前未评估个人能力，勾选仅表示完成准备，不改变知识库学习状态。

## P0：Go 与 Python 的实际开发

对应：职责 1，任职 1、2。

- [ ] **核对履历与阅读 Go 代码**：分别列明总开发年限、Go 使用时间与实际负责模块；选一段真实代码，解释切片、map、接口、错误处理与资源释放，能说明修改会影响哪些行为。短期练习与正式项目分别表述。
- [ ] **解释并发与失败处理**：结合一次服务请求，说明 goroutine、Channel 或锁怎样配合；请求超时、调用失败或用户取消后，怎样使用 [[go-context-interview|Context]] 通知下游退出，并检查阻塞、竞态与资源回收？
- [ ] **展示 Python 开发经验**：用实际代码说明依赖管理、输入输出、异常处理和测试；选择自己熟悉的 Python 开发库或 AI/ML 框架，解释它承担的工作及调用边界。保留原文「生态系统或 AI/ML 框架」的选择关系。

完成证据：Go 与 Python 各自可定位的项目代码、个人贡献说明及成功和失败用例；若两种语言在同一系统中协作，补充接口与数据约定。JD 未指定具体框架，也未要求所有服务必须混合两种语言实现。

## P0：Agent 项目怎样完成业务任务

对应：职责 3，任职 4；公司介绍中的协作与编排方向仅作背景。

- [ ] **讲清一项真实 Agent 功能**：用户要解决什么问题，为什么采用 Agent？沿一次任务说明模型、程序、工具与状态各自负责什么，以及自己的实现范围。可复用[[learning-plan-agent-interview|学习计划 Agent 项目介绍]]中的需求澄清、画像查询、选题、提交、校验与降级，再核对实际代码和贡献。
- [ ] **解释工具失败与任务停止**：工具参数错误、调用超时、结果不满足要求时如何反馈、重试或降级？怎样[[agent-loop-interview|限制循环与重复工具调用]]，并说明任务为什么结束、还有什么未完成？
- [ ] **用结果证明效果**：围绕[[agent-evaluation-interview|业务成功标准与 Agent 评测]]，准备正常、信息不足和工具失败样例；检查最终业务结果、执行过程、延迟与成本。项目已上线、做过演示和完成过评测分别提供证据。

完成证据：一份项目口述稿、任务执行轨迹、关键代码和代表性结果。已有项目介绍可承接准备，但具体使用量、效果和性能仍须核对；不把材料已整理视为此项自动完成。

## P0：结构化 AI 编程经验

对应：任职 3、5；原文提及 Codex、Claude Code 等工具资源。

- [ ] **还原一次完整研发任务**：从需求与验收条件开始，展示如何提供代码上下文、拆分任务、组织 AI 实现、读取差异、运行验证和修复问题；说明由谁作出方案与业务判断，怎样控制改动范围。
- [ ] **复盘一次错误建议或返工**：AI 曾误解什么、遗漏了哪些边界？怎样通过代码、运行结果或测试发现并纠正，最终为什么接受这份改动？能否在脱离工具后解释和继续维护代码？

完成证据：一项真实任务的需求、任务拆解、代码差异与验证结果，附个人判断和工具失误案例。「结构化」在 JD 中未给出具体标准，上述过程是准备建议；仅列工具名称或展示生成截图不足以证明交付能力。

## P1：架构、性能与模型服务集成

对应：职责 1–3，任职 5 中的工程思维。

- [ ] **复盘一项架构与选型决策**：在明确业务量、交付时间与维护条件下，如何划分 Go/Python 服务和外部模型依赖？比较采用与放弃的方案，说明扩容时哪个环节可能先受限，以及怎样验证。
- [ ] **讲清模型服务的部署与集成**：选实际经历中的一种接入方式，说明模型服务在哪里运行、应用怎样调用、配置和凭证如何管理；模型不可用、接口变化或新版本质量退化时，怎样发现、切换或回退？分别说明自己承担的部署与调用集成工作。
- [ ] **准备一次性能定位与优化**：沿[[api-latency-interview|接口耗时排查]]拆分排队、数据库、模型和工具耗时，提出可验证的瓶颈假设；相同任务、数据与负载下，对比修改前后的延迟、吞吐、错误率和资源消耗。

完成证据：架构与请求流程、选型理由、部署或接入配置，以及一次性能对照或明确标注的验证计划。模型 API 集成经历不能直接证明自托管部署经验；JD 未写必须训练模型、管理 GPU 集群或达到某个并发数字。

## P1：产品协作与必要的前端支持

对应：职责 4、5，任职 5。

- [ ] **复盘一次需求到迭代的协作**：怎样识别用户问题、澄清含糊需求，与产品、设计和前端约定接口、页面状态和验收条件？需求变化或出现问题时，如何沟通取舍、主动推动解决，并用反馈判断改动是否有效？
- [ ] **展示一项前端支持工作**：选择实际承担的页面或交互，解释接口联调、加载与错误反馈、输入校验如何处理；写清个人负责范围。原文限定为「必要时支持部分前端」，具体占比和技术栈待确认。
- [ ] **说明学习与任务承接方式**：遇到陌生框架或临时任务，怎样确认目标、补足知识、汇报风险并验证交付？用一次具体行动说明务实、主动和学习能力；职责 5 的「其他任务」范围在面谈确认。

完成证据：一次协作与迭代记录、一项前端支持成果，以及个人行动和实际结果。补做练习须注明，不能替代已有经验。

## P2：0–1 项目经历

对应：任职 5 中的明示优先条件。

- [ ] **复盘从需求到首次可用的过程**：选择真实经历，说明最初用户问题、范围取舍、最早版本、上线与反馈，以及自己负责哪些决策和实现。可从已有学习计划 Agent 经历切入，核对可展示的成果。

完成证据：初始需求、关键版本和反馈记录；区分独立负责、参与开发与个人练习。没有相应经历时如实说明，不把优先条件改写为必须补做一个项目。
