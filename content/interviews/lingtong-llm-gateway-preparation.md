这份[[llm-gateway|大模型网关]]岗位的核心是「**把普通 API 网关能力扩展为可治理、可观测、可持续运行的大模型请求入口**」：既要统一模型接入、适配协议并分发请求，也要处理 Token 限流、计费、缓存和线上故障。本清单沿用“要求 → 能力 → 问题 → 证据”的方法，用于学习、项目复盘与面试自查。

依据为 2026-10-20 保存的[杭州灵通云智算科技大模型网关工程师 JD](https://www.zhipin.com/job_detail/5235db4823e0b4e80nB_3di6F1BS.html)，本地原件为 `content/sources/「大模型网关工程师招聘」_杭州灵通云智算科技招聘-BOSS直聘.md`。下文编号沿用原文；问题、优先级和完成标准是准备建议，不是真实面试题或公司考纲。

## 岗位边界与准备顺序

原文只有 3 项职责和 4 项任职要求。先用完整请求链路组织准备，再按治理与故障场景深入；不把短 JD 扩成整个 AI 技术栈。

| 顺序 | 原文依据 | 要准备的能力 |
| --- | --- | --- |
| P0：接入与请求链路 | 职责 1；任职 2、3 | 解释 API 网关原理，完成模型接入、协议适配、路由与负载均衡 |
| P0：LLM 治理 | 职责 2 | 区分 Token/请求/并发限制，设计计费与缓存及其失败处理 |
| P0：监控与高可用 | 职责 3；任职 4 | 沿完整链路定位故障，控制超时、重试、流量和恢复 |
| P1：编码与工程证据 | 任职 1、4 | 用熟悉的语言实现、测试、压测与诊断；整理真实设计取舍 |
| P2：优先经验深入 | 任职 2 的“优先”部分 | 从 Kong、APISIX、Envoy 二次开发或自研网关中选一条路径，证明具体工程深度 |

P1 仍包含明确任职要求，顺序不表示可省略。原文要求本科及以上、3 年以上后端经验，Go、Node.js、Rust「**至少一种**」；C++ 出现在标签和简短描述中，正式任职条目没有将其列为必需，应确认实际技术栈。网关二次开发或自研经验为优先项，不要求三套产品全会，也不要求必须从零自研。

鉴权、租户隔离、记账持久化、配置发布与测试是为完成职责推导出的工程准备点，不作为原文新增的独立门槛。当前没有简历和能力评估，勾选只表示完成该准备项，不代表岗位匹配度或知识库学习状态。

## P0：网关原理、统一接入与协议适配

对应：职责 1；任职 2、3。

- [ ] **画出一次请求的完整路径**：客户端请求进入后，在哪里解析协议、识别调用方、匹配路由、执行治理规则、选择上游和转发响应？请求处理与配置更新分别由谁负责，规则执行顺序改变会影响什么？
- [ ] **定义模型适配契约**：统一入口支持哪些端点、请求字段、错误与流式事件？供应商对模型名、工具调用、结构化输出或用量信息的支持不同，哪些可以转换，哪些必须拒绝或明确声明不支持？若采用 OpenAI 兼容接口，具体兼容范围是什么？
- [ ] **区分 TCP 分片、HTTP 数据与 SSE 事件**：为什么一次网络读取不能直接当作一个 JSON 或完整事件？怎样处理半包、多事件合并、UTF-8 字符跨分片、流终止和错误事件？用[[sse|SSE 的事件格式]]检查解析边界。
- [ ] **解释长连接与双向通信**：HTTP 连接复用、代理缓冲与刷新怎样影响流式输出？[[websocket-sse-interview|SSE 与 WebSocket]]分别适用于什么交互，WebSocket 握手、帧转发、心跳与关闭怎样排查？断开 TCP 连接后，应用怎样判断任务是否完成？

完成标准：提交请求链路图、供应商能力/字段映射表，以及“正常响应—碎片流—错误响应—客户端断开”的协议测试记录。统一接口应列出实际支持范围，不能只用“接口地址一样”说明兼容。

## P0：路由、负载均衡与故障切换

对应：职责 1、3；任职 2、4。

- [ ] **区分路由与负载均衡**：先根据模型能力、租户策略、区域、成本或额度选哪个服务，再怎样在候选实例间分配？权重、连接数、在途请求和已消耗 Token 分别能表达什么负载？
- [ ] **决定何时可以重试或换上游**：连接失败、429、5xx、首段迟到、已输出部分内容时分别怎么处理？一次逻辑请求怎样关联多次尝试，避免把不同生成结果拼成同一条连续回答？如何记录可能发生的额外用量？
- [ ] **设计配置更新与故障摘除**：密钥或路由配置变化如何校验、灰度和回滚？健康探测、被动错误统计与[[service-circuit-breaker|熔断]]分别依据什么；恢复探测怎样避免把全部流量同时送回刚恢复的节点？

完成标准：固定两个可控上游，记录每次路由选择、尝试和最终结果；覆盖单上游故障、部分输出后失败、全部不可用和配置回滚。[APISIX ai-proxy-multi](https://apisix.apache.org/docs/apisix/plugins/ai-proxy-multi/) 可作为多实例代理的实现参照，需按所选版本确认策略和重试条件，不能据此推断公司架构。

## P0：Token 限流、配额与并发

对应：职责 2；任职 4。先明确「限制谁、限制什么量、在哪个时间范围统计、超出后怎么办」。

- [ ] **区分不同计量单位**：模型输入/输出 Token、[[token-bucket|令牌桶算法]]中的许可、每分钟请求数、每分钟 Token 数、在途并发数和账户总额度，各解决什么问题？同样的请求数为何可能带来不同压力？
- [ ] **设计请求前后两阶段治理**：输出长度未知时，选择预估/预留、限制最大输出、执行中控制还是完成后结算？估算与实际用量不一致、流取消或用量缺失时，如何释放、补扣、标记待核实？哪些策略允许当前请求超额，哪些要提供更严格的保证？
- [ ] **处理多实例竞争与依赖故障**：多个网关实例怎样共享租户/模型配额，判定和更新如何避免竞争超发？共享计数不可用时选择拒绝、有限放行还是本地额度，分别接受什么风险？
- [ ] **控制慢请求积压**：速率没超但长流占满连接时怎么办？结合[[service-backpressure|背压]]设计并发上限、有界等待、排队超时和公平性，明确队列满后的行为。

完成标准：给出计量单位、范围、原子更新和故障策略；用并发请求验证普通流量、突发、长输出、取消与多实例竞争。测试应分别检查放行量、实际用量和残留预留，不能只断言“返回了 429”。

[APISIX ai-rate-limiting](https://apisix.apache.org/docs/apisix/plugins/ai-rate-limiting/) 提供按模型用量限制请求的实现参照；其文档示例允许本次响应用量超过剩余额度、再限制后续请求。这与请求前严格预占的目标不同，应先选定需要的保证，再比较实现。

## P0：计费记录与对账

对应：职责 2。限流决定能否继续使用，计费还需说明哪些用量归属于哪次调用、以什么价格结算。

- [ ] **设计逻辑请求与调用尝试的记录**：调用方、租户、模型、供应商、尝试编号、时间、输入/输出用量、价格版本和结算状态怎样关联？哪些来自供应商确认，哪些是本地估算？
- [ ] **复盘不确定用量**：流中断而最终用量未到达、上游已执行但本地超时、失败后重试或缓存命中时，分别记录什么？平台向用户收费和供应商实际成本有哪些独立规则需要确认？
- [ ] **处理重复与漏记**：用量事件重复、写入失败或网关重启时怎样重放和对账？如何让一次调用不会被重复结算，又能发现漏记、未确认和价格版本变化？

完成标准：画记账状态与持久化时点，提供“成功—取消—重试—重复事件—未知用量”的账本示例和核对结果。「**估算、供应商确认用量、平台收费规则与已结算金额必须可区分**」，不能用 Token 总数直接代表完整账本。

## P0：缓存的收益、正确性与隔离

对应：职责 2。

- [ ] **明确缓存对象**：网关复用完整响应、语义相似请求复用结果、供应商复用 Prompt 前缀计算，分别改变了哪段处理？先选择精确响应缓存验证基本能力，语义缓存与供应商 Prompt Cache 作为对照，不默认全部实现。
- [ ] **定义缓存键与隔离范围**：租户、模型/版本、消息、生成参数、工具定义和权限变化中，哪些应进入匹配或失效规则？私人数据、带外部状态的请求和不完整流是否允许缓存？
- [ ] **验证命中后的协议与记账**：缓存重放时怎样生成流式事件、终止信号和用量记录？并发未命中、[[cache-avalanche-interview|过期洪峰]]、后端缓存不可用时怎样处理，如何检验性能收益与错误复用的代价？

完成标准：列出可缓存条件、键、TTL/失效、租户边界及失败策略；检查相同输入命中、关键参数变化未误命中、跨租户隔离和不完整流不进入完整响应缓存。

[APISIX ai-cache](https://apisix.apache.org/docs/apisix/plugins/ai-cache/) 是响应/语义缓存的参照，文档说明其默认隔离按路由，按 consumer 隔离需配置；缓存 SSE 时只保存完整终止的响应。因此不能仅凭“按路由建缓存”推定租户隔离已经满足。具体能力按选定版本复核，不把插件行为当作所有缓存实现的统一保证。

## P0：全链路监控、高可用与排障

对应：职责 3；任职 3、4。

- [ ] **拆开延迟与失败口径**：分别测量入口排队、连接上游、首个有效事件、持续生成、下游发送和端到端耗时；统计错误、限流、取消、部分完成与成功的规则是什么？网关自身开销怎样与模型生成耗时区分？
- [ ] **关联诊断证据**：一次逻辑请求、多次上游尝试、租户、路由、模型、用量与记账状态怎样用日志、指标和 Trace 串联？敏感 Prompt/密钥怎样脱敏，指标标签如何避免无限增长，采集或导出失败怎样被发现？
- [ ] **设计超时与容量保护**：连接、读取空闲、首段等待、整条请求的[[timeout-and-deadline|超时与截止时间]]分别覆盖什么？如何处理慢上游、慢客户端、连接/文件描述符耗尽和并发峰值？什么条件触发拒绝、熔断、降级或切流？
- [ ] **完成故障处置复盘**：从“首段变慢、错误升高、账本异常、网关内存增长”中选一个，按[[api-latency-interview|现象、证据、定位、止血、修复与验证]]形成路径；配置变更、依赖中断和实例重启如何恢复？

完成标准：给出诊断视图与故障演练记录，能区分上游问题、代理转发问题和客户端接收问题；为关键指标写明统计窗口和成功条件。没有公司 SLA 和规模数据，不自行规定其可用性或性能门槛。

[NGINX proxy 模块](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) 中的 `proxy_read_timeout` 是连续两次读取之间的超时，不等于整个请求时限；已经向客户端发送响应后，也不能依靠换上游透明修复原响应。这些边界可用来检查自己的流式超时与故障策略。

## P1：编码、压测与项目表达

对应：任职 1、4。示例可优先使用熟悉的 Go；Node.js 或 Rust 同样符合原文语言选择。

- [ ] **实现可取消的流式代理**：模块划分覆盖协议适配、路由、治理、传输、计量和诊断；检查连接池、响应体关闭、取消传播、缓冲上限与异常收尾。Go 方向可结合[[go-context-interview|Context]]解释取消何时真正生效。
- [ ] **准备一套可重复压测**：固定负载模型、输入/输出长度分布、并发数、连接复用、流持续时间和软硬件环境；区分模拟上游的代理开销实验与真实模型实验，比较吞吐、延迟分位数、错误率、CPU/内存/连接数。若声称“高性能”，说明基线、瓶颈和取舍。
- [ ] **提供代码与故障证据**：用代码审查说明接口、错误分类、资源释放和测试习惯；准备一次真实项目中的容量/一致性取舍和故障复盘。没有网关生产经历时，可以展示后端项目的可迁移经验与练习，但需明确各自范围。

完成标准：保留可运行代码、启动与测试命令、压测条件和实际结果；能沿某个失败请求定位到代码。练习结果只能说明该环境与负载下的表现，不推断为公司业务规模下的保证。

## P2：选择一条网关深入路径

对应：任职 2 的优先经验。先决定扩展成熟产品还是自研核心，再证明自己解决过什么问题。

| 路径 | 准备什么 | 什么证据能支持深入程度 |
| --- | --- | --- |
| Kong/APISIX/Envoy 二次开发 | 选择实际接触的一套，跟踪请求生命周期、扩展入口、插件/过滤器顺序、配置更新和错误收尾；语言与扩展方式按实际机制选择 | 固定版本/提交，一项真实改动或练习扩展、对应测试、性能代价与升级兼容说明 |
| 自研网关 | 说明为何现有产品不能直接满足需求，自己承担了哪些路由、传输、治理与运维能力，以及维护成本 | 架构与模块边界、关键实现、与基线比较的实验、失败处理和可回滚发布方案 |

选择其中一条准备即可；资料阅读、个人实验、二次开发和真实线上责任分别表述。该岗位未明确要求 Agent 运行时、桌面端、模型训练或 GPU 调度，不把上一份 [[lingdi-agent-preparation|Agent 平台岗位清单]]的全部内容搬来；两者可复用流式治理和故障处理基础。

## 一个可选综合练习

实现一个「**双上游模型网关**」：客户端用同一入口提交请求，网关按规则选上游，支持普通响应与 SSE，增加租户 Token 配额、用量记录和可关闭的精确响应缓存。使用两个可编排分片、延迟、错误和用量返回的模拟上游，不必购买模型服务；再按需要对接一个真实供应商检查协议差异。

| 场景 | 要检查的结果 |
| --- | --- |
| SSE 事件跨多个网络分片，或一片含多个事件 | 按事件边界解析/转发，内容、顺序和结束信号正确 |
| 首段前失败与部分输出后失败 | 执行各自的重试/切换策略，部分结果不冒充完整响应，每次尝试可追踪 |
| 两租户并发、额度临界与共享计数故障 | 不串租户；实际放行和超额范围符合已声明策略，预留与结算能核对 |
| 用量缺失、记账事件重复或进程重启 | 未确认记录可发现，重复事件不重复结算，可恢复或对账 |
| 缓存命中、参数变化、租户变化与不完整流 | 命中范围符合缓存策略，避免错误复用；命中用量与费用口径明确 |
| 慢客户端、取消、上游卡住与网关实例退出 | 缓冲/并发有界，超时与清理符合策略，残留请求和连接可观察 |

练习成果为请求链路图、关键接口/状态、代码和测试/压测记录。未运行的场景保留未完成，不把测试矩阵本身称为验证；无需先搭建多种网关产品或完整云平台。

## 面试前收口与待确认事项

- [ ] **整理口述与证据**：一次项目介绍、一次完整请求链路讲解、一次流式故障复盘，配架构图、关键代码和有条件说明的测试数据。
- [ ] **确认真实工作范围**：现有网关产品/版本、二开还是自研、主要语言与 C++ 占比、接入的模型/协议、现有团队分工与上线责任。
- [ ] **确认治理目标与面试形式**：流量/并发与输出长度分布、限流允许误差、收费规则、缓存隐私边界、SLA，以及是否考察编码、源码或系统设计；这些信息 JD 均未交代，不能预设。

本清单覆盖原文职责 1–3 与任职 1–4，沿用项目 tech-study-map 的目标、问题与证据对应方法。官方资料核对日期为 2026-10-20；APISIX 插件参考页面标示 3.19.0，链接内容仍可能更新，实施时应固定实际版本。当前交付为准备目标与验收要求，尚未评估个人差距、执行练习或核实公司面试流程。
