我会在[[agent-checkpoint-recovery|Checkpoint]]里保存当前进度，并关联这次[[tool-approvals|待审批的工具调用]]：包括审批 ID、调用 ID、工具名、版本、完整参数和审批状态。**先持久化，再展示给用户审批；批准后执行原来保存的调用。** 这些信息可以直接放在 Checkpoint 中，也可以另存记录、通过 ID 关联。

重复点击或客户端重试，可能让同一个批准请求到达多次。我会用原子条件更新，只允许状态从 `pending` 变成 `approved` 一次，重复请求返回已有状态，避免重复触发执行。批准结果也要持久化：即使批准后、工具启动前服务退出，重启仍能找到已批准但未执行的调用；拒绝则跳过调用，把结果交回 Agent。

审批去重只保证同一次批准不会反复触发恢复。工具已经执行、结果却没保存时，仍要按[[agent-checkpoint-failures-interview|工具执行的故障恢复机制]]核查结果和处理幂等。

**审批不一定需要过期。** 没有业务时效要求、持久状态仍保留时，可以一直等待用户批准，[[langgraph-human-interrupts|LangGraph 的中断机制]]也支持这种等待。参数可以在申请时冻结，批准接口只提交审批 ID 和决定，无须支持改参；确实需要更换参数或工具版本时，再创建新调用并重新审批。

**缺少必要信息时向用户提问，也可以复用同一套中断与恢复流程。** 保存问题和已有进度，向用户展示问题后结束当前执行；收到回答时，关联原任务与本次中断，校验回答、合入上下文，再恢复执行，并防止重复恢复。等待期间无须保持原 HTTP 请求。[[intent-clarification|澄清]]补充的是信息，审批确认的是操作权限，两者按各自语义校验；补充信息不等于批准后续操作。
