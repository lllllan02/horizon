我会让用户在 Agent 执行期间继续补充要求，由程序在后续步骤中纳入处理。实现上就是**「接收并保存消息 → 通知执行程序 → 取出消息 → 合入上下文 → 下一次调用模型」**。

只把消息写进数据库或文件，不会自动让执行程序感知到。可以通过[[agent-communication-interview|同进程的 Channel，或跨进程的 Redis 等通信方式]]通知它，也可以让执行循环在每次调用模型前检查待处理消息。接收端负责入队，执行循环按顺序取出，作为用户消息追加到当前对话中，再组装下一次请求。模型拿到的是更新后的[[agent-context-input|上下文]]，按普通用户消息理解和处理，不需要专门的「追加消息」接口。

**补充消息通常从下一次模型调用开始生效，已经发出的请求不会自动改变。** 如果用户要求立即停止当前操作，就需要另外走[[agent-cancellation-interview|取消机制]]，不能只等消息被读取；已经完成的外部操作也不会因追加消息自动撤销。

需要可靠保存时，我会先持久化消息，再发通知，并用消息 ID 防止重复消费；通知丢失后仍能查回待处理消息。任务结束与消息到达也要协调好：新消息要么被当前执行接收，要么触发后续处理，避免留在队列里没人读取。
