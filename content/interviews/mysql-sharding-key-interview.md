我会先根据业务主要的查询方式选择[[mysql-sharding-sources#从业务拆库到水平分片|分片键（Sharding Key）]]。比如经常按用户 ID 查订单，就考虑按用户 ID 分片；主要按地区筛选，就考虑按地区分片，同时检查数据和请求是否均衡、字段是否稳定，以及关联操作能否尽量留在同一个分片。

如果「**多个查询维度都很频繁**」，会结合核心读写链路、一致性要求和查询成本，选择一种主要分片方式，其他查询再按场景补充访问路径：

1. [[mysql-sharding-sources#路由映射补充查询入口|添加路由映射表]]：比如订单已经按用户 ID 分片，只知道订单号时，可以先通过映射表找到数据位置，再查询目标分片。映射需要随订单变更保持一致；定位以后，分片内部仍然需要合适的数据库索引。

2. [[mysql-sharding-sources#多维高频查询与物化数据|额外维护查询副表]]：如果按地区查询的订单散在很多分片，映射后仍然需要多片查询、归并结果。跨片开销可以接受时就保留这种方式；如果查询频繁、开销很大，可以额外维护一份按地区组织的查询数据：业务写入以主表为准，再通过[[data-sync-interview|异步复制]]更新地区查询数据，后台直接查这份数据。

   这种方式增加了存储和同步成本，也可能有延迟；如果必须立即读到最新结果，就不能直接依赖异步查询副本。
