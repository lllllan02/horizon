**GraphQL 是面向 API 的查询语言，以及在服务端按类型系统执行这些请求的运行时。** 客户端在请求中写明需要哪些字段，服务端校验后提供数据，返回的数据结构与字段选择相对应。

当列表页只需要用户姓名，详情页还需要联系方式和文章时，客户端可以针对各自页面选择字段，减少接收无关数据；有关联的对象也能在同一次操作中请求。前提是服务端已开放这些字段和关系，客户端不能任意读取底层数据。

## 一次查询

假设 API 提供用户及其文章，客户端可以发送：

```graphql
query {
  user(id: "42") {
    name
    posts {
      title
    }
  }
}
```

一次成功响应可以是：

```json
{
  "data": {
    "user": {
      "name": "小林",
      "posts": [{ "title": "接口设计笔记" }]
    }
  }
}
```

这里请求的是 ID 为 `42` 的用户姓名，以及该用户文章的标题；未选择联系方式或文章正文。以上是说明语法的假设示例。

服务端用「**Schema（模式）**」定义 API 有哪些类型、字段、参数及关系，例如 `user` 接受 `id` 参数，用户有 `name` 和 `posts` 字段。收到请求后先按 Schema 校验，再由「**Resolver（字段解析函数）**」提供字段值：它可以读取已有对象属性，也可以调用业务服务或数据库，最后组装响应。具体过程见[[graphql-official-guide#类型契约与执行|官方类型系统与执行导读]]。

## 查询、修改与订阅

GraphQL 的操作分为三类：

- **Query（查询）**：读取数据，如上面的用户查询。
- **Mutation（变更）**：执行创建、修改、删除等有副作用的操作，并选择要返回的结果字段。
- **Subscription（订阅）**：建立持续请求，在事件发生时接收所选数据；具体传输可用 [[websocket|WebSocket]] 或 SSE，由实现约定。

Schema 必须支持 Query，Mutation 与 Subscription 按需提供。订阅的事件来源、连接维护和重连仍需要相应实现，见[[graphql-official-guide#操作与订阅|操作与订阅导读]]。

## 与数据库、REST 的关系

GraphQL 作用于 API 层，**不绑定数据库或存储引擎**。名称中的「Graph」指类型之间可以表达关系，例如用户关联文章；采用它不要求把数据存入图数据库。Resolver 背后仍可使用 SQL、NoSQL 或现有服务。

REST 与 GraphQL 都可作为同一业务系统的 API 入口。GraphQL 的辨识点是类型化 Schema 和请求中的字段选择；接入后，已有业务规则、数据存储及权限判断仍需保留，见[[graphql-official-guide#业务边界与执行成本|业务边界与执行成本]]。

**按需返回字段，不保证只读取相应数据库列，也不保证只执行一次数据库查询。** 若每个关联对象都单独取数，仍可能出现 N+1：先查一次列表，再为 N 个对象分别查询关联数据。因此 GraphQL 需要维护 Schema、Resolver 和取数效率，也需要校验调用者权限及限制昂贵查询；它本身不保证接口更快。
