**Redis Streams 可以按事件 ID 读取保留的历史事件，并在没有新事件时阻塞等待；恢复范围受事件保留策略限制。** 本文节选 Redis 在线文档中 XREAD 的读取位置与阻塞语义，以及 XTRIM 的裁剪行为，核对于 2026-10-20；不覆盖消费组、Redis 故障持久性或完整部署方案。

## 按事件位置补读与等待新消息

[XREAD 文档](https://redis.io/docs/latest/commands/xread/)规定，调用方为每条流提供一个 ID，命令返回 ID 严格大于该位置的条目。因此，读完一批后以最后收到的 ID 继续读取，就能推进读取位置。

使用 BLOCK 时，已有符合条件的事件会立即返回；没有事件时，才等待新事件或阻塞超时。历史补读和实时等待可以沿同一个读取位置连续进行，无须在两种读取模式之间另设一个切换时点。

特殊 ID `$` 表示从调用时流的末尾开始，只关注之后的新事件。文档明确指出，后续调用应传入最后收到的 ID；反复使用 `$`，可能跳过两次调用之间新增的条目。因此，重连时已有恢复位置，就应从该位置继续读取。

据此可以设计「历史快照＋事件位置」的应用恢复协议：快照表示已经包含到哪里，再补读这个位置之后的事件。**快照与位置一致、事件处理去重，以及位置与实际已应用内容对应，都需要应用保证**，不是 XREAD 自动提供的能力。若先订阅新事件再查快照，仍须补齐快照位置与订阅起点之间的事件。

## 裁剪决定能够回放多久

[XTRIM 文档](https://redis.io/docs/latest/commands/xtrim/)提供按条目数量 MAXLEN 或最小 ID MINID 裁剪流的方式，并区分精确与近似裁剪。已经删除的条目无法通过继续 XREAD 找回；一个旧游标仍能读到后续数据，不代表中间事件完整。

由此可归纳：应用需要定义回放窗口，并识别所需历史已不完整的情况。窗口之外应改用覆盖缺口的完整快照或最终结果；如果它们也不完整，就需要明确反馈无法恢复全部中间输出，不能宣称已经无损恢复。

以上恢复协议属于基于命令语义的设计归纳，未执行断线、并发读写或裁剪实验。
