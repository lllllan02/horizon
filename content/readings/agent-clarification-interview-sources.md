**这些回答将是否追问与上下文、信息来源及猜错代价联系起来，不能据此得到一个通用的“模糊度阈值”。** 前两份直接回答何时澄清，第三份讨论已知意图集合的分类与迭代。本文仅总结相关题目，以及 zero2Agent 的多轮状态说明，不覆盖三个页面的全部内容；网站的面经归属未独立核实，也未复现其效果。

## zero2Agent：先看能否自行补齐信息

原题为「一个 Agent 系统里，什么时候应该追问用户，什么时候应该自己继续推理？」及后续极度模糊请求的追问，位于[记忆与上下文章节](https://onefly.top/zero2Agent/learn-agent-interview/04-memory-context/index.html)。

作者从两项检查出发：缺口是否影响执行，能否通过上下文或外部资料补足，再结合错误代价和可逆性决定。已有可信信息可以减少重复追问；历史偏好不足以确定当前要求时，应呈现理解并请用户确认，低风险情况可采用默认值并保留修正入口。

对于几乎没有目标信息的请求，原文提出先利用会话和入口信号，再生成少量候选让用户选择。置信度也应结合证据、字段完整性与工具反馈，不能只看模型自报。作者要求每次只问一题且必须带选项，这是其交互建议，原文没有提供足以推广到所有任务的对比实验；默认行动也不能替代必要授权。

同章后续关于状态与上下文的问答，将状态用于显式保存任务事实、进展、结果与待确认信息，运行时再按需组织为模型上下文。可据此补充多轮澄清：用户后续只说增量要求时，模型结合已保存的任务信息理解和更新，而非只对最新一句话判断。这里的改进是维护重要信息，不是重复传递本来已经在对话中的历史。

## 规划面试题：先消除会带来高成本返工的未知

[规划第18题](https://book.zyh.lol/interview/planning/)询问「什么时候应该先让 Agent 产出澄清问题，而不是直接开始执行？」

其回答指出，目标存在不同理解、重要限制缺失、完成标准不明，或者第一步出错会带来较大代价时，应优先澄清。原因是过早执行会把未经确认的猜测变成后续计划的前提，增加返工。

对低风险、容易试探且能快速收到反馈的任务，可以先推进局部工作。原文强调消除会影响后续结果的未知，而不追求所有信息齐全；它提供了判断方向，没有给出让模型可靠识别所有歧义的算法。

## 牛客：固定意图分类的澄清与评测闭环

[程序员芝士的文章](https://www.nowcoder.com/discuss/908634420217675776?sourceSSR=post)针对多个已知意图提出分层识别：规则处理确定请求，Embedding 缩小候选集合，再由 LLM 分类；不确定时询问用户，收到补充后重新识别。

作者进一步建议用 Trace 回放输入、候选、提示词和识别结果，定位错误环节；从真实请求抽样标注，形成评测集与长期回归集，检查提示词或模型更新是否退化。运行指标用于发现异常，不能直接证明语义判断正确。

**这套分类架构依赖已定义的意图集合。** 可借鉴澄清后的重新判断、错例回流与回归验证，不能直接作为通用 Agent 的理解方案。文中用于演示的置信度阈值未提供通用校准依据，标题里的比例也不是本次核实的统计结论；其关于生产系统普遍做法的概括不作为事实采用。

## 对通用 Agent 的参考价值

结合上述答法，核心开发方向是在提示词中让模型检查目标、预期结果和重要要求，区分已知内容与猜测，再按缺口的影响决定追问、查证或采用默认值。工具校验是反馈，语义判断仍由模型完成。

多轮对话中可进一步维护[[agent-task-state|任务状态]]：模型提取并更新已确认要求、待解决问题与进展，程序保存；收到补充时先[[agent-task-state-update|合并有效要求]]，再判断仍缺什么。对话本就包含历史时，不能把“再次提供上下文”本身算作新增优化。最后用真实错例校准漏问、多问和错误推进。这些是结合来源与任务状态机制的工程归纳，不是三份原文共同验证过的完整实现。

开放任务的目标与缺口仍由模型结合当前对话理解，不能靠固定意图标签覆盖。[[agent-clarification-strategies|通用澄清研究]]补充了动态提出意图假设、比较追问收益的依据，也保留了近似估计和效果验证的限制。
