**「原文把 Agent 开发中的工程重点转向环境、知识组织和可执行反馈：模型遇到困难时，团队检查缺少了什么条件，再把条件补进系统。」**

## 为什么有模型还不足以交付？

团队尝试由 Codex 编写产品代码与配套工程产物。早期进展慢，原因包括缺少可用工具、结构与信息；人类的职责因此转向拆解目标、定义验收和改善工作环境。

仅让 Agent 写代码，仍会把验证压力留给人。团队让应用按工作区独立启动，并提供浏览器、日志与指标访问，使 Agent 能自行复现问题和验证修改。

## 知识为什么从大提示改为可导航的仓库？

把全部规则放进 AGENTS.md 会占用窗口、模糊优先级，也难以维护。团队改用短入口指向仓库中的设计、计划和参考文档，按任务逐步读取；计划与进度也作为版本化材料保存。

这依赖可发现、可维护的记录：只存在于聊天或人员记忆中的决定，Agent 无法可靠使用。文档检查与定期整理用于减少事实来源失效。

## 文档仍不能阻止架构漂移

团队把依赖方向、日志和命名等约束写成检查程序，并**「在错误信息里给出修复线索」**。模型得到的反馈因而从「请遵守规范」变成具体违规与下一步动作；边界内仍保留实现自由。

Agent 也会复制仓库中的坏模式。团队将人工集中清理改为持续扫描、小范围修复，把重复出现的意见转成规则或工具，避免偏差继续传播。

## 哪些经验不能直接照搬？

原文较少阻塞合并、偏向快速修复的做法，建立在高吞吐和特定工具投入上，并非通用发布规则。报告的效率提升是团队估计，长期架构维护仍是开放问题。

其方法是**「将失败反馈到环境、知识和检查机制中」**，而不只是反复修改同一条提示。
