**「作者把 Harness 广义地理解为模型之外的配套系统，并从希望 Agent 具备的行为，反推需要哪些机制。」** 这包括代码、配置、工具与基础设施，不代表它们必须是一个部署单元。

## 从生成输出，到操作真实任务

模型本身不能持久保存工作、执行程序或准备环境。要让它处理真实任务，首先需要工作区与文件工具：资料和中间结果可以存放在窗口之外，Git 则提供版本与交接记录。

只有文件还不够。Bash 和代码执行让模型组合操作，而不必为每个动作预先设计专用工具；沙箱提供执行边界，浏览器、日志与测试工具让模型观察结果。这些能力共同形成「行动 → 观察 → 验证」的反馈。

## 信息增长后，不能只增加输入

原文给出三种互补机制：

- 历史接近窗口上限时压缩，保留后续工作所需信息。
- 工具输出过大时，将完整结果放到文件，只把必要片段交给模型。
- 工具或能力说明过多时，通过 Skills 等方式按需展开，避免启动时全部加载。

记忆和搜索补充已有经验与新信息，但仍通过上下文供模型使用。它们没有改变模型权重，也不能免除输入选择。

## 怎样支撑长任务？

文件与 Git 留下进展，规划维护待办，验证为修正提供依据。原文还介绍用退出钩子继续任务的循环模式：重新开始的上下文通过文件接续工作。这里的关键依赖是持久状态与完成条件，而非单纯增加循环次数。

## 模型变强后，Harness 会消失吗？

作者区分两种作用：**「补偿当前模型不足」**，以及**「提供环境、工具、状态和验证条件」**。前者可能随模型升级减少，后者仍有价值。模型训练与工具接口也会相互适应，因此改动 Harness 应实测，不能只凭组件更多判断效果。
