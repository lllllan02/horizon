**「LangChain 将上下文工程归纳为写入、选择、压缩与隔离四类可组合策略，分别处理信息存在哪里、何时取入、怎样缩减和由谁使用。」** 本文导读对应 2025-07-02 的文章。

## 问题为什么不限于窗口超长？

历史积累还会带来错误被反复引用、既有内容牵制行为、无关信息干扰，以及信息彼此冲突。原文借用 Drew Breunig 的失败分类，说明控制 token 数不能独自解决这些问题。

## 四类策略分别改变什么？

| 策略 | 机制与例子 | 必要取舍 |
| --- | --- | --- |
| 写入（Write） | 把计划等信息保存到文件或运行状态；跨会话经验存为长期记忆 | 保存之后仍需决定何时读取 |
| 选择（Select） | 从笔记、记忆、知识和工具定义中取当前相关部分 | 召回可能引入无关偏好；代码检索可组合搜索、结构信息与重排 |
| 压缩（Compress） | 摘要改写历史、工具结果或交接信息；裁剪直接过滤记录 | 关键事件与决策容易遗漏，需核对保留质量 |
| 隔离（Isolate） | 子 Agent 使用独立窗口；环境变量和状态字段保存大对象，只向模型暴露所需部分 | 子 Agent 增加协调与 token 成本；隔离也可在单 Agent 内完成 |

例如，工具返回的大对象可以留在执行环境，模型只接收选定结果。这里的上下文隔离表示「信息没有全部进入模型输入」，并不自动代表安全权限隔离。

## 怎样判断实现是否有效？

作者建议**「先观察真实轨迹和 token 使用」**，再评测改动对任务结果的影响。LangGraph 用检查点持久化线程状态、用长期存储跨会话保存信息；节点可选择输入、处理摘要，状态字段与沙箱可承载外部数据。LangSmith 用于追踪和评测。

这些框架能力是文中实现示例，四类策略并不依赖特定框架。文章汇集不同系统经验，不能把其中某个实验的收益直接推广到其他任务；工具数量较多时的检索方案，也需结合 [[manus-context-engineering-summary|Manus 提出的缓存与历史一致性约束]]判断。
