**「Anthropic 将上下文工程（Context Engineering）定义为持续选择、维护模型推理时所见信息的工作，目标是用足够且高信号的输入支持下一步行动。」** 本文是其 2025-09-29 工程文章的导读。

## 为什么提示词之外还需要管理？

Agent 循环不断加入工具结果和历史，输入的相关性随任务变化。作者援引长上下文研究，指出**「窗口能容纳信息，不代表模型能同样可靠地利用它」**；因此每次调用都要重新考虑指令、工具、外部资料与历史的组合。

## 先把输入设计清楚

系统指令应明确又留有判断空间：过细的条件分支容易脆弱，过空的原则又不能指导行为。工具应职责清晰、参数易懂、返回精简；示例应有代表性和差异，避免堆满边缘案例。作者建议从最小可用提示开始，根据实际失败补充。

## 信息何时进入窗口？

[[context-loading|按需加载]]**「先保留路径、查询或链接，再由工具读取细节」**。文件名、目录和时间等元数据帮助缩小探索范围。例如用查询及局部文件读取处理大数据，而不把整份结果塞进输入。

每次读取还会提供下一步的线索：目录和文件名帮助判断用途，大小提示内容规模，时间信息帮助判断相关性。模型逐步缩小范围，不要求先建立向量索引；针对性查询、文件搜索和局部读取也能支持这一过程。

原文以 Claude Code 说明混合方式：先提供项目指令，再通过 glob、grep 等工具定位需要的文件。代价是运行时探索增加延迟，也可能走错方向或遗漏关键信息，因此工具和检索指导同样重要。此处对应原文 `Context retrieval and agentic search`，讨论的是任务资料获取。

## 长任务怎样延续？

| 做法 | 保留什么、怎样继续 | 取舍 |
| --- | --- | --- |
| 压缩（Compaction） | 摘要保留决策、未决问题和必要细节，继续新一轮交互 | 先检查遗漏，再删除冗余；未来所需细节可能被误删 |
| 外置笔记 | 将目标、进度、依赖写入文件，重置后读回 | 适合有明确阶段的迭代任务；文中以游戏进度与地图为例 |
| 子 Agent | 在独立窗口探索，向主 Agent 返回精炼结果 | 适合可分工研究，主 Agent 无需接收全部探索过程 |

旧工具结果清理也是一种较轻的处理方式。上述做法按任务组合；本文提供工程经验，不能据此认定所有任务都有相同收益。
