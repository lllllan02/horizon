**SGD（Schema-Guided Dialogue）用能力说明定义可办理的任务，再按对话轮次记录用户目标、参数和动作。** 它帮助区分「系统能做什么」「本轮说了什么」与「目前已知道什么」。

本篇节选 Google 数据集 README 的 Schema Representation 与 Dialogue Representation，不总结全部基准实验。

## 整体怎样组织？

服务能力说明 → 对话中按服务记录每轮内容 → 保存累计状态与系统动作 → 用标注检查理解结果

能力说明称为 schema，其中列出意图与槽位，并给出自然语言描述。槽位是日期等参数；每个意图说明哪些必填、可选、属于结果，以及是否为交易操作。这样，识别任务后还能判断信息是否齐全。

## 一轮表达与累计状态有何不同？

每轮按服务组织的记录称为 frame。`frame.slots` 用字符位置定位当前句中的非枚举槽位，`frame.state` 保存当前意图 `active_intent`、用户询问字段 `requested_slots` 和已知值 `slot_values`。

当前句没有重复订单号，累计状态仍可保留此前提供的订单号。非枚举槽位在 `slot_values` 中的字符串列表表示同一个值的不同写法，例如「下午六点」与「18:00」，不能当成多个独立对象。

用户动作还区分提供、询问、肯定、否定，以及接受或拒绝系统建议。因此找到一个编号只完成内容定位，还要判断它是在被提供、纠正还是否定。系统请求补充、确认、报告结果及服务调用也分别记录。

## 设计时有哪些边界？

**「用户询问的字段」与「系统缺少的必填参数」不同。** 后者要结合任务定义和已有值计算，不能直接照搬 `requested_slots`。

评估集包含未见服务或领域；SGD-X 用意义接近、措辞不同的能力描述检查描述变化的影响。它能提示描述质量影响理解，但不提供所有业务通用的状态合并算法、数据库并发或执行授权保证。

这是任务型对话数据结构，适合作为设计参考。原记录注明仓库于 2026-04-19 归档，本篇按静态资料使用。
