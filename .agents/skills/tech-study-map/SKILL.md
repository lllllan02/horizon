# 技术学习清单与问题探索

核心能力是理解用户当前想解决什么学习问题，判断还需要了解、澄清、实现或验证哪些内容，并将其组织成能继续讨论的清单、问题或补充说明。用户可以从一个主题开始，也可以在讨论、阅读、项目分析或复习过程中随时使用；不要求先走完整规划流程。

遵守项目 [AGENTS.md](../../../AGENTS.md)。知识库检索与保存沿用 [知识库管理细则](../../../docs/knowledge-management.md)。以下场景和输出方式是可组合的参考，不是能力白名单；遇到新场景，用相同的判断方法处理，不因未列出而要求用户换成某个固定模式。

## 理解本轮目的

结合当前提问和上下文，判断用户想拓展范围、理解机制、补足前置、深入实现、分析项目取舍、准备面试，还是检查已有内容。这些目的可以并存，并可随讨论变化。

利用已经提供的信息开始工作，不要求固定的公司、简历、年限、技术栈或能力表。缺少信息时先给在现有条件下有用的内容，简短标明影响结论的假设；只有歧义会显著改变方向时才澄清。用户给出的范围、数量、形式和深度优先。大专题整理且范围或深度未明确时，按[分层推进细则](../../../docs/knowledge-management.md#大专题的分层推进)先确认，不能用假设替代用户对学习范围的选择。

## 大专题整理的推进

按[专题工作方法](../../../docs/knowledge-management.md#专题整理的工作方法)与[分层推进](../../../docs/knowledge-management.md#大专题的分层推进)执行当前阶段。每轮保存交给 knowledge-save，结构调整交给 knowledge-maintain；用[场景检查](references/evaluation-cases.md)核对范围与停止点，不另维护一套推进规则。

## 获取需要的依据

按本轮目的选择材料，不必每次执行所有检索：

- 从主题或一般场景生成清单时，按用户目标确定范围；涉及技术事实与机制判断时，先按[回答与写作的依据](../../../docs/knowledge-management.md#回答与写作的依据)核对材料。除非任务需要，不默认关联或巡检知识库；已有笔记数量不决定应学范围。
- 用户要求基于某个话题检索知识库、检查卡片或从已有材料出题时，先读指定材料；未指定文件则按项目检索细则用 `npm --silent --prefix apps/web run retrieve -- query <主题词及同义词>` 定向搜索配置中启用的内容目录，再读相关正文和必要引用。结论引用实际文件，不能仅凭标题判断覆盖；检索异常与截断按项目规则处理。
- 用户指出当前讨论太浅、实现不具体或问题不合理时，先检查当前讨论和已知约束，不自动扩大为全库巡检。项目资料、代码或外部文档与问题直接相关时，可按任务需要读取核对。
- 涉及产品版本、配置、实现行为或真实面试事实时，核对官方文档、源码或明确原始来源，保留适用条件。区分输入事实、库内依据、模型推导与待核实信息；设想的项目场景和生成的面试题不能冒充用户经历或真实面试记录。

用户要求先找文档时，直接按学习主题及其同义词检索，优先选择官方设计说明、教程或公开源码；不把范围限制在前面偶然提到的产品，也不只返回搜索计划。筛选少量互补材料，说明各自能回答什么、具体定位和适用条件，避免用大量重复链接代替判断。领域问题优先选直接涉及该场景的资料，通用理论只补必要前置。

资料查找、阅读总结、形成自己的方案可以分阶段进行；用户要求「先找资料，再讨论」时先完成检索，不把产品做法直接写成唯一方案。要求保存时接入 knowledge-save，外部摘要按[来源与巡检](../../../docs/knowledge-management.md#来源与巡检)归入 readings，自己的判断更新相应卡片。用户未要求保存时仍留在对话中。

## 识别值得学习和补充的内容

编排主题或收到「只需了解、不要太深入」等要求时，按[专题入口细则](../../../docs/knowledge-management.md#专题入口与阅读组织)区分覆盖范围与展开深度，核对调整前后重要方面是否仍清楚可见；未要求保存时仅在对话中完成判断，不写卡或 TODO。

围绕“当前目标需要什么，而现有解释或材料提供了什么”作判断。按需组合以下角度，不给每个话题机械套全部维度：

- **范围与前置**：主要问题是否覆盖，哪些概念或关系是理解它的前提，哪些只是可选延伸；合并重复考点，避免把学习点拆成孤立术语。
- **机制与因果**：是否只有结论，能否讲清参与者、处理过程、状态变化，以及为什么会得到这个结果。
- **实现与验证**：需要哪些数据结构、接口、状态或协调步骤；成功与失败路径如何处理；用什么现象、测试或指标判断实现满足要求。按目标选择必要细节，不默认全部深入源码。
- **场景与取舍**：业务目标、规模、一致性、延迟、资源或运维约束怎样影响方案；更换条件后结论是否仍成立，有哪些替代选择及代价。
- **问题与解释质量**：题目前提是否成立，约束是否足够，是否有多个合理答案；现有解释有无错误、跳步、缺少边界或与目标深度不匹配。

基于 JD 生成面试、准备或学习清单时，按[JD 拆解与准备清单](../../../docs/writing-style.md#jd-拆解与准备清单)核对要求性质、范围、能力与证据、优先级及覆盖；本技能提供通用探索方法，不另维护岗位清单标准。基于卡片时，先确认其原本的问题范围及相关卡片是否已有展开；概念篇简短不等于质量不足，应区分正文错误、目标深度下的解释不足和另一个值得学习的问题。

## 把建议落实为可判断的问题

形成关键学习项或补充建议时，连起以下关系。它用于检查内容质量，不要求每次展示成四列表格，也不强制用户接受测验：

- **为什么需要**：对应哪个用户目标、JD 条目、项目约束或材料中的具体表述；仅为扩展视野的建议要标为可选，不宣称用户存在缺口。
- **要能做到什么**：写清具体动作、对象与条件，避免只写“了解原理”“掌握某技术”。
- **什么结果算达到目标**：说明回答应解释的关键关系，或实现应表现出的行为及边界。这是判断标准，不是完整标准答案；不把“说了关键词”当作理解证据。
- **什么问题能检验或推进它**：题目、追问或练习应当确实需要上述能力。若只靠复述定义就能回答，就不能用它证明实现、排障或方案取舍能力。

这是对上游目标—证据—任务关系的简化适配（见 [S3](references/sources.md#s3)），而不是要求建立评分系统。用户只要学习清单时可以不展示题目，但要求本身仍应具体到可判断；若一项混入互不依赖的目标就分开，若多题只检验同一关系就合并。

检查材料时，将上述“为什么需要”落到实际段落，并区分：已经说明、只提到但缺少必要解释、当前检索范围未找到、证据不足待确认。再确定下一步是阅读已有内容、补一段解释、验证某个判断，还是学习新的问题。缺少提及不能直接判为内容错误或用户不会。这是借鉴简历证据映射后的项目适配（见 [S5](references/sources.md#s5)）。

例如，“能处理消费重试”若对应数据库写入场景，判断标准可落在“能解释业务提交与消息确认之间的失败窗口，并说明如何避免重复业务效果”；相应问题是“业务写入已提交，但消息确认前进程退出，恢复后应怎样处理？”只问“什么是幂等”不足以覆盖这个目标。具体正确性仍须结合实现和数据约束核对。

## 形成有用的输出

选择最能帮助用户继续学习的形式，不强制每次同时输出学习路线、题库、答案和评估报告：

- **学习要求／待学清单**：说清要了解或掌握什么，必要时说明前置、顺序及优先级。
- **问题／追问**：把需要理解的关系转成可讨论的问题，必要时说明考察点、场景条件或追问方向。
- **检查意见／补充建议**：指出具体解释或材料的不足、为什么影响目标，以及值得补充的问题或内容。
- **补充说明／例子／验证任务**：用户希望继续深入时，可直接补足必要解释，用场景、实现思路或小型练习帮助理解，不必先重新列一份完整清单。

“了解、理解、掌握”可用于标记目标深度，但要附具体要求；目标深度、学习优先级与用户当前能力分别判断。资料有记载、已经讲过或读过，均不能证明用户已经掌握；材料缺少说明也不能证明用户不会。

问题应服务学习目标，数量随范围和请求变化，不固定十题、不凑同义题。场景题交代影响判断的约束，保留合理的多种方案，不把有条件结论当唯一答案。需要真实面试依据时才作相应事实判断，不以“必考”、频率或通过率包装推断。

提出实现练习时，交代任务、必要输入与约束、预期结果和验证方式；帮助和解答按用户需要提供。可围绕同一核心目标逐步增加约束，而不是仅换成“简单／困难”的标签。这取自 [S6](references/sources.md#s6) 的任务与结果结构，不要求所有学习都做练习。

默认聚焦本轮最有用的内容；范围大时按模块呈现主要问题和必要顺序，说明尚未展开部分，避免遗漏关键要求或一次灌入所有细节。用户只要问题时不附整套答案，只要要求时不硬塞题库；需要实操时可提出实现与验证任务，不需要时不强加 Demo、部署或日程。

## 随讨论继续推进

沿用已经形成的清单、场景约束和讨论结论，根据用户的追问、理解困难或新材料补充、调整、深入或转向。需要追问时，先指出已有解释或回答中的具体未决处，再选择机制、边界、取舍或验证方向深入；已经讲清的部分不重复，未经讨论的部分记为未知，不推断为答错。此做法借鉴 [S4](references/sources.md#s4)，不继承强制一问一答或模拟面试阶段。用户要求检查回答或抽查时围绕选定内容处理；单纯索要清单不自动开始模拟面试、评分或逐题作答。

问题、建议和补充说明可以先在对话中用于学习。用户要求保存、补充或修订知识卡片时，使用项目 [knowledge-save](../knowledge-save/SKILL.md) 检索归属并写回，无需重复确认。保存范围以用户要求和讨论收敛内容为准；不把未讨论的整份清单自动扩写为卡片，也不把每个追问机械拆卡。

### 按回答逐步追问

用户要求“围绕这篇笔记追问我”“检查我的理解”或“帮我推敲这个方案”时，可采用以下方式推进（借鉴 [S7](references/sources.md#s7) 的问题依赖与动态调整方法）。普通答疑、讲解或生成清单不自动进入连续追问。

- 围绕当前目标区分已经说明、仍需澄清和依赖前提的问题。优先解决会改变后续判断的前提；后一个问题依赖尚未回答的条件时，等条件明确后再问，不替用户假定答案。彼此独立且负担较小的问题可以一起问，不固定每轮数量，也不要求展示整棵问题树。
- 每轮根据实际回答调整下一问：已讲清的部分跳过，含糊处用例子或条件变化澄清，前提变化时重新核对受影响的结论；不照着预设题单问到底。能从笔记、代码或来源查明的事实先自行核对，把个人目标、真实经历和方案取舍留给用户说明。
- 检查理解时先让用户解释，再针对回答反馈或追问，默认不提前展示推荐答案。推敲方案时可以给出有条件的建议与理由，保留不同选择的代价；用户接受建议不等于已经理解，技术事实也不靠用户选择来确定。
- 用户缺少前置或要求解释时转为补讲，不把“不知道”变成继续加压的理由。达到本轮目标、用户要求停止或转向时收束，简短说明已澄清内容及仍待确认处；不以穷尽分支为完成条件，不自动评分、保存或改变学习状态。

交付前确认：内容是否回应当前目的，要求与问题是否具体且有依据，假设和事实是否分明，是否顺应用户的学习方式，以及是否仅在本轮需要时才检索、展开或保存。没有明显缺口时如实说明，不为凑建议而制造问题。用户只要几个模块时先给粗粒度方向，随后逐项深入；不要把可选生产场景、复杂审批或持久化实现都当作当前必学要求。按[学习反馈与修订](../../../docs/knowledge-management.md#学习反馈与修订)记录获准暂缓的 TODO；按[正文写法](../../../docs/writing-style.md)提供具体规则与 Go 风格示例。

## 来源与维护

本技能参考并改写了五个仓库中的六个 MIT 技能的部分方法，并借鉴 grilling 的问题依赖与动态追问思路，结合用户要求作项目适配。逐项来源、取舍和证据局限见 [来源说明](references/sources.md)，原六个技能的许可证见 [LICENSE.txt](LICENSE.txt)。来源存在不等于方法已被实证验证，技能方法也不能替代技术事实来源。维护时用 [场景检查](references/evaluation-cases.md) 检查实际输出，不把格式校验当作效果证明；不依赖原仓库工具或全局技能。
