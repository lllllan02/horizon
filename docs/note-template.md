本模板从 Agent 专题的现有文档提炼，用于后续新建知识笔记。默认阅读主线是 **「是什么 → 为什么需要 → 怎样运作与有什么边界」**，需要指导使用、设计或排障时，再补工程实践中的「怎么做」。短文可以用几个段落讲完，不必逐项设标题。

具体要求由 [[docs/writing-style|正文写法]] 维护，本文件提供成稿骨架与参考方式。Reading、随查术语、项目规则和 Skill 按各自用途组织，不直接套用完整骨架。

## 正文骨架

先确定本篇要让读者理解或判断的一个问题，再裁剪下面的骨架。标题改为当前内容的简短名称，删掉不需要的小节及所有占位说明。

```markdown
**概念名（必要的英文名）是……。**

在……场景下，它帮助……，因此适合……。这里说明具体收益及必要条件；
仍不足以理解时，再补原有做法遇到的困难与代价。

## 基本过程

从……输入开始，由……依据……处理，得到……结果。
先让读者认识整体，再解释其中真正需要展开的关系或判断。
涉及反馈循环时，交代反馈带回什么、回到哪里、何时停止。

（关系或变化较复杂时，在这里插入配图，让图承担具体展开。）

保留读者应从过程或配图得到的核心判断，并说明它仍受什么条件限制。

## 工程实践

（只在本篇需要指导实践时保留，标题可改成具体的设计或操作问题。）
说明在什么条件下采用什么做法、由谁执行、依据什么判断，
以及怎样检查结果；失败或证据不足时怎样处理。
代码、命令或配置只保留影响理解和使用的部分。

## 适用边界

（边界较多时独立成节；一句话能说清的，放回相关定义或做法旁边。）
说明不能保证什么、会增加什么成本，以及何时需要其他方案配合。
```

这份骨架规定需要讲清的信息，章节顺序与数量随解释需要调整。承接前篇困难的机制文章，可以先用一两句交代困难，再引出定义；边界也可以紧接相关结论。正文标题从二级开始，文档标题、时间、标签和学习状态按 [[docs/metadata-and-links|格式规则]] 填写，不复制其他笔记的状态或时间。

## 开篇怎样写

开篇让读者直接知道对象是什么、在什么情况下有用。定义独立成段，指出对象所属类别与关键特征；动机通常紧接一句或一段，不写成「提高效率、增强可靠性」这样的笼统收益。

例如，[[content/notes/agent-checkpoint-recovery|中断恢复]]的开篇写法可提炼为：

> **中断恢复（Interruption Recovery）是利用持久保存的数据与执行进度，在中断后接续未完成任务的机制。**
>
> Agent 意外退出，或暂停等待审批、补充信息与外部结果后，可以由原进程或新进程接手，复用已完成的工作。

这两段先给出定义，再把收益落到中断和接手的场景；接下来才需要解释保存什么、怎样恢复、哪些工作可能重做。开篇一般讲到这种程度即可，不为动机补一套冗长故事。

## 正文按问题展开

不同类型的文章保留不同重点，不把骨架中的「基本过程」和「工程实践」变成每篇的必填栏目：

| 文章用途 | 展开重点 | 现有参考 |
| --- | --- | --- |
| 专题概览 | 定义、用途与基本运行方式；由实际困难引出各分支，在对应解释中链接子文 | [[content/notes/agent\|Agent]] 从最小循环逐步引出上下文、规划、恢复等能力 |
| 概念与机制 | 处理对象、整体过程与关键变化；说明为什么这样处理、还受什么限制 | [[content/notes/agent-context\|上下文管理]] 用整体图与少量要点解释窗口内外材料怎样配合 |
| 比较与选型 | 先解释共同问题及方案，再按可比维度说明差异、代价与选择条件 | [[content/notes/agent-vs-workflow\|Agent 与工作流]] 将选择落在「谁决定下一步」与步骤是否明确 |
| 工程实践 | 简要承接概念与目的，重点给出执行方法、判断依据、结果验证及失败处理 | [[content/notes/agent-evaluation-practice\|Agent 评测示例]] 交代运行条件、实际结果与验证范围 |

需要多个新概念时，在各自参与解决问题的位置分别定义；涉及模型与程序协作时，明确谁判断、谁执行、谁保存、谁验收。例子用于补解释缺口，代码用于展示关键判断，不因骨架留了位置就追加完整工程。

## 复杂处如何交给图

**「文字保留定义、原因、判断与边界，图片展开复杂关系和对象变化。」** 同一件事已经由图解释清楚，就删去正文里的逐框复述；读者略过图片，仍应知道为什么需要这个机制、适用条件是什么。

| 理解困难 | 图中应让读者直接看见 |
| --- | --- |
| 多个对象怎样配合 | 对象、归属与包含关系，以及必要的数据流转 |
| 同一对象发生了什么变化 | 处理前后的内容、保留与改变的部分，以及导致变化的操作 |
| 为什么需要一种机制 | 相同输入或约束下，原做法的困难与引入机制后的变化 |
| 循环或分支怎样结束 | 判断条件、反馈返回位置，以及正常与已纳入范围的异常出口 |

例如，[[content/notes/agent-memory#容量与保留期限|记忆保留期限]]用图呈现过期、归档和淘汰的不同效果，正文只补期限与容量的选择依据。简单先后关系用一行箭头，共同维度的比较用表格，记录格式用少量 JSON，不必都生成图片。

配图放在对应解释处，沿用 [[docs/writing-style#图文分工|图文分工]] 的默认画风、内容取舍与显示尺寸要求；具体绘制交给 excalidraw-diagram。图要展示具体对象及其变化，不能只是把段落中的术语装进框里，也不为配图增加本篇没有讨论的组件。

## 交付前读回

按 [[docs/writing-style#阅读验收|阅读验收]] 检查实际正文，重点确认：

- **「脱离聊天仍能读懂」**：读者能说明对象是什么、为什么值得用，进入做法时不需要自己补出关键原因。
- **「实践有判断与验证」**：需要指导操作的部分能回答何时用、怎样做、怎样判断结果；来源事实、假设示例、推导和实测结果可区分。
- **「图文各有作用」**：图解释复杂处，正文保留核心判断；同一案例、过程或结论不因换用图表而重复保留。
- **「单篇围绕一个问题」**：删掉重复与无关展开；确需独立深入时复用或拆分子文，链接落在需要它的概念或做法上。

模板帮助安排解释，完成与否仍以正文能否讲清当前问题为准，不能只检查栏目是否齐全。
