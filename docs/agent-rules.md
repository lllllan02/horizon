本文件维护规则的归属、修订依据与 Skill 选用标准。知识内容的归属见 [[docs/knowledge-management|知识库管理细则]]。

## 规则维护

反思嵌入实际任务：收到用户要求、纠正、对结果的评价，或发现同类习惯反复出现时，就核对当前做法与用户期望的差距，并在当轮落实；不等待任务结束、定期复盘或用户另行要求记录。

1. 先修正当前结果。结合上下文确定反馈针对内容、深度、表达还是操作方式，检查整个受影响部分，不只改被点名的一句话。
2. 判断适用范围。“以后都这样”等明确长期要求直接持久化；多次一致反馈能支持的习惯，提炼出适用条件后写入对应规范。单次选择或例子只用于当前任务；是否长期适用仍有歧义时，先完成当前修正，只有会影响后续行为的重要歧义才简短澄清，不擅自推广。
3. 找到现有落点再改。已有规则明确时修正执行，并检查读取、操作或验收环节为何漏掉；表述不清就改原条目，确有缺口才补充。规则按下表归属，功能行为落实到代码，知识内容按保存授权写回，不将反馈复制成另一份日志。
4. 读回当前结果和更新的规则，确认要求已实际体现、适用边界清楚且没有重复或冲突；后续同类任务按该规则执行，再次反馈时修正原落点。简短说明持久化了什么及位置，不把写入成功当作效果已验证。

这项授权允许在项目内及时维护要求与习惯，不要求逐次确认；明确只读或禁止写入时遵从当前限制。无新增可复用要求时不制造规则，不恢复独立的经验目录、状态追踪或反思记录。

规则按职责存放，每项详细规则只维护一份，其他入口保留适用条件与链接：

| 位置 | 唯一职责 |
| --- | --- |
| AGENTS.md | 跨任务约束、授权边界和任务路由 |
| docs/knowledge-management.md | 知识检索、归属、来源、专题覆盖与学习反馈的判断 |
| docs/metadata-and-links.md | 目录、命名、字段、状态、日期与链接语法 |
| docs/writing-style.md | 个人写作与展示偏好、学习编排和阅读验收 |
| 本文件 | 规则归属、Skill 选用与验收 |
| .agents/skills/*/SKILL.md | 有明确触发条件的操作流程及按需参考入口 |
| Skill 的 references、scripts、assets | 条件性详解、可执行工具、交付用素材；不是另一套项目规范 |
| README 与 apps/web/README | 项目使用和实现说明；不复制 Agent 流程或格式规范 |

修改前重读当前文件，保留并行编辑。正文、规则与代码分别在所属位置修正；代码缺陷优先修实现，不用“以后注意”替代修复。不因维护规则扩大成知识库或代码全面改写。只有偏好而没有独立流程时，不新建 Skill。

## Skill 选用与替换

先找当前流程的具体缺口，再检查候选的正文、参考资源、依赖、许可与维护来源。安装量和仓库声誉只辅助筛选，不能证明质量；不因搜索命中或名称相近就覆盖本地技能。优先复用会话已有能力；项目专用规则保留在 docs，外部技能不能带入另一套目录、模板、学习状态或授权流程。

项目能力按职责组合：

- knowledge-save 编排新内容写回，knowledge-maintain 负责既有结构操作；规则修改直接按本文件处理。
- tech-study-map 组织学习目标与问题，summarize 读取和总结材料；两者只有在保存授权下才交给 knowledge-save。
- obsidian-markdown 提供语法，tag-taxonomy 处理标签语义；字段含义只在格式文档维护。
- frontend-design 负责视觉方案与实现，web-design-guidelines 负责界面质量审查；Three.js 三个 Skill 分别负责场景生命周期、后处理和着色器，按实际改动选用。
- excalidraw-diagram 编排知识配图，按需用 Excalidraw 交付可编辑图，或配合 imagegen 生成插画式解释图；默认画风与图文分工由写作规则决定。

本项目已适配的 Obsidian、Summarize、Excalidraw 和 Three.js 能力继续保留上游来源。经正文比较，Anthropic 的 [doc-coauthoring](https://github.com/anthropics/skills/tree/main/skills/doc-coauthoring) 侧重多阶段共同写作，不替换日常入库流程；Vercel 的 [web-design-guidelines](https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines) 用于补足界面审查，采用本地适配入口，不照搬英语文案惯例、框架假设或固定性能阈值。

借鉴 Arpit Bhayani 的 [ape-help-me-understand](https://github.com/arpitbbhayani/ape-skills/blob/master/ape-help-me-understand/SKILL.md)（[MIT](https://github.com/arpitbbhayani/ape-skills/blob/master/LICENSE)）中的判断与证据梳理、摘要保真和类比边界方法，按项目需要改写：来源核对集中在知识库管理细则，教学解释与图文取舍集中在正文写法，summarize 和知识配图技能只编排执行。不引入其固定四段式、品牌文案、同目录另存规则或样式依赖。

替换时保留有效本地适配与上游许可，比较触发边界和实际输出；先确认旧资源的调用者，再移除被替代内容并更新引用。新增 Skill 不要求添加无用途的 README、日志或模板。不要批量更新无关全局技能、安装 hooks 或启动后台任务。

## 依赖与示例兼容

开发 Skill 的示例是实现选项，不授权依赖升级或架构迁移。使用前核对 `apps/web/package.json`、安装版本和实际调用点；Three.js 示例接入现有生命周期，避免复制第二套 renderer 或动画循环。按变更检查 resize、资源释放、颜色转换和实际渲染等适用行为，参考代码存在不代表兼容或性能已验证。

## 规则验收

1. 对照改动前的有效要求，确认都保留、合并或有新归属；保留用户已有编辑。查入站引用，更新移动后的路径与锚点。
2. 对同一任务沿「AGENTS → docs → Skill」走一遍，检查触发、授权、判断与验收是否一致，详细规范是否只在一处维护。读取范围不应循环要求加载全部文件。
3. 对实质修改的 Skill 使用可用的 skill-creator 检查 frontmatter、触发描述、引用与必要脚本；可执行脚本改动须运行验证。用有代表性的请求推演路由、写入范围和停止条件，复杂行为只有实际运行后才称已验证。
4. 读回实际结果，确认用户要求已落实；简短报告变化及验证边界，不另存修订流水。
